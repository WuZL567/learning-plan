# SSE 流式输出

## 什么是 SSE

SSE（Server-Sent Events，服务器推送事件）是浏览器原生支持的一种"服务器持续往浏览器推消息"的技术。它基于普通 HTTP 长连接，响应头里的 Content-Type 必须是 text/event-stream。

AI 应用大量使用 SSE，因为大模型的输出是一个字一个字产生的。如果等全部生成完再一次性返回，用户要盯着空白屏幕十几秒；用 SSE 边生成边推，感觉就像"AI 在打字"。

## 为什么不用 WebSocket

AI 输出是单向的：服务器到浏览器，不需要双向通信。SSE 基于普通 HTTP，浏览器原生支持、自动重连、实现比 WebSocket 轻得多。WebSocket 适合聊天室这类双方都要随时发消息的场景。

另一个现实原因：EventSource 只支持 GET 请求，而聊天必须把对话内容 POST 过去，所以生产环境的 AI 应用基本都是 fetch 加手动解析 SSE，而不是用 EventSource。

## SSE 的帧格式

一帧的格式是若干条 data 行，最后跟一个空行表示这条消息结束。

    data: 第一行
    data: 第二行
    （这里有一个空行）

data 后面跟一个空格是约定不是必须。正文里的换行必须拆成多条 data 行，因为换行符已经被征用成结构符号了。如果正文里直接写换行，接收端会把它当成一条 data 行的结束，紧跟其后的文字既不以 data 开头也不是空行，按规范会被直接忽略，现象就是"AI 回答里某几个字凭空消失"。

## 帧边界和网络块边界没有关系

这是实践中最容易踩的坑。SSE 的一帧是"data 内容加空行"，但网络可能把 data 那一行和后面的空行分成两次给你。也就是说，一次 read 拿到的可能是半帧、一帧、或者三帧半。

所以行缓冲区和帧状态必须声明在读取循环外面。如果写在循环里，每次读网络块都会重置，导致跨块的帧被丢掉，现象是整段回答一个字都不显示，而且时好时坏。

## 怎么知道说完了

流正常读完、后端进程被 kill、网线被拔，这三种情况在前端看来都是 read 返回 done 为 true，一模一样。HTTP 层分不出来，只能在应用层加一个哨兵信号，比如最后推一条 data: [DONE]。

前端循环结束后检查有没有见过这个哨兵，没见过就当异常处理。

## 流式接口的错误怎么传

HTTP 的状态码写在响应头里，而响应头在第一块数据之前就发出去了，发出去就收不回来。所以流到一半出错时没法改成 500，只能在流里推一条自定义事件，比如 event: app_error，data 里放给人看的文案。最后仍然要补一条 [DONE]，否则浏览器的 EventSource 会当网络抖动自动重连。

## 停止生成

前端用 AbortController 可以中止 fetch 请求。但要注意停止不是立刻生效的：后端如果用的是同步客户端跑在线程池里，取消要等当前那次网络读返回，所以最多会多读一块回来。生产做法是改用异步客户端，并检测连接是否已断开。
