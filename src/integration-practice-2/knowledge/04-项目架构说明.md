# 项目架构说明

## 整体结构

这是一个最小可用的 AI 问答 Demo，包含三部分：浏览器前端、FastAPI 后端、外部模型 API。

浏览器不能直接调大模型，因为 API Key 会暴露在 Network 面板里，任何人按 F12 就能抄走刷爆额度。所以后端充当"中转站"：浏览器把问题发给后端，后端带着 Key 去调模型，再把结果传回来。

## 请求链路

前端用 fetch 发一个 POST 到 /chat/stream，请求体里有本轮问题、历史对话和 temperature。后端先用 Pydantic 校验请求体，脏数据在进业务代码之前就被拦成 422。

校验通过后，后端把系统提示、历史对话、本轮问题拼成 messages 数组发给模型。这就是多轮对话的全部秘密：模型本身没有记忆，所谓"记得上文"，不过是把之前的对话原样再发一遍给它。

模型以流的方式返回，后端收到一块就转成 SSE 帧推给前端，前端边收边渲染。

## 为什么对话历史由前端传

后端保持无状态，加机器就能水平扩展，不用考虑"这个用户的会话在哪台机器上"。演示项目够用。真要做多用户，历史应该放 Redis 或数据库，用 session_id 关联。

## 三个接口

/health 是健康检查，部署时用来看服务活没活。

/chat 是非流式接口，等全部生成完一次性返回，留着是为了和流式版做对比。

/chat/stream 是流式接口，也是这个项目的主力接口。

## 已知限制

后端无状态，对话历史由前端传，没做多设备同步。

停止生成不是立刻生效的，因为后端用同步客户端跑在线程池里，取消要等当前那次网络读返回。

没有上下文摘要压缩，历史只按条数截断，长对话会丢早期信息。

没有做限流和鉴权，任何人都能调这个接口刷额度。
