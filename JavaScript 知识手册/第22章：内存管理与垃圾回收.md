# 第22章：内存管理与垃圾回收

## 22.1 为什么需要垃圾回收

**一句话解释：**
程序运行时会不断创建变量、对象、函数，这些都占用内存。如果不及时清理不再使用的数据，内存会被耗尽，程序崩溃。垃圾回收（Garbage Collection，简称 GC）就是 JS 引擎**自动找出不再使用的数据并释放内存**的机制。

**餐厅比喻：**
厨房的空间是有限的（内存有限）。厨师不断从仓库拿食材出来放在台面上（创建变量），菜做好了端出去后，用完的食材包装、废弃的配料碗还堆在台面上（不再使用的数据）。如果不及时清理台面，厨房就会被垃圾堆满，没法继续做菜。垃圾回收就是**自动打扫卫生的清洁工**——他定期巡视，发现没人用的东西就清走。

~~~
程序内存的生命周期：

1. 分配内存    → 程序创建变量、对象、函数时，自动分配内存
2. 使用内存    → 读写变量、调用函数
3. 释放内存    → 不再需要时，垃圾回收器自动回收

┌─────────────────────────────────────────┐
│              内存（台面空间）              │
│                                         │
│  ┌──────┐  ┌──────┐  ┌──────┐          │
│  │ 菜品A │  │ 菜品B │  │ 菜品C │          │
│  │ 还在用 │  │ 没人要 │  │ 还在用 │          │
│  └──────┘  └──────┘  └──────┘          │
│              ↑                          │
│         垃圾回收器：这个没人要了，清走！   │
└─────────────────────────────────────────┘
~~~

~~~javascript
// ========== 内存自动分配 ==========
let 名字 = "红烧肉";              // 分配一块内存存字符串
let 价格 = 38;                    // 分配一块内存存数字
let 菜品 = { 名字, 价格 };         // 分配一块内存存对象

// ========== 内存自动释放 ==========
菜品 = null;  // 菜品不再引用那个对象，垃圾回收器会回收它
// 但 名字 和 价格 还在用，不会被回收
~~~

## 22.2 引用计数（Reference Counting）

**一句话解释：**
最古老的垃圾回收策略——看一个对象**被引用了多少次**。引用次数为 0 时，就认为它是垃圾，可以回收。

**餐厅比喻：**
每份食材上贴了一个**计数器**——有几个人在用它，计数器就显示几。当最后一个人用完了（计数器归零），清洁工就把它扔掉。

~~~javascript
// ========== 引用计数的基本原理 ==========
let 菜品A = { 名字: "红烧肉" };   // 菜品A 被(citation:1)次（变量 指向它）
let 菜品B = 菜品A;                 // 菜品A 被(citation:2)次（菜品A 和 菜品B 都指向它）

菜品A = null;                       // 菜品A 引用减少为1次（只有 菜品B 指向它）
菜品B = null;                       // 菜品A 引用减少为0次 → 垃圾回收！
// { 名字: "红烧肉" } 这个对象被回收了
~~~

### 引用计数的致命缺陷：循环引用

~~~javascript
// ========== 循环引用：两个对象互相引用，引用计数永远不为 0 ==========
function 做菜() {
  let 厨师 = { 名字: "张师傅" };
  let 菜品 = { 名字: "红烧肉" };

  厨师.正在做 = 菜品;   // 厨师 引用 菜品
  菜品.负责厨师 = 厨师;  // 菜品 引用 厨师（循环引用！）

  // 函数执行完毕后，厨师 和 菜品 这两个局部变量会被回收
  // 但 厨师 和 菜品 互相引用，引用计数都是 1
  // 旧的引用计数算法无法回收它们 → 内存泄漏！
}

做菜();
// 现代浏览器的标记清除算法可以处理这种情况，不再有这个问题
~~~

## 22.3 标记清除（Mark and Sweep）

**一句话解释：**
现代 JS 引擎使用的主流垃圾回收策略——从**根对象**（全局对象、调用栈上的变量等）出发，沿着引用链**递归标记**所有能访问到的对象。标记完成后，**没有被标记的对象就是垃圾**，可以清除。

**餐厅比喻：**
清洁工从**仓库入口**（根对象）出发，沿着所有通道走一遍，**经过的地方都贴上"有用"标签**。走完之后，所有没贴标签的东西——不管放在哪——统统清走。

~~~
标记清除的过程：

第1步：标记阶段（从根出发，标记所有可达对象）

  根对象（全局/调用栈）
    ├──→ 菜品A ✅ 标记
    │      └──→ 配料X ✅ 标记
    ├──→ 菜品B ✅ 标记
    │
    │     菜品C（没有任何引用指向它）❌ 不标记
    │      └──→ 配料Y（虽然被菜品C引用，但菜品C不可达）❌ 不标记

第2步：清除阶段（清除所有未标记的对象）

  清除：菜品C、配料Y
  保留：菜品A、配料X、菜品B
~~~

~~~javascript
// ========== 标记清除能处理循环引用 ==========
function 做菜() {
  let 厨师 = { 名字: "张师傅" };
  let 菜品 = { 名字: "红烧肉" };

  厨师.正在做 = 菜品;
  菜品.负责厨师 = 厨师;  // 循环引用

  return "做好了";
}

做菜();
// 函数执行完毕后：
// 厨师 和 菜品 不再被任何根对象可达
// 虽然它们互相引用，但标记清除从根出发找不到它们
// → 两个都会被回收 ✅（不会内存泄漏）
~~~

### 引用计数 vs 标记清除

| | 引用计数 | 标记清除 |
|---|---|---|
| 原理 | 引用次数为 0 就回收 | 从根出发，不可达就回收 |
| 循环引用 | ❌ 无法处理（会泄漏） | ✅ 可以处理 |
| 实时性 | 每次引用变化时立即判断 | 定期批量处理 |
| 目前状态 | 已淘汰（旧版 IE） | 主流方案（所有现代浏览器） |
| 餐厅比喻 | 数人头，没人用了就扔 | 从入口走一遍，没走到的就清走 |

## 22.4 V8 引擎的垃圾回收策略

**一句话解释：**
V8（Chrome 和 Node.js 使用的 JS 引擎）采用**分代收集**策略——把内存分成**新生代**（短命对象）和**老生代**（长命对象），用不同的算法分别管理。

**餐厅比喻：**
厨房把台面分成两个区域：
- **临时区（新生代）**：放刚拿出来的食材，用完很快就扔。空间小，但清理频率高，速度快
- **常驻区（老生代）**：放经常用的调料、工具。空间大，清理频率低，但清理时更仔细

~~~
V8 内存分代：

┌───────────────────────────────────────────┐
│                  堆内存（Heap）             │
│                                           │
│  ┌─────────────────────────────────────┐  │
│  │         新生代（Young Generation）    │  │
│  │         空间小（1-8MB）              │  │
│  │         短命对象（临时变量、闭包等）  │  │
│  │                                     │  │
│  │  ┌──────────┐    ┌──────────┐       │  │
│  │  │  From 空间 │    │  To 空间  │       │  │
│  │  │  （使用中）│    │  （空闲）  │       │  │
│  │  └──────────┘    └──────────┘       │  │
│  └─────────────────────────────────────┘  │
│                                           │
│  ┌─────────────────────────────────────┐  │
│  │         老生代（Old Generation）      │  │
│  │         空间大（几百MB）              │  │
│  │         长命对象（全局变量、缓存等）  │  │
│  └─────────────────────────────────────┘  │
└───────────────────────────────────────────┘
~~~

### 新生代：Scavenge 算法

~~~javascript
// ========== 新生代：对象存活时间短，频繁回收 ==========

// Scavenge 算法（复制算法）：
// 1. 新生代分成 From 空间和 To 空间（各一半）
// 2. 新对象先进入 From 空间
// 3. From 空间快满时，触发 GC
// 4. 把 From 中还活着的对象复制到 To 空间
// 5. 清空 From 空间
// 6. From 和 To 互换角色

// 对象如果在新生代中存活了足够多次（2次 GC），就会被"晋升"到老生代
function 做菜() {
  const 临时配料 = ["葱", "姜", "蒜"];  // 新生代：临时变量，函数结束就该回收
  return 临时配料.join("、");
}
做菜();  // 临时配料 变为垃圾，新生代 GC 回收
~~~

### 老生代：标记清除 + 标记整理

~~~javascript
// ========== 老生代：对象存活时间长，不频繁回收 ==========

// 标记清除（Mark-Sweep）：
// 标记所有可达对象，清除不可达对象
// 问题：会产生内存碎片（清除后留下的空洞）

// 标记整理（Mark-Compact）：
// 在标记清除的基础上，把存活的对象向一端移动
// 消除内存碎片，但移动对象有额外开销

// 全局变量、缓存等长命对象都在老生代
const 菜品缓存 = new Map();  // 老生代：一直存在
const 全局配置 = { 主题: "深色" };  // 老生代

// 老生代 GC 时会"停顿"（Stop-The-World）
// 因为标记和整理需要时间，这段时间 JS 代码会暂停
// V8 用"增量标记"和"并发标记"来减少停顿时间
~~~

### 新生代晋升到老生代

~~~javascript
// ========== 对象从新生代"晋升"到老生代的条件 ==========

// 条件1：对象已经经历过一次 GC，仍然存活
function 创建对象() {
  let 临时对象 = { 数据: "..." };
  // 第一次 GC 后，临时对象仍然存活 → 晋升到老生代
  return 临时对象;
}
const 长命对象 = 创建对象();  // 长命对象 活了下来，晋升

// 杂件2：To 空间已经超过 25% 使用率
// 如果复制到 To 空间时，To 空间已经用了超过 25%
// 那么当前对象直接晋升到老生代（避免 To 空间溢出）
~~~

## 22.5 内存泄漏的常见原因

**一句话解释：**
内存泄漏是指**不再需要的数据仍然被引用**，垃圾回收器无法回收它，导致内存持续增长。

**餐厅比喻：**
台面上有些食材明明不用了，但因为有人**不小心把标签贴错了**（错误的引用），清洁工以为还有人在用，就不敢扔。时间一长，台面越来越满。

### 原因1：闭包持有不再需要的引用

~~~javascript
// ========== 闭包导致内存泄漏 ==========
function 创建处理器() {
  const 大数据 = new Array(1000000).fill("数据");  // 占用大量内存

  return function 处理() {
    // 这个闭包引用了大数据，大数据无法被垃圾回收
    console.log(大数组.length);
  };
}

const 处理器 = 创建处理器();  // 大数据 被闭包引用，一直在内存中

// 解决：不再需要时解除引用
// 处理器 = null;  // 闭包被回收，大数据也可以被回收了

// ========== 更好的做法：只引用需要的部分 ==========
function 创建处理器2() {
  const 大数据 = new Array(1000000).fill("数据");
  const 长度 = 大数据.length;  // 只提取需要的值

  return function 处理() {
    console.log(长度);  // 不引用整个大数据，只引用长度这个数字
  };
  // 大数据 可以被回收了
}
~~~

### 原因2：全局变量

~~~javascript
// ========== 意外创建的全局变量 ==========
function 做菜() {
  菜名 = "红烧肉";  // 忘了写 let/const/var → 变成全局变量！
  // 全局变量永远不会被垃圾回收，直到页面关闭
}
做菜();

// 解决：始终用 let/const 声明变量
// "use strict" 模式下，未声明的变量会报错

// ========== 全局缓存不断增长 ==========
const 缓存 = {};

function 缓存数据(键, 值) {
  缓存[键] = 值;  // 只增不减，缓存无限增长
}

// 解决：设置缓存上限或用 WeakMap
~~~

### 原因3：定时器未清除

~~~javascript
// ========== setInterval 未清除 ==========
function 开始监控() {
  setInterval(() => {
    // 这个回调被 setInterval 引用，永远不会被回收
    // 如果回调内部引用了大量数据，就造成内存泄漏
    const 大数据 = new Array(10000).fill("...");
    console.log(大数据.length);
  }, 1000);
}
// 开始监控();  // 即使不需要了，定时器还在跑

// 解决：保存定时器 ID，不需要时清除
let 定时器ID;

function 开始监控2() {
  定时器ID = setInterval(() => {
    console.log("监控中...");
  }, 1000);
}

function 停止监控() {
  clearInterval(定时器ID);  // 清除定时器，回调可以被回收
}

// ========== setTimeout 也可能泄漏 ==========
function 延迟处理() {
  const 大数据 = new Array(1000000).fill("...");
  setTimeout(() => {
    console.log(大数据.length);  // 闭包引用大数据
  }, 60000);  // 60秒内大数据无法被回收
}
~~~

### 原因4：DOM 引用未清理

~~~javascript
// ========== DOM 引用导致内存泄漏 ==========
const 缓存 = {};

function 缓存元素() {
  const 元素 = document.getElementById("大列表");
  缓存.列表 = 元素;  // JS 对象引用了 DOM 元素
}

// 后来 DOM 元素从页面上移除了
// document.body.removeChild(缓存.列表);
// 但 缓存.列表 还引用着那个 DOM 元素
// → DOM 元素无法被垃圾回收！

// 解决：移除 DOM 元素后，也清除 JS 中的引用
// 缓存.列表 = null;
~~~

### 原因5：事件监听器未移除

~~~javascript
// ========== 事件监听器导致内存泄漏 ==========
function 初始化() {
  const 按钮 = document.getElementById("按钮");
  const 大数据 = new Array(1000000).fill("...");

  按钮.addEventListener("click", function() {
    console.log(大数据.length);  // 闭包引用大数据
  });
  // 即使按钮从 DOM 移除了，事件监听器可能仍然持有引用
}

// 解决1：用 AbortController 移除
function 初始化2() {
  const 控制器 = new AbortController();
  const 按钮 = document.getElementById("按钮");

  按钮.addEventListener("click", function() {
    console.log("点击了");
  }, { signal: 控制器.signal });

  // 需要时一次性移除所有监听器
  // 控制器.abort();
}

// 解决2：手动 removeEventListener
function 初始化3() {
  const 按钮 = document.getElementById("按钮");

  function 处理点击() {
    console.log("点击了");
    按钮.removeEventListener("click", 处理点击);  // 触发后移除
  }

  按钮.addEventListener("click", 处理点击);
}
~~~

## 22.6 WeakRef / FinalizationRegistry

**一句话解释：**
- `WeakRef`：创建对象的**弱引用**——不会阻止垃圾回收器回收该对象
- `FinalizationRegistry`：在对象被垃圾回收后，**执行清理回调**

**餐厅比喻：**
- `WeakRef` 就像用**铅笔**在便签上记了食材位置——轻轻一擦就没了，不影响清洁工清理
- `FinalizationRegistry` 就像在食材上贴了一个**通知条**——"如果这份食材被扔了，请通知采购部补货"

~~~javascript
// ========== WeakRef：弱引用 ==========
let 原始对象 = { 名字: "红烧肉", 价格: 38 };

// 创建弱引用
const 弱引用 = new WeakRef(原始对象);

// 通过弱引用访问对象
console.log(弱引用.deref());  // { 名字: "红烧肉", 价格: 38 }

// 解除原始引用
原始对象 = null;

// 弱引用不会阻止垃圾回收
// 但 GC 的时机不确定，所以 deref() 可能返回 undefined
// 在实际代码中可能需要等待一段时间
console.log(弱引用.deref());  // undefined 或 对象（取决于 GC 是否已执行）

// ========== WeakRef 实现缓存 ==========
class 弱缓存 {
  constructor() {
    this.缓存 = new Map();
  }

  set(键, 值) {
    this.缓存.set(键, new WeakRef(值));
  }

  get(键) {
    const 弱引用 = this.缓存.get(键);
    if (!弱引用) return undefined;

    const 值 = 弱引用.deref();
    if (值 === undefined) {
      // 对象已被回收，清理缓存条目
      this.缓存.delete(键);
      return undefined;
    }

    return 值;
  }
}

const 缓存 = new 弱缓存();

let 菜品 = { 名字: "红烧肉" };
缓存.set("今日特选", 菜品);

console.log(缓存.get("今日特选"));  // { 名字: "红烧肉" }

菜品 = null;  // 解除引用后，对象可能被 GC 回收
// 缓存.get("今日特选") 可能返回 undefined
~~~

~~~javascript
// ========== FinalizationRegistry：对象被回收后的清理回调 ==========
const 注册表 = new FinalizationRegistry((持有的值) => {
  console.log(`对象被回收了，持有的值：${持有的值}`);
});

let 菜品 = { 名字: "红烧肉" };

// 注册：当 菜品 被回收时，执行回调，传入 "红烧肉已下架"
注册表.register(菜品, "红烧肉已下架");

菜品 = null;  // 解除引用
// 未来某个时刻 GC 回收后，会执行：
// "对象被回收了，持有的值：红烧肉已下架"

// ========== 实际用途：自动清理关联资源 ==========
const 资源清理 = new FinalizationRegistry((资源ID) => {
  console.log(`自动释放资源：${资源ID}`);
  // 这里可以发请求通知服务器释放资源
  // fetch(`/api/release/${资源ID}`);
});

function 打开数据库连接(连接名) {
  const 连接 = { 名字: 连接名, 状态: "已连接" };
  资源清理.register(连接, 连接名);  // 注册清理回调
  return 连接;
}

let 连接 = 打开数据库连接("订单数据库");
// ... 使用连接 ...
连接 = null;  // 连接被回收时，自动触发资源清理
~~~

## 22.7 如何避免内存泄漏的最佳实践

~~~javascript
// ========== 1. 始终用 let/const 声明变量 ==========
// ❌ 菜名 = "红烧肉";           // 全局变量，永远不会回收
// ✅ const 菜名 = "红烧肉";     // 作用域内，离开作用域可回收

// ========== 2. 及时清除定时器 ==========
let 定时器 = setInterval(() => { }, 1000);
clearInterval(定时器);  // 不需要时清除
定时器 = null;

// ========== 3. 及时移除事件监听器 ==========
const 控制器 = new AbortController();
document.addEventListener("click", () => { }, { signal: 控制器.signal });
控制器.abort();  // 不需要时移除

// ========== 4. 避免不必要的闭包引用 ==========
function 创建处理器(大数据) {
  const 长度 = 大数据.length;  // 只取需要的值
  return () => console.log(长度);  // 不引用整个大数据
}

// ========== 5. 使用 WeakMap/WeakSet 替代 Map/Set ==========
// 当键/值是对象且可能被回收时，用弱引用版本
const 弱映射 = new WeakMap();  // 键是弱引用
~~~

## 第22章 总结

| 术语 | 一句话解释 | 餐厅比喻关键词 |
|---|---|---|
| 垃圾回收 | JS 引擎自动找出不再使用的数据并释放内存 | 自动打扫卫生的清洁工 |
| 内存生命周期 | 分配 → 使用 → 释放 | 拿食材 → 做菜 → 清理台面 |
| 引用计数 | 引用次数为 0 就回收（已淘汰） | 数人头，没人用了就扔 |
| 循环引用 | 两个对象互相引用，引用计数永远不为 0 | 两份食材互相粘着，扔不掉 |
| 标记清除 | 从根出发，不可达就回收（主流方案） | 从入口走一遍，没走到的就清走 |
| 标记整理 | 标记清除 + 移动对象消除碎片 | 清理后台面整齐排列 |
| 分代收集 | 内存分新生代和老生代，不同策略管理 | 临时区和常驻区分开管理 |
| 新生代 | 短命对象，空间小，频繁回收（Scavenge） | 临时区：用完很快扔 |
| 老生代 | 长命对象，空间大，不频繁回收 | 常驻区：常用的东西放这里 |
| 晋升 | 新生代存活够多次后移到老生代 | 临时区的东西用久了搬到常驻区 |
| 内存泄漏 | 不再需要的数据仍被引用，无法回收 | 标签贴错了，清洁工不敢扔 |
| 闭包泄漏 | 闭包持有不再需要的大数据 | 便签纸粘着一大袋食材扔不掉 |
| 全局变量泄漏 | 未声明变量或全局缓存只增不减 | 东西堆在公共区域没人清 |
| 定时器泄漏 | setInterval 未清除 | 闹钟一直在响没人关 |
| DOM 引用泄漏 | DOM 移除了但 JS 还引用着 | 菜撤走了但账本上还记着 |
| 事件监听泄漏 | 监听器未移除，闭包引用数据 | 门铃一直挂着，连着一堆电线 |
| WeakRef | 创建弱引用，不阻止 GC | 铅笔写的便签，一擦就没了 |
| FinalizationRegistry | 对象被回收后执行清理回调 | 食材被扔了通知补货 |
| WeakMap/WeakSet | 弱引用版本的 Map/Set | 磁铁吸的便利贴，冰箱搬走自动掉 |
| 最佳实践 | let/const、清定时器、移监听器、弱引用 | 保持台面整洁的好习惯 |
