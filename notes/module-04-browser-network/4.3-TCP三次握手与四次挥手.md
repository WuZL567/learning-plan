# 4.3 TCP三次握手与四次挥手

## 一句话说清楚

（用一句白话解释三次握手和四次挥手分别是干什么的，解决什么问题。参考：打电话确认双方都能听到、挂电话确认对方把话说完。）

三次握手：是为了建立服务端和客户端之间的TCP连接；
四次挥手：是为了断开服务端和客户端之间的TCP连接；

## 三个要点

### 要点一：三次握手的过程与为什么是三次

画出（或文字描述）三次握手的完整流程：每一方的报文叫什么（SYN/ACK）、seq 是怎么变化的。然后回答：**为什么两次不够？为什么三次正好？**

提示：第二次回复后，谁还不确定什么？想想"服务端是否知道客户端能收到自己发的消息"。

第一次握手：客户端 -> SYN seq=x -> 服务端；
第二次握手：客户端 <- SYN+ACK seq=y <- 服务端；
第三次握手：客户端 -> ACK seq=x+1 -> 服务端；

两次握手，服务端不知道客户端是否接受到了自己的消息；三次刚好是因为客户端返回了信息给服务端确保连接真正建立；

### 要点二：四次挥手的过程与为什么是四次

画出（或文字描述）四次挥手的完整流程：谁先发 FIN、中间的 ACK 是谁回的、为什么挥手要四步而不是三步。

提示：被动方收到 FIN 时，如果它还有数据没发完，会先做什么再做什么？"我说完了"和"我也说完了"为什么不能合成一句话？

第一次挥手：主动关闭方 -> FIN -> 被动关闭方；
第二次挥手：主动关闭方 <- ACK <- 被动关闭方；
第三次挥手：主动关闭方 <- FIN <- 被动关闭方；
第四次挥手：主动关闭方 -> ACK -> 被动关闭方；
等待2MSL之后关闭连接；

要四步的原因是因为第二次挥手时并不一定是发送数据完毕了，需要先回复主动关闭方，不要断开，第二次和第三次挥手之间，就是在传输最后的数据，传输完毕后，再进行第三次挥手，告诉主动关闭方，我也处理完了；

### 要点三：TIME_WAIT 状态

用你的话说清楚：挥手结束后谁进入了 TIME_WAIT？要等多久（2MSL 是什么）？为什么要等？

主动关闭方进入TIME_WAIT，等待2MSL时间，2MSL是2 倍报文最大生存时间，约 2×30秒=1 分钟，因为避免丢失ACK；

提示：从两个角度想——（1）如果最后一个 ACK 丢了怎么办？（2）如果旧连接的报文还残留在网络里，会对新连接造成什么影响？

丢了最后一个ACK，对方重发FIN后，还能继续发送一次；
会混进新的连接中；

## 不确定的点

（诚实写出没完全搞懂的部分。比如：TIME_WAIT 和 CLOSE_WAIT 的区别、为什么要 2MSL 而不是 1MSL、HTTP/1.1 keep-alive 跟握手有什么关系、HTTPS 的 TLS 握手和 TCP 握手是什么关系。写不出来就写"没有不确定的点"，但要想清楚再写。）
1、TIME_WAIT是主动关闭方的状态，在第四次挥手之后，会有一个状态；CLOSE_WAIT是被动关闭方的状态，在第一次挥手之后，就进入到了CLOSE_WAIT的状态；
2、一个完整的"丢包→重发→补救"往返需要 2MSL，最后的 ACK 丢了，对方重发 FIN——这个 FIN 要最多 1 个 MSL 才能到你，你回的补救 ACK 又要最多 1 个 MSL 才能到对方；等够 2MSL，意味着无论最后一个 ACK 是否丢失，这个连接上的所有报文（包括双方方向的残留在途报文）都已在网络里过期消失，不会污染新连接
3、keep-alive是避免重复建立TCP连接；
4、不确定；
