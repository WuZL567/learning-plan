# 对话记录：4.8 HTTP/3 核心特性

日期：2026-09-01

---

## 教学过程

### 为什么需要它

HTTP/2 解决了 HTTP/1.1 的队头阻塞，但引入了新问题：**TCP 层的队头阻塞**。

打个比方：HTTP/2 像一条高速公路有多个车道（多路复用），但如果路上出了车祸（一个 TCP 包丢了），所有车道都得堵着等——因为 TCP 必须保证顺序交付。

HTTP/3 换了个思路：**把底层从 TCP 换成 UDP + QUIC**，彻底解决这个问题。

### 一句话说清楚

HTTP/3 = HTTP/2 的应用层 + QUIC 传输层（基于 UDP），核心是**每个流独立重传**，一个包丢了只堵那一个流，其他流不受影响。

### 核心改动

| 对比项 | HTTP/2 | HTTP/3 |
|--------|--------|--------|
| 传输层 | TCP | QUIC（基于 UDP） |
| 队头阻塞 | TCP 层仍存在 | 彻底消除（流独立重传） |
| 握手耗时 | TCP(1RTT) + TLS(1-2RTT) = 2-3RTT | QUIC 内置 TLS 1.3，首次 1RTT，后续 0RTT |
| 连接迁移 | 不支持（IP 变了断连） | 支持（Connection ID 追踪，WiFi 切 4G 不断） |

3. 场景应用：用户在地铁里刷手机，WiFi 和 4G 频繁切换，HTTP/2 和 HTTP/3 分别会怎样？

**第三层：场景应用** ❌
> 追问：用户在地铁里刷手机，WiFi 和 4G 频繁切换，HTTP/2 和 HTTP/3 分别会怎样？

学生回答：未回答

正确答案：
- HTTP/2：TCP 连接基于 IP+端口，IP 变了连接断了，得重新握手（2-3RTT），用户感知到页面卡一下
- HTTP/3：QUIC 用 Connection ID 追踪连接，IP 变了 Connection ID 不变，连接无缝迁移，用户无感知

### 导师补充修正

学生请求导师直接修改文档，导师补充了以下内容：

**要点2 补充**：UDP 本身不可靠（不保证顺序、不保证送达），QUIC 在 UDP 之上自己实现了可靠性：序号、确认、重传、流控，相当于把 TCP 的活自己干了，但做到了"每条流独立"。

**要点3 补充**：QUIC 内置 TLS 1.3，握手和加密合并为一步。首次连接 1RTT：QUIC 握手时同时完成密钥交换，只需一个往返就能建立连接。后续连接 0RTT：客户端缓存了上次的密钥，下次连接时直接带上加密数据发出去，不用等服务端确认。

2. Connection ID 具体是什么格式？服务端怎么通过它识别同一个连接？
3. 0RTT 有什么安全风险？（重放攻击？）

### 不确定点解答

1. **QUIC 在 UDP 上怎么保证可靠性**：简单说就是"自己干 TCP 的活"——每个包有序号，接收方要确认（ACK），丢了就重传。但关键是每条流独立做这些事，不像 TCP 那样所有数据混在一起排队。

2. **Connection ID 格式**：通常是一串随机生成的字节（8-18字节），不绑定 IP 和端口。服务端通过它识别"这是同一个客户端"，即使 IP 变了。

3. **0RTT 的安全风险**：确实有重放攻击风险。攻击者可以截获 0RTT 数据包重发。所以 0RTT 一般只用于幂等请求（GET），不用于非幂等请求（POST/扣款）。
