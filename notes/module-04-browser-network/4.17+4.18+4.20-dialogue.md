### 技术点一：4.17 JSONP 跨域方案原理与限制

**为什么需要它：**  
前面学了 CORS，但实际开发中还有其他跨域方案。JSONP 是古老但面试必问的方案。

**一句话说清楚：**  
利用 `<script>` 标签不受同源策略限制的特性，让服务器返回一段可执行的 JavaScript 代码来传递数据。

**核心原理：**  
就像你在 HTML 里写 `<script src="https://cdn.com/jquery.js"></script>` 不会跨域一样，JSONP 动态创建 `<script>` 标签，src 指向后端接口，后端返回的不是 JSON 数据，而是一段 JS 代码：`callback({"name": "张三"})`。前端提前定义好 `callback` 函数，代码一执行就能拿到数据。

**完整执行流程：**
1. 前端动态创建 `<script>` 标签，src 为 `http://api.example.com/users?callback=handleData`
2. 通过 URL 参数传递回调函数名 `handleData`
3. 后端返回可执行代码：`handleData({"name": "张三", "age": 25})`
4. 浏览器加载 script 后自动执行，调用前端预先定义好的 `handleData` 函数

**致命限制：**
1. **只能 GET 请求**：`<script>` 标签加载资源只能用 GET
2. **安全风险高**：后端返回的是可执行代码，如果后端被劫持会直接执行恶意代码（XSS）
3. **错误处理困难**：`<script>` 加载失败只能拿到简单的 error 事件

所以现在基本不用了，但面试会问。

### 技术点二：4.18 代理跨域方案

**为什么需要它：**  
代理是开发环境天天用的跨域方案。

**一句话说清楚：**  
浏览器有同源策略，但服务器之间通信没有跨域限制。前端请求同源的代理服务器，代理服务器转发请求到目标服务器。

**核心原理：**
```
浏览器（localhost:5173）→ Vite Dev Server（同源代理）→ 后端 API（api.example.com）
```
前端以为自己在请求 `http://localhost:5173/api/users`，实际上 Vite 偷偷帮你转发到了 `http://api.example.com/v1/users`。

**两种场景：**
- **开发环境用 Vite proxy**：在 `vite.config.ts` 配置，只在本地开发时生效
- **生产环境用 Nginx**：在 `nginx.conf` 配置 `proxy_pass`，生产环境的反向代理服务器

**Vite proxy 配置示例：**
```typescript
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://api.example.com',
        changeOrigin: true,  // 修改 Origin 头
        rewrite: (path) => path.replace(/^\/api/, '/v1')
      }
    }
  }
})
```

**Nginx 配置示例：**
```nginx
location /api/ {
    proxy_pass http://api.example.com/v1/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

### 技术点三：4.20 SSE（Server-Sent Events）

**为什么需要它：**  
SSE 是 AI 应用的核心技术，你做 AI 问答 demo 时必然会用到流式输出。

**一句话说清楚：**  
基于 HTTP 的服务器单向推送技术，服务器保持长连接持续推送数据，浏览器通过 `EventSource` API 接收。

**核心原理：**
- 客户端发起一个 GET 请求，服务器返回 `Content-Type: text/event-stream`
- 连接保持打开，服务器有数据就推送，格式是 `data: xxx\n\n`
- 浏览器自动处理重连，断线后会自动发起新请求

**对比 WebSocket：**

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 通信方向 | 单向（服务器→客户端） | 双向 |
| 协议 | HTTP | 独立协议（ws://） |
| 自动重连 | 浏览器内置 | 需手动实现 |
| 适用场景 | AI 流式输出、实时通知、股票行情 | 聊天室、协同编辑、游戏 |

**AI 应用为什么用 SSE：**  
DeepSeek/ChatGPT 流式输出时，只需要服务器推送给前端，不需要前端频繁发消息。SSE 更简单，浏览器原生支持，自动重连省心。

### 第二层追问：对比理解

**问题 4：JSONP 和 CORS 都能解决跨域，有什么区别？为什么现在基本不用 JSONP 了？**

学生回答：
> 区别在于 JSONP 是利用了浏览器的漏洞，而CORS是服务器和浏览器的标准协议；JSONP只能发送GET请求，无法处理其他的请求，但是CORS没有这样的限制；JSONP因为返回的是JS代码，所以更容易造成XSS攻击；JSONP的错误处理困难，没有详细的错误信息，无法区分是网络错误还是服务器错误；因为它缺点都多，相比之下，CORS是更好的跨域解决方案。

✅ **评判：正确**  
讲清楚了 4 个核心差异（GET 限制、XSS 风险、错误处理、标准协议），对比全面。

**问题 6：SSE 和 WebSocket 有什么区别？AI 流式输出为什么用 SSE 不用 WebSocket？**

学生回答：
> SSE是服务器单向的推送消息，webSocket是双向的；SSE是基于HTTP协议的，WebSocket有自己的协议ws://；SSE支持无限自动重连，WebSocket需要手动实现；SSE的消息格式是纯文本，WebSocket支持二进制和纯文本；AI流式输出只需要服务器主动推送消息给前端，不需要前端频繁的发送消息；支持自动重连，复用HTTP协议。

✅ **评判：正确**  
对比清晰，讲清楚了通信方向、协议、重连、消息格式四个维度的差异，并说明了 AI 场景选 SSE 的原因。

**问题 9：场景选择**

三个场景分别该用哪种跨域方案？

- **场景 A**：本地开发，前端 `localhost:5173`，后端 `localhost:3000`，后端可以随便改代码。
- **场景 B**：请求第三方 API（如高德地图），对方不支持 CORS，只支持 JSONP，且只需要 GET 请求。
- **场景 C**：生产环境部署，前端和后端不同域名，后端支持 CORS。

学生回答：
> 场景A：Vite proxy；场景B：JSONP；场景C：Nginx 代理

❌ **评判：场景 C 答错**

**扣分原因：**  
题目说"后端支持 CORS"，那前端直接跨域请求就行，不需要代理。Nginx 代理适用于"后端不支持 CORS 且无法修改"的场景。

**正确答案：**
- 场景 A：Vite proxy（开发环境本地代理）✅
- 场景 B：JSONP（第三方 API 只支持 JSONP）✅
- 场景 C：**直接用 CORS**（后端已支持，前端直接跨域请求即可）❌

**关键理解：**  
能用 CORS 就用 CORS，代理是后端不支持 CORS 时的备选方案。
