## 一、教学过程

### 为什么需要它

你点开一个网页，浏览器发的 HTTP 请求是"寄一封信"，但信不是凭空飞的——底层得先有一条可靠的传输管道，这就是 TCP 连接。面试问"浏览器输入 URL 发生了什么"，讲到 HTTP 请求之前一定会卡在"先建立 TCP 连接"，这一关过不去，后面的渲染流程都白讲。另外你天天看到 network 面板里的 `Connection: keep-alive`，它就是为了**省掉反复握手**——你不懂握手，就理解不了这个优化。

### 一句话说清楚

三次握手是"建连接前先互相确认对方能收能发"的两次半对话，四次挥手是"断开前互相确认对方把话说完"的两段告别，TIME_WAIT 是主动说再见那一方在门口多站一会儿，防止"最后一句话没送到"。

### 核心原理

**三次握手（连接建立）**——拿打电话做类比：

```
客户端                    服务端
  |---- SYN, seq=x -------->|   "喂，我想说话，你能听到吗？"
  |<--- SYN+ACK, seq=y -----|   "能听到！我也想说，你能听到我吗？"
  |---- ACK, seq=x+1 ------>|   "能听到！开始说吧"
  |        (连接建立)        |
```

- **为什么不是两次**：第二次回复后，客户端知道了"我发的你能收到、你发的我能收到"，但**服务端**还不知道"我发的客户端能不能收到"。少了最后一次 ACK，服务端不敢确定信道双向可用——就好比你说"喂"，对方说"在呢"，但你没回话，对方不确定你到底听没听见。
- 顺带一提：你发 HTTP 请求前每次都要走这个流程，`keep-alive` 就是复用已建立的连接，不再反复握手。

**四次挥手（连接断开）**——"挂电话"要分两步，因为两边都可能还有话没说完：

```
主动关闭方                   被动关闭方
  |---- FIN ---------------->|   "我说完了，我要挂了"
  |<--- ACK -----------------|   "收到，我这边还有话，等我说完"
  |<--- FIN -----------------|   "我也说完了，我也挂了"
  |---- ACK ---------------->|   "收到，再见"
  |   (等待 2MSL 后关闭)      |
```

- **为什么是四次而不是三次**：被动方收到 FIN 后不一定马上说完，得先回个 ACK 稳住对方，等自己把剩余数据发完再发 FIN。两次"告别"之间隔着一段传输数据的时间，所以拆成了四步。

**TIME_WAIT（最常被追问的点）**：先发 FIN 的一方（主动关闭方）收到对方的 FIN 并回完最后的 ACK 后，不会立刻关闭，而是等 **2MSL**（2 倍报文最大生存时间，约 2×30秒=1 分钟）。两个原因：
1. 怕最后一个 ACK 丢了，等对方重发 FIN 时还能再回一次；
2. 让这条连接上残留的"幽灵报文"在网络里过期消失，避免它混进后面对同一端口的新连接。

## 二、验收过程

### 学生首次提交的笔记核心内容

- 一句话说清楚：三次握手是为了建立服务端和客户端之间的 TCP 连接；四次挥手是为了断开连接（功能描述，未答到"确认"本质）
- 三次握手流程：SYN seq=x → SYN+ACK seq=y → ACK seq=x+1 ✅；为什么两次不够：服务端不知道客户端是否收到自己的消息 ✅
- 四次挥手流程：FIN → ACK → FIN → ACK ✅；为什么四次：第二次挥手时被动方不一定发完数据，需先回复不要断开，第三次挥手返回剩余数据（表述有偏差：数据在二三次之间传，第三次发的是 FIN）
- TIME_WAIT：主动关闭方进入，等 2MSL（2 倍报文最大生存时间约 1 分钟），避免丢失 ACK；丢 ACK 后对方重发 FIN 还能再回；幽灵报文混进新连接 ✅
- 不确定的点：4 个占位符"不知道"（未认真填写）

### 初步反馈

指出两个问题：
1. 严重：「不确定的点」只填了占位符，模板里给的四个方向（CLOSE_WAIT、2MSL、keep-alive、TLS）一个没碰

### 三层追问完整记录

#### 第一层追问（白话复述）

导师：「假设三次握手只有两次——客户端发 SYN，服务端回 SYN+ACK，然后直接认为连接建立、开始发数据。具体会发生什么实际的坏事？提示：想象网络里有一个'迟到很久'的旧 SYN 包，恰好在你这次请求时送到服务端。用你的话讲，服务端会怎么被骗，后果是什么？」

学生：「假设有一个很旧的SYN包，在我这次建立连接时传给了服务端，这时候服务端建立的连接就不会是我，所以后续数据也不会准确的发送。」

评判：方向正确 ✅——服务端被骗，建立错误连接。导师补充完整：旧 SYN 到达 → 服务端回 SYN+ACK 并分配资源 → 客户端发现没发起过该连接，忽略或发 RST → 服务端白等，资源被占；更坏是历史数据包混进新连接。三次握手的作用是"防历史报文欺骗"：客户端只在主动发过 SYN 且收到匹配 SYN+ACK 后才确认连接成立，旧包对不上号被识破。第一层通过。

#### 第二层追问（对比理解）

导师：「四次挥手过程里其实有两个中间状态，一个是 TIME_WAIT，另一个是 CLOSE_WAIT。回答我：1. 谁进入 TIME_WAIT？谁进入 CLOSE_WAIT？（分别在挥手的哪一步进入）2. 假如你是后端运维，发现服务器上大量连接卡在 CLOSE_WAIT 状态不消失，这说明什么？问题出在谁身上？」

学生：「主动关闭方进入TIME_WAIT。在第四次挥手后进入；不知道谁会进入CLOSE_WAIT。」

评判：TIME_WAIT 部分答对 ✅（主动方，第四次挥手后）。CLOSE_WAIT 不知道。导师教学：CLOSE_WAIT 是被动关闭方的状态——被动方收到 FIN、回完 ACK 之后进入，等自己剩余数据发完；发完发 FIN 进入 LAST_ACK，收到最后 ACK 关闭。类比：TIME_WAIT = 主动说再见的人在门口等 1 分钟；CLOSE_WAIT = 被动方收到"对方说完了"但自己赖着不挂。大量 CLOSE_WAIT = 服务端收到 FIN 却一直没发 FIN，是应用层没关 socket（如 Node 没监听 close 事件、没调 socket.end()）的代码 bug 信号。第二层部分通过。

#### 第三层追问（场景应用）

导师：「你在浏览器里 F5 刷新一个页面，这个页面连着同一个域名的几十个请求。1. 第二次刷新时，这些请求还需要全部重新走一遍三次握手吗？浏览器是怎么省掉握手的？2. 如果这时候你改了后端代码、重启了 dev server，浏览器这边会发生什么？你平时调试时遇到过这种情况吗？」

学生：「1、不需要，keep-alive；2、刷新界面，数据重新请求，会建立新的TCP链接；没有遇到过」

评判：第一问答对 ✅（keep-alive），导师补充机制：服务端和浏览器通过 `Connection: keep-alive` 约定连接不关，后续请求复用管道。第二问答对一半：会建立新连接 ✅，但漏掉"连接被重置"（RST）现象——dev server 重启瞬间，浏览器拿旧连接发请求，服务端已关闭，请求报错/白屏，刷新即恢复。学生说"没遇到过"，实际上每次改代码重启 dev server 都发生，只是没意识到那一刻发生了什么。第三层部分通过。

### 修改后重新提交的笔记内容

- 第三次挥手表述修正 ✅：「第二次和第三次挥手之间，就是在传输最后的数据，传输完毕后，再进行第三次挥手，告诉主动关闭方，我也处理完了」
- CLOSE_WAIT 补入 ✅：TIME_WAIT 主动方第四次挥手后；CLOSE_WAIT 被动方，"在第一次挥手之后进入"（细节偏差：精确时机是收到 FIN、回完 ACK 之后，即第二次挥手发出后）
- 不确定的点 ✅：①TIME_WAIT vs CLOSE_WAIT 区别（已写出）②2MSL 是为了冗余设计吗？（真实疑问，导师解答：不是冗余。MSL 是报文最大生存时间，最坏情况最后 ACK 丢失 → 对方重发 FIN 需 1 个 MSL 到达 → 补救 ACK 又需 1 个 MSL 送达，一个完整"丢包→重发→补救"往返需要 2MSL。等够 2MSL 保证无论 ACK 是否丢失，双方方向的残留报文都已在网络过期）③keep-alive 是避免重复建立 TCP 连接（理解正确）④"不确定"留白
