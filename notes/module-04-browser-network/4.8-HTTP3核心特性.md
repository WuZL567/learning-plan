# 4.8-HTTP/3 核心特性

## 一句话说清楚

> 这里用一句白话解释 HTTP/3 是什么，重点说清楚它和 HTTP/2 的本质区别（提示：从传输层协议的角度）

HTTP/3是为了解决HTTP/2中TCP层队头阻塞以及网络切换导致连接中断的问题；
HTTP/3使用QUIC替代之前的TCP，是每一个流都独立传输和独立确认，不会因为其中一个出现问题就阻塞其他流；
HTTP/3支持连接迁移，使用连接ID，避免网络切换时连接中断；

## 三个核心要点

### 要点1：解决了什么问题

> 这里写 HTTP/3 要解决的核心问题是什么（提示：HTTP/2 虽然解决了应用层队头阻塞，但底层 TCP 还有什么问题？）
TCP层队头阻塞以及网络切换导致连接中断；
HTTP/2的TCP只有一条，会在TCP出现问题时阻塞所有的流；

### 要点2：用什么技术解决

> 这里写 HTTP/3 的核心技术方案（提示：QUIC 协议是什么？基于什么传输层协议？为什么能解决队头阻塞？）
HTTP/2：应用层 HTTP/2 + 传输层 TCP + TLS
HTTP/3：应用层 HTTP/3 + 传输层 QUIC（基于 UDP，内置 TLS 1.3）
核心差异：TCP 是单一字节流，一个包丢失全阻塞；QUIC 基于 UDP，多个独立流，丢包只影响单个流

### 要点3：带来了什么额外好处

> 这里写 HTTP/3 除了解决队头阻塞，还带来了哪些性能提升（提示：0-RTT 连接恢复、连接迁移分别是什么？）
网络切换时连接不会中断，因为使用的连接ID作为连接标识，连接会迁移；
0-RTT 连接恢复（第一次连接后保存会话票据，第二次直接用票据加密发送数据，不需要握手）

## 我的理解中不确定的部分

> 这里诚实写出你没完全搞懂的点，比如：
> - QUIC 基于 UDP，那丢包怎么办？
QUIC 自己实现了可靠传输机制，有确认应答（ACK）、超时重传、流量控制，和 TCP 类似，但是每个流独立重传，不会阻塞其他流
> - 0-RTT 连接恢复具体是怎么做到的？
第一次连接后，服务器给客户端一个"会话票据（Session Ticket）"，客户端下次连接直接用这个票据加密发送数据，不需要握手
> - 连接迁移的连接 ID 是怎么生成的？
服务器在连接建立时生成一个随机的连接 ID（类似 UUID），客户端和服务器都记住这个 ID。IP 变了，只要连接 ID 对得上，连接就能继续
> - HTTP/3 现在浏览器支持情况怎么样？
主流浏览器都支持了（Chrome、Edge、Firefox、Safari），但服务器端支持还不够普及（Nginx、Cloudflare 等大厂 CDN 都支持了）
