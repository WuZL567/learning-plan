# 4.18 代理跨域方案（Vite proxy / Nginx）

## 一句话说清楚
浏览器有同源策略限制跨域请求，但服务器之间通信没有跨域限制。通过让前端请求同源的代理服务器，再由代理服务器转发请求到目标服务器，绕过浏览器的同源策略。

## 核心要点一：为什么代理能解决跨域
**原理解析：**

浏览器的同源策略只限制**浏览器发起的跨域请求**，但服务器之间的 HTTP 请求不受同源策略限制。

**完整流程：**
```
浏览器（localhost:5173）
    ↓ 请求 /api/users（同源请求，不跨域）
Vite Dev Server / Nginx（代理服务器）
    ↓ 转发到后端（服务器间通信，无跨域限制）
后端 API（api.example.com/v1/users）
    ↓ 返回数据
代理服务器
    ↓ 转发回浏览器
浏览器收到数据
```

**类比理解：**  
就像你不能直接跟国外网站对话（跨域），但你可以让国内的朋友（代理服务器）帮你转达消息。浏览器只看到自己在和同源的代理服务器通信，看不到背后的跨域请求。

## 核心要点二：Vite proxy 和 Nginx 代理的配置与区别
**两种代理方案对比：**

| 维度 | Vite proxy | Nginx 代理 |
|------|-----------|-----------|
| 使用环境 | 开发环境 | 生产环境 |
| 配置位置 | vite.config.ts | nginx.conf |
| 生效时机 | npm run dev 时 | 部署后 |
| 核心作用 | 本地开发时解决跨域 | 生产环境反向代理 + 负载均衡 |

**Vite proxy 配置示例：**
```typescript
// vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://api.example.com',
        changeOrigin: true,  // 修改 Origin 头，让后端以为请求来自同源
        rewrite: (path) => path.replace(/^\/api/, '/v1')
      }
    }
  }
})
```

**为什么只在开发环境用 Vite proxy？**  
因为生产环境没有 Vite Dev Server。执行 `npm run build` 后，生成的是静态文件（HTML/CSS/JS），部署到服务器（如 Nginx）上，此时需要 Nginx 来做代理。

**Nginx 配置示例：**
```nginx
location /api/ {
    proxy_pass http://api.example.com/v1/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

Nginx 不仅能做代理，还能做负载均衡、静态资源托管、HTTPS 配置等，是生产环境的标准方案。

## 我的理解中不确定的部分
**已解答的疑问：**

1. **Vite proxy 的 `rewrite` 配置是什么意思？**  
   路径重写。前端请求 `/api/users`，代理转发时改成 `/v1/users`（去掉 `/api` 前缀）。这样前端不需要关心后端的真实路径结构。
   ```javascript
   rewrite: (path) => path.replace(/^\/api/, '/v1')
   // /api/users → /v1/users
   ```

2. **Nginx 的 `proxy_set_header` 要配置哪些头？**  
   - `Host`：保留原始请求的域名
   - `X-Real-IP`：传递客户端真实 IP（否则后端只能看到 Nginx 的 IP）
   - `X-Forwarded-For`：记录代理链路中的所有 IP
   - `X-Forwarded-Proto`：传递协议（http/https）

3. **代理会增加延迟吗？**  
   会有微小延迟（多一跳网络请求），但开发环境在本地可以忽略。生产环境 Nginx 通常和后端在同一内网，延迟很小（1-2ms）。

4. **CORS 和代理能同时用吗？什么时候该用哪个？**  
   技术上可以，但没必要。如果后端支持 CORS，直接用 CORS 最简单。代理方案适用于：后端不支持 CORS 且无法修改、或需要统一网关管理所有请求的场景。
