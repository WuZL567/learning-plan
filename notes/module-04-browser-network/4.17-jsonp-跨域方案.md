# 4.17 JSONP 跨域方案原理与限制

## 一句话说清楚
利用 `<script>` 标签不受同源策略限制的特性，动态创建标签请求后端接口，后端返回可执行的 JavaScript 代码来传递数据。

## 核心要点一：JSONP 的实现原理
**完整执行流程：**

1. **前端动态创建 `<script>` 标签**：
   ```javascript
   const script = document.createElement('script');
   script.src = 'http://api.example.com/users?callback=handleData';
   document.body.appendChild(script);
   ```

2. **通过 URL 参数传递回调函数名**：前端把回调函数名（如 `handleData`）通过 `callback` 参数告诉后端。

3. **后端返回可执行的 JavaScript 代码**：
   ```javascript
   // 后端返回的不是 JSON，而是可执行代码：
   handleData({"name": "张三", "age": 25})
   ```

4. **前端接收数据**：浏览器加载 script 后自动执行，调用前端预先定义好的 `handleData` 函数，数据作为参数传入。

**类比理解：**  
就像你在 HTML 里写 `<script src="https://cdn.com/jquery.js"></script>` 不会跨域一样，JSONP 利用这个漏洞，让服务器返回的不是静态 JS 文件，而是动态生成的函数调用代码。

## 核心要点二：JSONP 的致命限制
**三大限制：**

1. **只能发 GET 请求**：  
   `<script>` 标签加载资源只能用 GET 方法，无法发送 POST/PUT/DELETE。如果需要提交表单或上传文件，JSONP 无能为力。

2. **XSS 安全风险极高**：  
   后端返回的是可执行代码，如果后端被劫持或不可信，可以返回恶意代码直接在前端执行，比如：
   ```javascript
   // 恶意后端返回：
   document.cookie = '';  // 清空 Cookie
   window.location.href = 'http://evil.com';  // 跳转到钓鱼网站
   ```
   这就是为什么 JSONP 只能用于完全可信的后端。

3. **错误处理困难**：  
   `<script>` 标签加载失败只能触发 `onerror` 事件，没有详细的错误信息（如 HTTP 状态码），无法区分是网络错误还是服务器错误。

**对比 CORS：**  
CORS 是浏览器和服务器的标准协议，支持所有 HTTP 方法，有完善的错误处理，更安全。JSONP 是利用浏览器漏洞的 hack 方案，现在只在极少数古老系统中使用（如需要兼容 IE8/IE9 且后端不支持 CORS）。

## 我的理解中不确定的部分
**已解答的疑问：**

1. **为什么叫 JSONP（JSON with Padding）？**  
   Padding 是"填充"的意思，指的是在 JSON 数据外面"包裹"了一层函数调用代码。原本只是纯数据 `{"name": "张三"}`，现在变成了 `handleData({"name": "张三"})`，多了函数名包裹。

2. **后端返回的代码格式到底长什么样？**  
   ```javascript
   // 前端请求：http://api.example.com/users?callback=myCallback
   // 后端返回（纯文本，Content-Type: application/javascript）：
   myCallback({"name": "张三", "age": 25})
   ```
   注意：后端返回的是可执行的 JS 代码字符串，不是 JSON 对象。

3. **JSONP 和 CORS 能同时用吗？**  
   技术上可以，但没必要。如果后端支持 CORS，就直接用 CORS，不需要 JSONP。JSONP 只在后端不支持 CORS 且必须兼容古老浏览器时才考虑。

4. **现在还有哪些场景必须用 JSONP？**  
   几乎没有。唯一的场景是：需要兼容 IE8/IE9 + 后端无法改动不支持 CORS + 只需要 GET 请求。现代项目基本不用。
