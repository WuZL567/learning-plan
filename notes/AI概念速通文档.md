## 第一部分：结构化输出（11.2.15）

### 是什么

LLM 默认输出的是自然语言文本，但我们写代码时需要的是**结构化数据**（JSON、对象）。结构化输出就是让 LLM 按照你定义的格式（JSON Schema）输出数据，并且用工具（Pydantic）校验格式是否正确。

### 为什么需要它

如果你让 LLM 返回用户信息，它可能返回：
```
用户叫张三，年龄 25 岁，邮箱是 zhangsan@example.com
```

但你的代码需要的是：
```json
{"name": "张三", "age": 25, "email": "zhangsan@example.com"}
```

不用结构化输出，你得自己写正则或字符串解析，LLM 输出格式稍微变一下你的代码就炸了。

### 怎么做

**OpenAI 方式**：用 `response_format` 参数强制 JSON 输出
```python
response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "提取用户信息：张三，25岁"}],
    response_format={"type": "json_object"}  # 强制 JSON
)
```

**Pydantic 校验方式**（更严格）：
```python
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int
    email: str

# LLM 返回后用 Pydantic 解析和校验
user_data = User.parse_raw(response.choices[0].message.content)
# 如果格式不对会抛异常，你可以 catch 后让 LLM 重新生成
```

### 和 Prompt 里说"请返回 JSON"的区别

- **Prompt 里说**：LLM 不一定听你的，可能返回 `这是 JSON：{"name": "张三"}`（多了前缀）
- **结构化输出**：API 层面强制，LLM 必须返回纯 JSON，格式不对直接报错

### 面试时怎么聊

> 面试官：你们项目里 LLM 返回的数据怎么处理的？
> 
> 你：我们用结构化输出，定义了 Pydantic 模型作为 schema，LLM 必须按这个格式返回 JSON。这样前端拿到的数据格式是确定的，不用写一堆容错逻辑。如果 LLM 返回格式不对，后端会捕获异常让它重新生成，最多重试 3 次。

## 第二部分：Function Calling 与工具调用（11.3）

### 是什么

LLM 本身不能查数据库、发邮件、调用 API，它只能生成文字。**Function Calling** 是让 LLM **决定调用哪个工具**，然后你的代码真正去执行工具，再把结果返回给 LLM。

类比：LLM 是大脑，Function Calling 是它的手和脚。

### 核心流程（重要）

1. **你定义工具清单**：告诉 LLM 有哪些工具可以调用，每个工具的参数是什么
   ```python
   tools = [
       {
           "type": "function",
           "function": {
               "name": "query_order",
               "description": "查询订单状态",
               "parameters": {
                   "type": "object",
                   "properties": {
                       "order_id": {"type": "string", "description": "订单号"}
                   },
                   "required": ["order_id"]
               }
           }
       }
   ]
   ```

2. **LLM 决定调用哪个工具**：用户问"我的订单 12345 发货了吗"，LLM 返回：
   ```json
   {
       "tool_calls": [{
           "function": {
               "name": "query_order",
               "arguments": "{\"order_id\": \"12345\"}"
           }
       }]
   }
   ```

3. **你的代码执行工具**：从数据库查订单 12345 的状态，比如返回 `{"status": "已发货"}`

4. **把结果返回给 LLM**：LLM 根据工具返回的数据生成最终回复："您的订单 12345 已发货"

### 为什么需要它

没有 Function Calling 之前，LLM 只能瞎编：
> 用户：我的订单 12345 发货了吗？  
> LLM：您的订单已发货（但它根本不知道真实状态，是瞎说的）

有了 Function Calling，LLM 能调用真实数据：
> 用户：我的订单 12345 发货了吗？  
> LLM：调用 query_order(12345) → 数据库返回"已发货" → LLM 回复"您的订单已发货"

### 工具白名单（权限最小化）

你定义的工具清单就是白名单。不在清单里的工具，LLM 没法调用。

比如你只给它 `query_order`（查订单）和 `apply_refund`（申请退款），它就算被攻击者劫持，也不能调用 `delete_user`（删除用户），因为这个工具根本不在清单里。

### Parallel Function Calling（并行调用）

用户问："帮我查一下订单 12345 和 67890 的状态"

传统方式：LLM 先调用 `query_order(12345)`，等结果回来，再调用 `query_order(67890)`，串行执行，慢。

并行调用：LLM 一次返回两个 tool_calls，你的代码并发执行，快。

### 面试时怎么聊

> 面试官：你们的 AI 客服怎么查真实数据的？
> 
> 你：我们用 Function Calling。定义了几个工具函数，比如查订单、查物流、申请退款。LLM 根据用户问题决定调用哪个工具，我们后端真正去执行工具函数，把结果返回给 LLM，它再生成用户能看懂的回复。
> 
> 面试官：如果用户问的问题没有对应的工具呢？
> 
> 你：LLM 会判断"这个问题不需要调用工具"，直接用它的知识回答，或者告诉用户"这个问题我帮不了你"。

## 第三部分：RAG（检索增强生成，11.4）

### 是什么

LLM 的知识是训练时学到的，训练完之后就固定了。如果你问它"我们公司 2024 年的销售数据"，它不可能知道，因为训练数据里没有。

**RAG** 的做法是：
1. 把用户的问题转成 **embedding**（向量）
2. 从你的**知识库**（向量数据库）里找最相关的文档
3. 把文档内容塞到 Prompt 里，让 LLM 基于这些文档回答

类比：LLM 是学生，RAG 是开卷考试，学生可以查资料。

### 为什么需要它

**场景 1：知识更新**  
LLM 训练数据截止到 2023 年，你问它"2024 年世界杯冠军是谁"，它不知道。但你把 2024 年的新闻存到知识库里，RAG 检索到相关新闻，LLM 就能回答了。

**场景 2：私有数据**  
你们公司的内部文档、客户资料，LLM 训练时不可能见过。用 RAG 把这些文档存到知识库，LLM 就能回答"我们公司的报销流程是什么"。

**场景 3：减少幻觉**  
LLM 不知道答案时会瞎编。RAG 强制它基于检索到的文档回答，文档里没有的内容它就说"我不知道"，不会瞎编。

### 核心流程（重要）

#### 1. 离线准备：构建知识库

1. **文档切分**：把长文档切成小块（chunk），比如每块 500 字，因为 LLM 上下文窗口有限
2. **生成 embedding**：用 OpenAI 的 `text-embedding-ada-002` 模型把每个 chunk 转成向量（一串数字）
3. **存到向量数据库**：比如 Pinecone、Milvus、Faiss，支持向量检索

#### 2. 在线查询：用户提问

1. **用户问题转 embedding**：把"我们公司的报销流程"转成向量
2. **向量检索**：在知识库里找最相似的 Top-K 个 chunk（比如 Top-3）
3. **拼接 Prompt**：
   ```
   参考资料：
   [chunk 1 内容]
   [chunk 2 内容]
   [chunk 3 内容]
   
   用户问题：我们公司的报销流程是什么？
   
   请基于参考资料回答用户问题。如果参考资料里没有相关信息，请说"我不知道"。
   ```
4. **LLM 生成答案**：基于检索到的文档内容回答

### Embedding 是什么（关键概念）

Embedding 是把文本转成向量（一串数字）。**语义相似的文本，向量也相似**。

比如：
- "今天天气真好" 的向量：[0.2, 0.8, 0.1, ...]
- "今天阳光明媚" 的向量：[0.3, 0.7, 0.2, ...]（和上面的向量接近）
- "我喜欢吃火锅" 的向量：[0.9, 0.1, 0.8, ...]（和上面的向量距离远）

向量数据库通过计算**余弦相似度**或**欧氏距离**，找出最相似的文档。

### 向量检索 vs 关键词检索

**关键词检索**（传统搜索引擎）：  
用户搜"如何报销"，只能匹配到文档里含有"报销"这个词的内容。如果文档写的是"费用申领流程"，就匹配不到。

**向量检索**（RAG）：  
"如何报销"和"费用申领流程"语义相似，向量相似度高，能检索到。

### RAG 的局限性

1. **检索不到就不行**：如果知识库里没有相关文档，LLM 还是不知道
2. **chunk 切分影响效果**：切太小，上下文不完整；切太大，检索不精准
3. **成本高**：每次查询要调用 embedding 模型 + 向量检索 + LLM 生成，比纯 LLM 贵

### 面试时怎么聊

> 面试官：你们的 AI 知识库是怎么实现的？
> 
> 你：我们用 RAG。离线时把公司的文档切分成小块，用 OpenAI 的 embedding 模型转成向量，存到向量数据库（比如 Pinecone）。用户提问时，先把问题转成向量，在知识库里检索最相关的 Top-3 文档，拼到 Prompt 里让 LLM 基于这些文档回答。
> 
> 面试官：为什么不直接把所有文档都塞到 Prompt 里？
> 
> 你：因为 LLM 的上下文窗口有限，比如 GPT-4 是 128K tokens，几百个文档根本塞不下。而且就算塞得下，LLM 处理太长的上下文会变慢，成本也高。RAG 只检索最相关的几个文档，又快又省钱。

## 第四部分：三个概念的关系（重要）

### 单独使用的场景

- **只用结构化输出**：让 LLM 提取用户信息、生成表单数据，不需要调用外部工具，也不需要查知识库
- **只用 Function Calling**：客服机器人查订单、查物流，数据在数据库里，不需要向量检索
- **只用 RAG**：AI 知识库问答，只需要检索文档让 LLM 回答，不需要调用工具

### 组合使用的场景（实际项目常见）

**场景 1：RAG + 结构化输出**  
AI 法律顾问：检索相关法条（RAG），然后让 LLM 生成结构化的法律意见书（结构化输出）

**场景 2：Function Calling + 结构化输出**  
AI 数据分析：调用工具查询数据库（Function Calling），返回结构化的图表配置（结构化输出）

**场景 3：RAG + Function Calling**  
AI 客服：用户问"我的订单发货了吗"，先用 Function Calling 查订单状态；用户问"你们的退货政策是什么"，用 RAG 检索公司政策文档

**场景 4：三个都用**  
复杂的 AI Agent：
1. 用 RAG 检索公司知识库，找到相关流程文档
2. 用 Function Calling 调用工具执行操作（比如创建工单）
3. 用结构化输出返回标准化的结果给前端

## 第五部分：关键对比（面试高频）

### 对比 1：结构化输出 vs Function Calling 返回的 JSON

**结构化输出**：LLM 直接生成给用户看的数据，比如用户信息、订单列表

**Function Calling 返回的 JSON**：LLM 告诉你"我要调用这个工具"，参数是什么。这个 JSON 不是给用户看的，是给你的代码看的。

### 对比 2：RAG vs Function Calling

**RAG**：用来回答"知识型问题"，答案在文档里，比如"公司政策是什么"

**Function Calling**：用来执行"操作型任务"，需要调用工具，比如"帮我查订单"

### 对比 3：RAG vs Fine-tuning（微调）

**RAG**：  
- 优点：知识库可以随时更新，不需要重新训练模型；成本低
- 缺点：只能回答知识库里有的内容；每次查询都要检索，慢一点

**Fine-tuning**：  
- 优点：模型学到了你的领域知识，回答更自然；不需要每次都检索
- 缺点：知识更新慢（要重新训练）；成本高；容易过拟合

实际项目中：**优先用 RAG**，除非你有大量标注数据，并且知识更新频率很低。

## 第六部分：实际项目中的典型架构

### 架构 1：纯 RAG 知识库问答

```
用户提问 → embedding → 向量检索 → 拼接 Prompt → LLM 生成 → 返回答案
```

适合：企业内部知识库、文档问答系统

### 架构 2：客服机器人（Function Calling）

```
用户提问 → LLM 判断意图 → 调用工具（查订单/查物流/申请退款）→ 返回结果 → LLM 生成回复
```

适合：电商客服、银行客服

### 架构 3：混合架构（RAG + Function Calling）

```
用户提问 → LLM 判断类型
  ├─ 知识型问题 → RAG 检索文档 → 生成答案
  └─ 操作型任务 → Function Calling 调用工具 → 生成回复
```

适合：复杂的 AI 助手
