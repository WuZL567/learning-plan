# 6.4 Cookie 与 JWT 认证的关系

冲刺模式模板：一句话说清楚 + 三个要点 + 不确定的点

## 一句话说清楚

这里用一句白话写：JWT 是什么、它和 Cookie 是什么关系（谁装谁）。
JWT是JSON Web Token，是一串三段的，签名加密过的身份凭证，可以装到Cookie中进行携带；

## 三个要点

**要点1：JWT 是什么**
写清楚三个部分（用 . 分隔的那三段）各是什么、能不能被篡改：
- Header 和 Payload 存什么？签名 Signature 怎么来的？
Header：存算法信息，可以读可以改；
Payload：存用户信息，base64位，可以读可以改；
Signature：由服务端加密生成；
- 客户端能改 Payload 里的数据吗？改了会怎样？
可以修改，修改之后签名验证就会失效；
- 服务端怎么验证 JWT 真伪（验证什么）？
验证签名是否准确；

**要点2：JWT 怎么存、怎么带**
两种主流方式对比：
- 放 Cookie（httpOnly）里：怎么带？优缺点是什么？
自动携带，优点：避免XSS风险。缺点：存在CSRF风险；
- 放 localStorage 里：怎么带（Authorization 头）？优缺点是什么？
手动放在Authorization中，优点：避免CSRF风险，缺点：存在XSS风险；
- 你自己项目里用过哪种？当时为什么这么选？
没用过；

**要点3：JWT 和 session 认证的区别**
用对比表或白话写清：
- session：状态存在哪？Cookie 里装的是什么？
session存在服务端，Cookie中装的是一个session id，服务端用这个session id去查找状态；
- JWT：状态存在哪？Cookie 里装的是什么？
JWT存在客户端，服务端没有任何状态，只验证签名；
- 哪个可以"无状态横向扩展"？为什么？
JWT，多个后端服务不需要共享，独立验签即可；

## 我的理解中不确定的部分

这里诚实写出还没完全搞懂的点。比如：JWT 过期了怎么办？服务端想提前作废一个 JWT 能作废吗？JWT 里的用户信息泄露了会怎样？
1、JWT过期后，会带着过期的JWT继续请求，服务端验证签名是发现过期，则返回401，引导用户重新登录；
2、没有办法主动提前作废；
3、泄漏后别人就可以用你的JWT冒充你一直到过期，缓解手段是 httpOnly + 短过期 + 刷新机制 + 敏感操作二次验证；

## 三层追问（验收时口答，不用写）

1. 白话复述：30 秒讲清楚 JWT 是什么、登录流程长什么样。
JWT就是JSON Web Token，是一串三段式的，签名加密的身份认证字符串，登录 → 服务端签 JWT → 客户端存（Cookie/localStorage）→ 请求带上 → 服务端验签放行
2. 对比理解：session 认证和 JWT 认证的核心区别是什么（状态存在哪）？
session存在服务端，JWT在客户端；
3. 场景应用：你的项目有 5 个后端服务（分布式），登录态用 session 存内存里，用户登录后访问 2 号服务发现没登录。为什么？换 JWT 能解决吗？
session 在 1 号服务内存里，2 号服务查不到 → 没登录。换 JWT 能解决，任何服务验签即可，无需共享存储；

## 打回修改
1. 为什么 JWT 能无状态横向扩展、session 不能
因为JWT的状态存在客户端，服务端只是验证签名，所以多个后端服务时，每个服务独立进行验签，不需要共享任何东西；
而session的状态存在服务端，需要通过session id来查询状态，多个服务时，需要共享才可以知道其他的服务的状态；

2. JWT 过期后的完整流程（401 → 刷新/重登）
JWT过期后，继续带过期的JWT下发，服务端验签发现过期，返回401，引导客户进行刷新或者重新登录；

3. 提前作废的解法（黑名单/短过期/版本号）
由于JWT是存在客户端的，服务端没有签发记录，没发主动作废，所以可以通过黑名单，缩短过期时间，用户信息增加版本号来提前作废；

4. 场景应用题：5 个服务 session 问题的完整答案
用户登录服务1后，进入服务2发现需要重新登录，是因为服务1和服务2之间没有共享状态导致的；
可以用JWT来处理，因为JWT只需要每个服务都独立验证签名即可，不需要共享；
