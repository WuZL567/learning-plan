## 第一部分：教学过程

### 6.1 Cookie 基本属性（P0，能讲清面试）

**为什么需要它**：5 年经验但面试官问"Cookie 的 domain 和 path 怎么匹配、max-age 和 expires 有什么区别"答不上来。Cookie 是浏览器网络面试的起手式，还是 6.2 安全属性、6.3 CSRF 的地基。

**一句话说清楚**：Cookie 是服务器通过 Set-Cookie 响应头下发给浏览器、由浏览器按 domain/path 规则自动保管、下次请求时自动原样带回的一小段键值对文本（约 4KB）。

**核心原理（快递柜类比）**：
- domain 匹配：不设置默认当前域名（不含子域）；显式设置 domain=example.com 则所有子域携带；跨域永远拿不到
- path 匹配：默认 /，设置为 /admin 后只有该路径开头才携带；domain 和 path 是 AND 关系
- expires vs max-age：expires 是绝对时间，max-age 是相对秒数，现代浏览器优先认 max-age；都不设 = 会话 Cookie（关浏览器进程清，不是关标签页）
- 大小限制：单个约 4KB，一域名约 20 个

**练习任务**：填笔记 notes/module-06-storage/6.1-Cookie基本属性.md（模板含四个要点 + 不确定的部分 + 三层追问）

### 6.2 Cookie 安全属性（P0，能讲清面试）

**为什么需要它**：裸奔的 Cookie 被攻击者利用产生两种经典攻击——XSS 窃取（页面注入脚本读 document.cookie）、CSRF 借刀（浏览器自动带 Cookie）。安全属性是三道锁。

**一句话说清楚**：httpOnly 锁住 JS 读取（防 XSS 偷）→ Secure 锁住传输通道（防中间人窃听）→ SameSite 锁住跨站携带（防 CSRF 借刀）。

**核心原理（银行门禁卡类比）**：
- httpOnly：设置后 document.cookie 读不到（JS 彻底不可见），但浏览器自动携带不受影响；防 XSS 窃取，防不了"代发请求"
- Secure：仅 HTTPS 携带；localhost 例外（浏览器视为可信源）
- SameSite：Strict 任何跨站不带；Lax（默认）跨站顶层导航带，iframe/fetch/图片不带；None 任何跨站都带，必须同时配 Secure
- 判断链：跨站 → 带不带？→ Strict 不带，None 带，Lax 看是不是点链接进来

**练习任务**：填笔记 notes/module-06-storage/6.2-Cookie安全属性.md

### 6.3 Cookie 与 CSRF 的关系（P0，能讲清面试）

**为什么需要它**：CSRF 是怎么发生的、为什么"自动携带"变成攻击武器、httpOnly 为什么防不了 CSRF。大厂高频追问点。

**一句话说清楚**：CSRF（跨站请求伪造）是攻击者借用你浏览器里已登录的 Cookie，以你的身份向网站发送恶意请求——浏览器自动带 Cookie 这个机制本身，就是攻击的帮凶。

**核心原理（借钥匙类比）**：
- 攻击链路四步：①已登录（浏览器存着 A 的 Cookie）②诱导（访问恶意页 B）③借刀（B 里埋 <img src="https://a.com/api/transfer?...">，浏览器自动带 A 的 Cookie）④得手（服务端以为是本人）
- httpOnly 为什么防不了：防的是 JS 读取，CSRF 全程没人读 Cookie，自动携带是网络层行为
- 三道防线：SameSite=Lax/Strict（源头断）、Referer/Origin 校验（服务端查来源）、CSRF Token（页面下发随机 Token，攻击者拿不到）

**练习任务**：填笔记 notes/module-06-storage/6.3-Cookie与CSRF的关系.md

### 6.4 Cookie 与 JWT 认证的关系（P1，能讲清面试）

**为什么需要它**：现代登录态主角。面试必问"登录态怎么存的？为什么用 JWT？放 Cookie 还是 localStorage？"

**一句话说清楚**：JWT 是一串三段的、带防伪签名的身份凭证——服务端验签名认人，不查数据库；JWT 可以装进 Cookie 里由浏览器自动携带。

**核心原理（演唱会手环类比）**：
- 三段结构：Header（算法，可读可改）、Payload（用户信息，Base64 可读可改）、Signature（header.payload + 密钥签名，改任何字符签名就失效）
- session vs JWT：session 状态在服务端（内存/Redis），Cookie 里装 session id，横向扩展需共享存储；JWT 状态在客户端，服务端无状态只验签，独立横向扩展
- 携带方式权衡：httpOnly Cookie（防 XSS 但 CSRF 风险，靠 SameSite/Token 防）vs localStorage + Authorization 头（防 CSRF 但 XSS 一读就走）
- JWT 过期 = 验签时发现 exp 过期返回 401（服务端没存过，不存在"清理"）；提前作废是痛点，解法黑名单/短过期/版本号；泄露 = 被冒用到过期，缓解 httpOnly + 短过期 + 刷新 + 二次验证

**练习任务**：填笔记 notes/module-06-storage/6.4-Cookie与JWT认证的关系.md

### 6.5 localStorage 特性（P0，能讲清面试）

**为什么需要它**：天天用 localStorage，面试考的是没深想的：什么时候清、谁读得到、存 Token 安不安全。

**一句话说清楚**：浏览器按域名隔离的、持久化的键值存储——关浏览器数据都在，只有手动清才没（本身没有过期概念），容量约 5MB，只能存字符串。

**核心原理（仓库储物柜类比）**：
- 作用域 = 同源（协议+域名+端口）；a.example.com 和 b.example.com 不同源读不到；同一源所有路径共享、所有标签页共享
- 没有过期时间；存对象必须 JSON.stringify/JSON.parse
- 不能存敏感信息：任何 JS 能读，XSS 下一读就走（6.11 Token 存储的伏笔）
- 跨标签页通知：storage 事件（只有其他标签页能收到，改数据那个页面收不到）

**练习任务**：填笔记 notes/module-06-storage/6.5-localStorage特性.md

### 6.6 sessionStorage 特性（P0，能讲清面试）

**为什么需要它**：核心差异学生已会，考的是三个刁钻边界：复制标签页、新开标签页、刷新。

**一句话说清楚**：标签页级的临时存储——数据绑定在"这个标签页 + 这个会话"，关标签页就清，刷新不清。

**核心原理（工位便利贴类比）**：
- 复制标签页：sessionStorage 复制一份副本（互不同步）；localStorage 共享同一份
- 新开标签页：不共享（新标签页 = 新会话）；例外 window.open 会复制父页面一份（仅跳转时）
- 同标签页同源跳转保留，跨域跳转丢失；刷新保留
- 典型场景：多步骤表单暂存（刷新不丢、关掉不留垃圾）

**练习任务**：填笔记 notes/module-06-storage/6.6-sessionStorage特性.md

### 6.8 IndexedDB 基本概念（P2，了解概念）

**为什么需要它**：面试场景是"localStorage 5MB 不够存更大的怎么办"——答出"IndexedDB，浏览器内置的非关系型数据库，容量大、支持索引查询、异步"即过关。

**一句话说清楚**：浏览器内置的完整数据库——存对象、支持索引和查询、容量远超 localStorage（几百 MB 到 GB 级）、异步操作。

**核心原理（Excel 表 vs 仓库货架）**：
- 容量：localStorage ~5MB vs IndexedDB 几百 MB~GB；存字符串 vs 对象/数组/Blob/File；同步 vs 异步（不阻塞主线程）；只有 key 取值 vs 索引 + 范围查询
- 典型场景：PWA 离线应用、大文件/图片缓存、复杂数据本地查询
- 关键词：异步 + 事务（一组操作的原子单元，全成功或全回滚）

### 6.3 验收（8/31）

**学生笔记核心内容**：攻击链路四步完整 ✅；"httpOnly 防不了 CSRF"灵魂问题答对（攻击者不需要知道 Cookie 内容，只借自动携带机制）✅；防线名目答全 ✅；Lax 下"GET 请求还是带 Cookie"（不够精确，已纠正为：只有跨站顶层导航的 GET 带）。
