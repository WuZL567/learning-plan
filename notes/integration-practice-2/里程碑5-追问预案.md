## A. 架构选型类（考你有没有独立决策能力）

### A1. 为什么用 RAG，不直接微调模型？

> **面试官为什么问**：考察你知不知道 RAG 和微调的适用边界。答"RAG 更好"是错的，两者解决不同问题。

**一句话**：**微调教模型"怎么说话"，RAG 教模型"说什么"。** 我这个项目要的是"说什么"，所以用 RAG。

**原理——五个维度对比**：

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 改文档 → 重新向量化，**分钟级** | 重新准备数据 + 重新训练，**天级 + 花钱** |
| 可溯源 | 天然支持（每个 chunk 带 source） | **做不到**，答完不知道它从哪学的 |
| 幻觉 | 能治（检索不到就拒答，答案有出处） | **治不了**，只是换了一种编法 |
| 成本 | 一次向量化几分钱 | 训练成本高，还要标注数据 |
| 适用场景 | 知识频繁变、要给出处、要可控 | 固定风格/格式、任务模式稳定 |

**项目里的体现**：我的知识库是我自己的 4 篇学习笔记，**它们会改**（写错了要订正、内容过时要更新）。
改完只要重跑一次 `build_index()` 就立刻生效，**不需要任何训练**。而且我的前端要显示引用卡片，
这要求系统**知道**答案来自哪个文件——**微调后的模型给不了这个信息**。

**追问延伸**：两者不是二选一。生产里常见组合是——**RAG 解决知识，微调解决输出格式/风格**。

### A2. 流式输出为什么用 SSE，不用 WebSocket？

> **面试官为什么问**：考察知不知道"选型看场景，不是看哪个更高级"。

**① 数据方向：单向上，双向才用 WebSocket**

SSE 是**单向**（服务端 → 客户端），WebSocket 是**双向**。

我这里是"你问我答"：客户端发一次请求，服务端持续推 token——**只需要服务端推**。
为单向场景上 WebSocket，要付出升级协议、维护连接状态、自己实现心跳和重连的代价，不划算。

WebSocket 该上的场景是**真的双向高频**：协同编辑、多人游戏、股票行情（客户端也在持续发数据）。

**② 协议和实现成本**

SSE 就是**普通的 HTTP 响应**，只是 `Content-Type: text/event-stream` 且不一次性关掉。
所以：走 80/443 不用改防火墙、能复用现有鉴权中间件、浏览器原生支持、后端就是一个生成器 +
`StreamingResponse`。

**③ 自动重连：在 AI 场景里是麻烦，不是好事**（你已订正，这里补足机制）

**结论**：`EventSource` 的自动重连在 AI 场景里是**麻烦，甚至是危险的**。

**为什么——它的重连机制决定了这件事**：

1. 连接断了，浏览器会**静默地**等几秒后**重发同一个请求**。前端不一定知道，用户也不知道。
2. 重连时它会带上 `Last-Event-ID` 头，本意是让服务端**断点续传**。但这要求服务端自己实现
   "从哪个 token 接着发"。
3. **我的后端是无状态的**——收到重连请求只会当成一次**全新的对话**：重新检索、重新调模型、
   从头开始生成。**不是"可能"重问，是"一定会"重问一遍。**
4. 结果：白烧一次 token（AI 场景这一问可能几千 token，还叠加检索和更长的 prompt），
   用户那边可能看到**重复或错乱的回答**。

所以「自动重连」这个 Web 时代的优点，在"每次重试都要花钱"的 AI 场景里变成了缺点。
我用 `fetch` 手写解析，一部分原因就是**重试要由我掌控**——真要重试，应该是用户点按钮，不是浏览器偷偷来。

**④ 那为什么不用 EventSource**

`EventSource` **只支持 GET**。聊天必须把消息内容、历史记录、参数 POST 过去，
GET 只能塞 query string，有长度限制而且会写进服务器日志。
所以真实 AI 应用走的都是 `fetch` + `ReadableStream` + 手动解析。

### A3. 向量检索为什么自己手写，不用 FAISS / Chroma？

> **面试官为什么问**：考察你是"会用库"还是"懂原理"。答"因为简单"会失分。

**① 我的数据规模**：知识库 4 篇文档，切成 **19 个 chunk**。这个量级下暴力遍历的全部成本
就是 19 次余弦相似度计算，**微秒级**，上向量库属于杀鸡用牛刀。

**② 手写的真正理由**：这个项目的目的之一就是**把向量检索每一步摊开看**——切块怎么切、
向量长什么样、余弦怎么算、top-k 怎么选、阈值怎么过滤。用 FAISS 的话 `index.search()` 一行返回结果，
**面试问"检索怎么实现的"，我不能答"调了个库"**。

**③ 复杂度，和它什么时候会崩**

暴力遍历是 **O(n)**（n = chunk 总数），**每个请求都要完整跑一遍**。

❌ **你原来答的**：「如果知识库数量庞大，代码中**向量化**这一步就会先卡住」
—— **错。崩的是检索，不是向量化。**

**关键区分**：向量化是**启动时跑一次的离线成本**；检索是**每个请求都要跑的在线成本**。

| 崩点（都在检索上） | 具体发生了什么 |
|------|--------------|
| **内存** | `VectorStore` 用 `list[list[float]]` 存向量。10 万 × 1024 维，Python 里每个 float 是**独立对象**（约 24 字节）+ 列表指针 8 字节 ≈ 32 字节 → **约 3.3 GB**，进程直接 OOM。（同样的数据换 numpy `float32` 只要 410MB——这就是数据结构选型的差别） |
| **延迟** | `search()` 把 query 和**全部** 10 万个向量逐个算余弦，而 `cosine_similarity` 是**纯 Python 循环**、不是 numpy 向量化 → **单次查询就是秒级**。并发几个用户直接把 CPU 吃满 |

**向量化那边确实也有 batch 上限，但它不致命**：它是**离线的、可分批并发的、跑完就完事**——
分批慢慢跑一小时的活儿，不影响任何用户。**检索是每个用户每次提问都要重做的，所以它才是瓶颈。**

**④ 生产项目我怎么选**

上带 **HNSW（近似最近邻）**索引的向量库：FAISS / Milvus / pgvector / Qdrant。
把 O(n) 暴力遍历换成近似 O(log n)，**用一点点召回准确率换几十倍速度**。
**万级数据开始有感，十万级以上必须上索引。**

> 这个答案其实就写在你自己 `VectorStore` 的 docstring 里——写代码时懂，面试时要能脱口而出。

## B. 实现细节类（考你真的动手了没有）

### B4. 完整讲一遍 RAG 的链路：从一篇文档到一次回答

> **面试官为什么问**：这题是"你是不是真的做过"的试金石。**讲不连贯 = 抄的。**

**关键：分两个阶段讲，别混在一起**——这一句话本身就体现你理解架构。

**阶段一：离线建索引（启动时跑一次）** —— `backend/rag.py`

```
load_documents()   →   split_text()   →   embed_texts()   →   store.add()
扫描 knowledge/       切成 chunk          【整批一次请求】     文本 + 向量
下的 .md 文件         (300/50)          调 bge-m3 向量化      分开存，下标一一对应
```

- `load_documents()`：扫目录、过滤非 md、**每块带上 `source`**——**引用来源从这一步就开始带了**
- `split_text()`：固定长度滑动窗口，`chunk_size=300` / `overlap=50`
- `embed_texts()`：**整批一次请求**（这就是 19 次 → 1 次那个优化）
- `store.add()`：文本和向量**分开存**，靠数组下标一一对应

**阶段二：在线问答（每个请求都要跑）** —— `rag_chain.py` + `main.py`

```
retrieve()             → filter_by_threshold()  → build_messages()   → to_sources_frame()
问题向量化                低分 chunk 扔掉            chunk 拼进           yield 给前端
→ store.search(k=3)      （空了就走拒答分支）        system prompt
                                                                          ↓
                                                                 调 DeepSeek stream=True
                                                                          ↓
                                                 逐块 to_sse_frame() → 前端解析渲染
```

**衔接点**：`main.py` 在**启动时**把 `build_index()` 的结果存成一个**全局变量**，
`/chat/stream` 每次请求直接用（不重建）。**这就是"离线"和"在线"的分界线。**

❌ **你原来答的不足**：链路本身顺序对了，但**没说出每一步在哪个文件/函数**——面试官会追问，
答不出来就显得是背的。

### B5. 切块为什么是 chunk_size=300 / overlap=50？怎么定的？

> **面试官为什么问**：考察你懂不懂"切块直接影响检索质量"——这是 RAG 调优的第一现场。

**① 太大 / 太小会怎样**

| 参数 | 太大 | 太小 |
|------|------|------|
| `chunk_size` | **语义稀释**：一块里混了好几个主题，向量变成"平均值"，跟谁都像又跟谁都不像 → 检索不准 | **语义不完整**：答案被切碎，检索到了也只有半句话 → LLM 答不上来 |
| `overlap` | 冗余块变多（同一内容被检索到两次，浪费 context 和 token） | 关键句正好跨在切割点上时**被切成两半，两块都不完整** → 检索不到 |

**② `overlap` 到底解决什么**

**防止关键句正好跨在切割点上被切碎。** 一句话如果正好跨在切割点上，
没有 overlap 的话它在前一块里只有半句、后一块里也只有半句，**两块都检索不到**。
加了 50 字重叠，这句话**至少有一块是完整的**。

**③ 我在这上面亲手踩过的坑（讲这个最加分）**

> 4A 写 `split_text` 时，我在"最后一块怎么收尾"上**改了三轮才对**，根因是**用错了位置**：
>
> ```python
> chunk = text[i:i + chunk_size]
> curr_end = i + chunk_size      # ❌ 名义位置：理论上最多能切到哪
> ```
>
> `04-项目架构说明.md` 总共 **772** 字。当 `i = 750` 时，`curr_end = 750 + 300 = 1050`——
> **但文档里根本没有第 1050 个字。** 应该用 `i + len(chunk)`（**实际**切到了哪）。
>
> 更坑的是我那个防御用的 `break` 是**死代码**：
> `curr_end - prev_end` 恒等于 `step`，而 `step = chunk_size - overlap > 0`，
> 所以条件**永远为假、`break` 永远不执行**。
> **看起来在防一个边界，实际什么都没防住——比不写还危险，因为你会以为自己已经防住了。**
>
> **我从中总结的模式**：这个项目里"修一处坏一处"出现了**三次**（里程碑 3 也有一次）。
> 后来我强迫自己**改代码前先写不变量测试**——而且测试数据别挑 `'0123456789'` 这种能整除的长度
> （它恰好掩盖了这个 bug），要挑**除不尽的、卡在边界上的**。

**④ 300 / 50 是拍脑袋的吗？**

**是起点，不是结论。** 300 是个常见默认值，50 约是它的 1/6。
正确做法是**靠评测定**：建一批"应该命中某篇文档"的问题跑一遍看命中率，调参数再跑对比。
**诚实答"我先用了常见起点，还没做系统评测"，比假装是算出来的强。**

### B6. 相似度为什么用余弦，不用欧氏距离？

> **面试官为什么问**：老牌题，考察向量空间的基本感觉。

**① 两者算的分别是什么**

- **余弦**：两向量**夹角**的余弦，只关心**方向**，完全不管长度
- **欧氏**：空间中两点的**直线距离**，方向和长度都算进去

**文本语义只体现在方向上**，所以余弦更贴切。

**② 向量的"长度"代表什么？**

❌ **你原来答的**：「长度代表它们的文本多长，和语义无关」
—— **前半句错**。embedding 的模长**跟文本长短没有直接关系**，它也是模型训练出来的数值。

**正确答案**：长度在语义上**没有可靠含义**——既不表示"文本有多长"，也不表示"语义有多强"。
**既然它没有意义，就不该让它影响相似度计算，所以要把长度这个因素除掉**——这正是余弦做的事。

**③ 什么时候两者结果一样？**

❌ **你原来答的**：「完全一样的句子」——太窄了。

**正确答案**：**当所有向量都被归一化（长度 = 1）之后。**

数学上，归一化后 `欧氏距离² = 2 - 2 × 余弦相似度`——两者**单调等价**，排序结果完全一致。
所以很多向量库的做法是：**入库前统一归一化，之后只算内积（点积）**——比余弦还快一步。

（你答的"完全一样的句子"只是余弦 = 1、距离 = 0 的**特例**，不是"两者等价"的条件。）

**④ 我代码里怎么处理零向量**

`cosine_similarity` 里判断模长为 0 就 `return 0.0`——零向量**没有方向**，余弦值数学上是 `0/0` 未定义。
返回 0 表示"不相关"是合理的工程处理，但要诚实说出它的**副作用**：
**它和"真正正交（余弦也是 0）"分不开**。真要严谨，应该返回 `None` 或抛异常，
让调用方知道"这条数据有问题"，而不是静默地当成"不相关"。

### B7. 引用来源为什么单开一个 `event: sources`，不混在正文里？

> **面试官为什么问**：考察接口设计意识（数据分离）。

**① 混在正文里会怎样**

**因为两者的"节奏"根本不同：**

- **正文是流式的**：一个 token 一个 token 来，几百毫秒到几秒才说完
- **引用是一次性的**：检索在**调模型之前**就完成了，所有来源信息**当场就有**

而且混在一起有两个具体的技术问题：

1. **前端没法区分**。正文本身可能包含换行、可能包含像 JSON 的文本。你无法在流式正文里
   可靠地插入一段结构化数据——前端会分不清"这是模型说的话"还是"这是引用元数据"。
2. **时机不对**。我实测过：`sources` 帧是在**第一个 token 之前**发出去的。
   引用应该在答案开始之前就准备好，混进正文就只能等最后才给——**用户得看完答案才看到出处**。

**② 前端拿到 sources 之后做了什么**（你答的"下方"是对的，这里补全细节）

`processEvent()` 按 `event:` 字段**分发**：`sources` → `renderSources()`，正文 → `renderMarkdown()`，
`[DONE]` → 解锁输入框。

**渲染位置：引用卡片在答案的【下方】**。这里有个反直觉的细节值得讲：

> **数据的到达顺序 ≠ 视觉的展示顺序。**
> `sources` 帧是**先**到的（第一个 token 之前），正文是**后**到的。
> 但我希望用户先看答案、再看出处，所以代码里 `renderSources()` 用 `appendChild`，
> 而 `renderMarkdown()` 用 **`item.prepend(contentEl)`**——把后到的正文**插到最前面**。
> 两个元素还必须分开（各占一个 DOM 节点），否则 `renderMarkdown` 每次重写 `innerHTML`
> 会把引用卡片冲掉。

**③ 通用原则叫什么**

**SSE 协议自带的 `event:` 字段就是干这个的**——用**事件类型**给同一路流里的不同数据打标签，
让前端能分别处理。本质是**把"传输通道"和"数据语义"解耦**：一条连接，多种消息类型。

同一个思路在别处也见过：WebSocket 消息里的 `type` 字段、Redux 的 action type、
HTTP 的 `Content-Type`——**都是"同一通道跑多种数据，得有一层类型标记"**。

## C. 边界与局限类（考你的工程判断力）

### C8. 检索不到相关内容时，你的系统怎么表现？

> **面试官为什么问**：考察你是不是只做了 happy path。
> **能主动说"拒绝回答是特性"的人，立刻就区分开了。**

**① 后端**

`filter_by_threshold()` 把低于 0.5 分的 chunk 全部丢掉，**可能返回空列表**。
空列表传给 `build_rag_system_prompt()` 时走的是**另一条分支**——不是"没有参考资料"，
而是明确告诉模型：**知识库里没有相关内容，不要编造，直接告知用户**。

**这是刻意设计的，不是兜底。关键词是：拒答是特性（feature），不是 bug。**

**② 前端**：答案气泡里显示"未命中知识库"，引用区显示找不到相关资料。

**③ 为什么"硬凑 top-k 喂给模型"比"返回空"更糟**

**因为检索一定会返回 top-k**——哪怕知识库里一个字相关内容都没有，它也会挑出分数最高的
3 个 chunk 给你。这些 0.3~0.4 分的垃圾塞进 prompt，模型会**照着垃圾一本正经地编答案**。
这是 **RAG 幻觉的头号来源**。

**而且它比"直接说不知道"危险得多**：**用户会以为这是你知识库里的答案。**

### C9. 你这个 demo 有什么已知限制？

> **面试官为什么问**：**必问题。** 答"没什么限制"= 没想过；答一堆 = 不自信。
> 正确姿势：**给 3 条 + 每条配一句"生产环境怎么解"**。

**① 后端无状态，对话历史不持久**

历史由前端每次带上来（最近 20 条截断），刷新页面就没了，也没法多设备同步。
**生产做法**：建 conversation 表按 `user_id` + `session_id` 存储，或用 Redis 存最近上下文。

**② 向量库在内存里，重启就没了**

每次启动都要重新加载文档、重新调 embedding API 建索引——**白花钱也白等**。
**生产做法**：向量持久化（FAISS 存 index 文件 / 上 pgvector），启动时先读，没有再建。
更进一步要用**文件 hash 判断内容有没有变**，只重建变了的文档。

**③ 检索质量：只有单路向量检索，没有 rerank**

现在是"向量召回 top-k → 阈值过滤"一条路走到黑。**两个改进方向**：

- **加 rerank（11.4.15）**：向量召回先捞多一些（比如 top-20），再用 rerank 模型精排取 top-3。
  **召回负责"别漏"，精排负责"别错"**——这是解决阈值分界带重叠的标准手段
- **混合检索**：向量检索（语义）+ 关键词检索（BM25 / 全文索引）合并。
  向量对**专有名词、报错码、函数名**这类没有语义泛化的词很弱，**关键词检索正好补这块**

**④ 没有评测集，不知道检索准不准**（❌ 你原来只写了这句，没有生产做法）

阈值 0.5 是"常见起点"，不是"我的数据的答案"。
**生产做法**：建评测集（正例 / 负例 / 边界），用 `recall@k`、`MRR` 这类指标量化，
或上 **RAGAS** 做端到端的忠实度评估。**没有评测，所有调参都是拍脑袋。**

**⑤ 没有鉴权和限流**

谁都能调这个接口刷额度，`.env` 里两个 Key 是实打实要花钱的。
**生产做法**：接口加鉴权（token / session）+ 限流（Redis 令牌桶），Key 只放服务端。

### C10. 19 次 API 调用优化到 1 次 —— 你怎么发现、怎么改的？

> **面试官为什么问**：这是你项目里**最像真实工程**的一段。他其实在问"你平时怎么定位性能问题"。

**① 为什么原来是 19 次**

`split_text` 把知识库切成 19 块，而我当时的 `build_index` 是：

```python
for chunk in chunks:
    embed_texts([chunk])      # ❌ 每块单独发一次请求
```

**19 块 = 19 次网络往返。** 不是模型慢，是我的调用方式蠢。

**② 怎么发现的**

看后端日志的耗时——建索引要 **3.79 秒**，远超预期。数了一下请求次数才反应过来。

> 诚实说：**不是设计时想到的，是看到耗时不对劲才回头查的**。这个回答比"我一开始就设计好了"可信。

**③ 怎么改的**

`embed_texts(texts)` 本身接受**列表**——把整批 chunk 一次性传进去，19 次网络往返变成 **1 次**。
耗时 **3.79s → 0.87s**。

**④ 这个数字怎么测的**

打印建索引开始/结束的时间戳，跑几次取稳定值。
**注意**：要排除首次请求的冷启动（DNS、TLS 握手）影响，所以**至少跑两轮看第二轮的稳定值**。

**⑤ 延伸：10 万条能一次性 batch 吗？**

**不行。** 两个墙：① embedding 接口**单次请求有条数上限和 token 上限**；
② 一次性把 10 万条文本读进内存会有**内存尖峰**。
**生产做法**：**每 100 条一批循环调用 + 并发**，配合失败重试。

### C11. 检索捞出了知识库里根本没有的内容，模型还照着答了——你怎么看？

> **面试官为什么问**：这是 C8 的**反向题**——拒答机制失效了，考察你能不能诊断。
> ⚠️ **这条考点你连着两次没答到**（4B 的 Q6 和这次），重点看。

❌ **你原来答的**：「先看下这个问题的答案是否正确，正确就没必要调整阈值」
—— **判断标准错了。不是"答案对不对"，是"答案该不该给"。**

**① 结论：这是拒答失败，不是"答案不够准"**

**知识库里没有微服务 → 任何答案都不该出现，哪怕它碰巧是对的。**

**为什么"碰巧对"反而更危险**：我的前端会**同时**渲染答案和引用卡片。
用户看到引用卡片，会默认"这是知识库说的"——而实际上模型是拿**预训练知识**编的。
**引用系统这时候变成了帮凶**：引用存在的全部意义是"可回溯验证"，
一旦允许"没检索到也答"，引用就成了摆设。

而且——**这次碰巧对，下次我就会觉得 0.513 也还行，阈值就是这么被一点点放弃的。**

**② 原理：为什么会有 0.513**

说明知识库里存在**"通用性较强"的中性 chunk**——讲架构、讲原理、讲通用概念的那类段落。
**它跟任何技术问题都有中等相似度。** 这类 chunk 是噪声源，也是阈值定不准的元凶。

**③ 正确做法（三步）**

1. **建评测集**：一批"知识库内"的问题当**正例**，一批"知识库外"的问题当**负例**
2. 看两组分数的**分布**，找正例最低分和负例最高分之间有没有**分界带**
3. 有分界带 → 阈值定在中间；**分界带重叠（正例低分和负例高分分不开）→ 单靠阈值解决不了**，
   得上 **rerank** 或回去改切块

**④ 根本问题**

**不是我阈值调得不对，是我从来没评测过这个知识库。**
0.5 是"bge-m3 的常见起点"，不是"我的数据的答案"。

### C12. 点引用卡片想跳转到完整原文，你的系统还缺什么？

> **面试官为什么问**：考察你做引用功能时，有没有想到"引用是可验证的"这个终点。
> ⚠️ 这题和 4B 的 Q8 是同一个，你上次只答出 1/3。

**三样东西，缺一不可：**

| # | 缺什么 | 为什么 |
|---|--------|--------|
| 1 | **位置信息** | chunk 存的时候要带 `offset` / 行号——"这段话在原文的第几行"。现在只存了 `source` + `text` |
| 2 | **取原文的接口** | 现在 `sources` 帧只带 `text[:200]`（**截断的前 200 字**），**前端手里根本没有全文**。就算给了位置信息，拿什么去高亮？要加个接口，比如 `GET /document/{source}` 返回全文 |
| 3 | **稳定 id** | 现在 sources 里的 `index` 是**每次检索时数组下标的临时值**，刷新一次就变了。引用卡片要做成可链接、可分享、可被稳定指向，chunk 需要一个**稳定 id**（比如 `文件名 + offset` 的哈希） |

**关键区分**：1 和 2 是两件事——**位置**是"原文在哪"，**接口**是"怎么把原文拿过来"。
你上次只想到了前者。

**当前实现的正确说法**：引用卡片显示的是**命中片段的前 200 字 + 来源文件名**。
面试演示时**不要说"能跳转到原文"**——做不到，被追问会很难看。
