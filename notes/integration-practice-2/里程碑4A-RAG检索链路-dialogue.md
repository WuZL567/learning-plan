## 二、教学过程（原文保留）

### 为什么需要 RAG

大模型的知识在训练完成那一刻就冻结了，你问它"我们公司内部文档里写了什么"，它不知道；而且它不知道的时候不会说不知道，会一本正经编一个——这就是幻觉。

两种解法：

| 方案 | 做法 | 代价 |
|------|------|------|
| **微调** | 把知识"训进"模型权重里 | 贵、慢、知识一更新就得重训 |
| **RAG** | 不改模型，提问时去知识库**现查**，把查到的资料塞进 prompt | 便宜、实时、可溯源 |

**类比：微调 = 让学生背书；RAG = 开卷考试。**

### 一句话说清楚

RAG 就是给大模型开卷考试：提问时先去知识库检索出最相关的几段资料，把资料和问题一起交给模型，让它照着资料回答，并告诉你答案是从哪来的。

### 核心原理：两个阶段、四步

```
【离线·建索引，进程启动时做一次】
  知识库文档 ──①切块──▶ 一堆 chunk ──②向量化──▶ 向量 ──③存进向量库
                                                          │
【在线·每次提问】                                           │
  用户问题 ──②向量化──▶ 问题向量 ──④和库里所有向量算余弦相似度──▶ top-k
                                                          │
                     把 top-k 拼进 system prompt ◀─────────┘
                                 │
                     调 DeepSeek 流式生成 ──▶ SSE 吐给前端（附带引用来源）
```

**关键点 1：为什么要切块**

整篇文档直接塞进去三个问题：超上下文窗口、token 巨贵、检索粒度太粗。
**切块就是把书拆成卡片——检索的单位是卡片，不是整本书。**

- **切太小** → 单块语义不完整，"它""这个"指代不明 → 模型看不懂
- **切太大** → 一块里混进太多无关内容 → 检索精度掉、token 浪费
- **overlap（重叠）** 解决边界切断问题：关键句跨在切割点上时，靠重叠保证它至少在某一块里完整

```
原文：  A B C D E F G H I J
chunk_size=4, overlap=1, 步长=3

块1: A B C D
块2:       D E F G      ← D 是重叠部分
块3:             G H I J
```

**关键点 2：Embedding 在干什么**

把一段文本变成一串固定长度的数字（bge-m3 是 1024 个浮点数）。神奇之处：**语义相近的文本，向量也相近**——相当于给每段文字在"语义地图"上定位，找相关内容就变成了**找最近的几个点**。

**关键点 3：余弦相似度**

```
cos = 1  → 方向完全相同 → 最相似
cos = 0  → 垂直         → 毫不相关
cos = -1 → 方向相反
```

公式：`cos(a, b) = (a·b) / (|a| × |b|)`

**为什么用余弦不用欧氏距离？** 余弦只看**方向**、不看**长度**。同一段话写长写短，方向基本不变、语义也没变，所以余弦能公平比较长短不一的文本。

## 三、开发过程中的四个坎

### 坎 1：`python rag.py` 报 `ModuleNotFoundError: No module named 'dotenv'`

**学生操作**：`❯ python rag.py`

**根因**：用了**系统 Python**，而依赖装在 `backend/venv/` 里。

**教学**（前端类比）：

| Python | 前端对应 |
|--------|---------|
| 系统 Python | 全局 `node` |
| `backend/venv/` | 项目的 `node_modules/` |
| `./venv/bin/python` | `./node_modules/.bin/vite` |

**关键点**：venv 里的 python 和系统的都是 3.12.10，**版本一样**——所以报错是"找不到模块"而不是"版本不对"，更隐蔽。

**两个修法**：
- 显式：`./venv/bin/python rag.py`
- 激活：`source venv/bin/activate` 之后 `python rag.py`
- 确认：`which python` 看路径

### 坎 2：不知道 `embed_texts` 怎么写

**导师给的通用技巧（比记住 API 更重要）**：

> **不确定一个对象长什么样，就 `print` 出来看。**
> 逐层往深挖：`print(resp)` → `print(resp.data)` → `print(resp.data[0])` → `print(type(resp.data[0].embedding))`
> 这比查文档快 10 倍，而且是**你自己验证过的事实**。

**学生探到的结构**：`resp.data[0].embedding` 是 `<class 'list'>`

**导师补充的语法映射**（JS → Python）：

```python
# JS:  numbers.map(n => n * 2)
doubled = [n * 2 for n in numbers]

# JS:  users.filter(u => u.age > 18)
adults = [u for u in users if u.age > 18]
```

**并强调了一个 RAG 的地基**：

```
chunks[i] ──► texts[i] ──► resp.data[i].embedding ──► vectors[i]
   ▲                                                      │
   └──────────── 必须严格一一对应 ─────────────────────────┘
```

一旦顺序错位，向量库里每块文本挂的都是**别人的向量**——检索结果完全乱套，但**不会报错**。

### 坎 3：`split_text` 三轮回合（本次最大教训）

#### 轮次 1：无脑 append → 尾部冗余块

```python
for i in range(0, len(text), step):
    chunk = text[i:i + chunk_size]
    chunk_list.append(chunk)
```

**实测**：`split_text('0123456789', 4, 1)` → `['0123', '3456', '6789', '9']`（应该是 3 块）
`04-项目架构说明.md`（772 字）→ `[300, 300, 272, 22]`，最后那块 22 字**完全被前一块覆盖**。

**这个 bug 的危险性**：不报错、输出看着正常，只是悄悄往知识库里灌垃圾 chunk（会拿到自己的向量参与检索，可能挤掉真正有用的块）。

#### 轮次 2：用「长度」判断 → 丢内容（更严重）

```python
if len(chunk) < chunk_size and i > 0:
    break
```

**错误假设**：「太短」≠「内容被前面的块覆盖了」。

**实测**：4 篇文档**全部丢失尾部内容**

| 文档 | 丢失 |
|------|------|
| 01-SSE流式输出.md | 约 30 字 |
| 02-RAG检索增强生成.md | 约 127 字 |
| 03-前端XSS防护.md | 约 92 字 |
| 04-项目架构说明.md | **约 222 字**（"三个接口""已知限制"整段没了） |

**导师点评**：`i > 0` 护栏只救了第一块，救不了尾巴。判断标准应该是「**这块有没有带来新内容**」，不是「这块有多长」。

**同时指出测试数据的问题**：学生测的是 `'0123456789'`（10 字），**恰好掩盖了 bug**（最后一块正好 4 个字）。换成 `'ABCDEFGHIJKL'`（12 字）立刻露馅（`JKL` 丢了）。

> **教训：测试数据的长度不要挑"能被整除"的整数，要挑除不尽的、卡在边界上的。**

#### 轮次 3：用了「位置」但用错 → 死代码，回到轮次 1

```python
prev_end = 0
for i in range(0, len(text), step):
    chunk = text[i:i + chunk_size]
    curr_end = i + chunk_size      # ← 名义位置
    if curr_end <= prev_end:
        break
    chunk_list.append(chunk)
    prev_end = curr_end
```

**导师证明这个 `break` 永远不会执行**：

```
prev_end  = (i - step) + chunk_size     # 上一轮留下的
curr_end  = i + chunk_size              # 这一轮算的

curr_end - prev_end = step
```

而 `step = chunk_size - overlap`，前面刚校验过 `overlap < chunk_size`，所以 **`step` 恒大于 0** → `curr_end` 永远大于 `prev_end` → **条件永远为假 → break 永远不执行**。

**这叫死代码**：看起来在防一个边界，实际防不住任何东西。它比"没写"更危险，因为**你会以为自己已经防住了**。

**关键引导**：

> `04-项目架构说明.md` 总共 **772** 个字。当 `i = 750` 时，你的 `curr_end = 750 + 300 = 1050`。
> **1050 这个数是真的吗？文档里第 1050 个字在哪？**
> `i + chunk_size` 是「理论上最多能切到哪」，不是「实际切到了哪」。

#### 轮次 4（最终）：用「实际位置」

```python
chunk = text[i:i + chunk_size]
# 当前块的结束位置，不用curr_end = i + chunk_size，这是理论位置，不是实际位置
curr_end = i + len(chunk)
if curr_end <= prev_end:
    break
chunk_list.append(chunk)
prev_end = curr_end
```

**✅ 通过**。四个测试用例全对，知识库切块结果 `04` 变成 `[300, 300, 272]`（冗余块消失），其余文档不变。

### 坎 4：`build_index` 一条条调 API（性能反模式）

**学生的实现**：

```python
for chunk in chunks:
    embedding = embed_texts(chunk)     # ← 一块一次 HTTP 请求，且传的是 str
    store.add(chunks=[{"source": source, "text": chunk}], vectors=embedding)
```

**实测证据**：

```
索引了 19 个文本块
调用 embed_texts 次数: 19          ← 19 个块 = 19 次 HTTP 请求
每次传进去的类型: {'str'}          ← 传的是字符串，不是 list
总耗时: 3.79 秒
```

**问题 1：丢了批量能力** —— 这正是 `embed_texts` docstring 里提醒过的事：

> 为什么要一批批传（input 是 list），而不是 for 循环一条条调？
> 想想网络往返（RTT）的成本 —— 100 条文本循环调就是 100 次 HTTP 请求。

**学生读了、却写成了反过来的样子。** 真实知识库 3000 个块的话，3000 次往返 ≈ 10 分钟。

**问题 2：传 `str` 给期望 `list[str]` 的参数——能跑通是"碰巧"**

| 巧合 | 为什么没炸 |
|------|-----------|
| `if not texts` | 非空字符串是 truthy，不会误判为空 |
| `input=chunk` | OpenAI SDK **宽容地接受单个字符串**，当成只有一条的批次 |
| `[... for item in resp.data]` | 返回 `[[1024个数]]`，长度 1 |
| `store.add(chunks=[1个], vectors=[[1024个数]])` | 长度 1 == 1，校验通过 |

每个环节都"刚好"对上了，但这不是设计出来的，是撞对的。

**导师还指出**：学生在 `retrieve` 里写对了（`embed_texts([query])`），说明会这个写法，只是 `build_index` 里没保持一致。

**修复后实测**：

```
embed_texts 调用: 1 次        (改前 19 次)
传参类型        : list        (改前 str)
构建耗时        : 0.87 秒     (改前 3.79 秒)  → 快 4.4 倍
```

### 三层追问（第一次）

**第一层 · 白话复述**

> 假设面试官完全不懂 AI。用你自己的话，30 秒说清楚 **RAG 是什么**、**为什么需要它**。

学生回答：

> RAG就是将知识库进行合理切块，然后通过向量化，将每一个块的内容都做成浮点数的二维数组，最后通过向量化的问题和知识库内容进行cos比较，按照-1，0，1的数值大小来判断这两者之间的相似度，从而定位到这个问题在知识库中的答案，需要它是因为它创建知识库之后，检索快且准，并且更新重建成本低，首次创建后，后续检索的性能好

**评判**：

| 项 | 判定 |
|----|------|
| 流程复述（切块→向量化→余弦→定位） | ✅ 正确 |
| 「浮点数的二维数组」 | ⚠️ 小偏差：单个 chunk 的向量是**一维**的（1024 个数），所有块合起来才是二维结构 |
| 「按照 -1、0、1 的数值大小判断」 | ⚠️ 会让人以为只有三个离散值。实际是**连续浮点数**（实测 0.683、0.588），应说"越接近 1 越相似" |
| **「增强 + 生成」环节** | ❌ **完全缺失** |

**导师指出核心缺失**：

> 你描述的是 Retrieval（检索），但 RAG 有三个字母：
>
> ```
> R  Retrieval   检索       ← 你讲的
> A  Augmented   增强       ← 漏了
> G  Generation  生成       ← 漏了
> ```
>
> **检索出来的是一段「原文片段」，不是答案。** 用户问"SSE 正文能不能放换行符"，你检索出的是那 300 字的文档片段——**那是资料，不是回答**。中间缺的那一步：**把检索到的片段塞进 prompt，让大模型基于这些资料重新组织语言，生成回答**，同时告诉用户答案来自哪几篇文档。

**⚠️ 面试风险提示**：面试官听完这个版本，一定会追问"**检索出来之后呢？**"——答不上来，前面的分全丢。

**第二层 · 对比理解**

> **RAG 和微调（fine-tuning）的区别是什么？** 什么场景下必须用 RAG，什么场景下微调更合适？

学生回答：

> 区别在于，微调成本更高，重建成本和更新成本都更高，如果知识库需要频繁更新，则选择RAG，如果知识库永久不更新可以选微调

**评判**：✅ 成本和更新频率抓准了；❌ 漏了三个维度

| 维度 | 微调 | RAG |
|------|------|-----|
| 知识更新 | 要重训（小时~天） | **改个文档就行（秒）** ✅ 答对 |
| 成本 | 高（GPU + 标注数据） | 低（只付 embedding + token） ✅ 答对 |
| **可溯源** | ❌ 答不出"我从哪学的" | ✅ **能给出引用来源** ← 漏了 |
| **幻觉** | 仍会编 | ✅ 有资料约束，显著降低 ← 漏了 |
| **权限控制** | ❌ 做不到 | ✅ 可按用户过滤检索范围 ← 漏了 |
| **适合场景** | 改**风格/格式/语气** | 供**事实知识** ← 漏了 |

**金句（务必记住）**：

> ### 「微调教模型**怎么说话**，RAG 教模型**说什么**。」

补充：学生的答案把它当成二选一（"更新就 RAG，不更新就微调"）。实际上**生产环境经常两个一起用**——微调让输出格式稳定、语气符合业务，RAG 提供实时事实。

**第三层 · 场景应用**

> 你的 demo 现在 `chunk_size=300, overlap=50, k=3`。上线后用户反馈两类问题：
> **(A)「经常检索出无关内容」** **(B)「经常漏掉关键信息」**
> 这两类问题，分别该往哪个方向调？除了调参数，还有哪些优化手段？

学生回答：

> 应该把三个参数往大了调，不知道

**评判**：❌ **方向答反了**

**导师讲解**：(A) 和 (B) 是**相反**的两个病

| | 症状 | 本质 |
|---|------|------|
| **(A)** | 经常检索出无关内容 | **精度**不够（precision 低）→ 想要**更准** |
| **(B)** | 经常漏掉关键信息 | **召回**不够（recall 低）→ 想要**更全** |

**想更准就要更聚焦，想更全就要更宽。这两个目标天然对立**——这是 RAG 里永恒的权衡（precision vs recall）。**不可能靠同一个方向调参同时解决两者。**

正确方向：

| | chunk_size | overlap | k | 为什么 |
|---|:---:|:---:|:---:|---|
| **(A) 检索出无关内容** | **调小** | 调小 | **调小** | 块太大 → 一块混了多个主题 → 向量是"平均值" → 匹配不准 |
| **(B) 漏掉关键信息** | **调大** | **调大** | **调大** | 块太小 → 语义被切碎，"它""这个"没上下文 → 检索到了模型也看不懂 |

**除了调参，还有四种优化手段**（之前只在知识库文档里写过，未在课上直接讲，故本次不重罚）：

| 手段 | 一句话 | 专治 |
|------|--------|------|
| **相似度阈值过滤** | 低于阈值的直接丢弃，宁缺毋滥 | **(A)** |
| **Multi-Query** | 让 LLM 把一个问题改写成 3-5 种不同问法，分别检索再合并 | **(B)** |
| **Reranking 重排序** | 向量检索快速召回 50 条 → Cross-Encoder 精排出前 5 条 | A+B |
| **MMR** | 在"相关性"和"多样性"之间平衡，避免 top-k 全是重复内容 | **(A)** |

> 巧合值得记：**bge-m3 本身就支持三种检索模式**（密集/多向量/稀疏），其中稀疏检索就是**向量检索 + 关键词检索的混合**，也是治 (B) 的手段之一。

## 五、通用方法论沉淀

### 不变量测试（比修 bug 更值钱）

写完任何函数，问自己一句：**「它的输出必须永远满足什么性质？」** 然后把这个性质写成断言。专治"静默错误"：

| 函数 | 不变量 |
|------|--------|
| `split_text` | **所有块必须覆盖全文，一个字都不能少**（轮次 2 的 bug 就是被这条抓住的） |
| `cosine_similarity` | 结果必须在 `[-1, 1]`；`sim(a,a) == 1.0` |
| `load_documents` | **任何输入都不能崩，只能返回 list** |
| `embed_texts` | `len(输出) == len(输入)`，且每个向量维度相同 |

**本次三个 bug 全都能被不变量测试提前抓住。**

### 动笔前先写三个输入输出对

用纸笔（或注释）写出：一个普通情况、一个边界情况、一个反例。

```
'ABCDEFGHIJKL', cs=4, ov=1  →  应该有 4 块，最后一块是 'JKL'
'0123456789',   cs=4, ov=1  →  应该有 3 块，不能有 '9'
'abc',          cs=4, ov=1  →  应该有 1 块，就是 'abc'
```

**有了这三行，就会立刻发现"长度"判不出区别——因为 `'JKL'` 和 `'9'` 都短于 4。** 这个矛盾会逼你找到正确的标准。

面试被问"你怎么保证代码质量"，能说出这个方法，比背任何八股都实在。

### 「修一处坏一处」的模式识别（第三次出现）

| 轮次 | 做法 | 结果 |
|:---:|------|------|
| 1 | 不判断，无脑 append | 冗余块 |
| 2 | 用「长度」判断 | **丢内容**（更严重） |
| 3 | 用「位置」判断，但用了名义位置 | 死代码，回到第 1 轮 |
| 4 | 用「**实际**位置」 | ✅ 通过 |

**根因**：没有先想清楚"正确的判断标准是什么"，就直接开始写代码。
**里程碑 3 也发生过同样的事**（"修好旧 bug，引入新回归"）。

> 面试素材：**能讲出"我发现自己有'修一处坏一处'的模式，于是开始用不变量测试"，比讲任何技术细节都加分。**
