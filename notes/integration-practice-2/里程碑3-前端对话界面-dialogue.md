## 一、教学过程

### 为什么需要它

里程碑 2 的后端已经能真流式了，但那是 `curl -N` 在终端里看到的。**流式输出的价值 90% 在肉眼，10% 在协议**——面试官不会 curl 你的接口，他只会打开页面点一下，然后看回答是"一个个蹦出来"还是"卡三秒砸下来"。

而且这个点有个送命题几乎每场 AI 应用面试都会问：

> "前端接流式为什么用 fetch 不用 EventSource？"

背概念的人说"EventSource 更简单"，做过的人会告诉你：**EventSource 只支持 GET**，而聊天必须把对话内容 POST 过去。所以生产环境的 AI 应用几乎清一色走 `fetch` + 手动解析 SSE。

### 一句话说清楚

不用 `await response.json()` 等全部返回，而是拿着响应体的"读卡器"一块一块地读，每读到一个 token 就追加到气泡里。

### 核心原理

**接水的两种姿势**：

```js
const res = await fetch(url)          // 水龙头已开
const data = await res.json()         // 端个盆接满 → 前端还是"卡三秒砸下来"
const reader = res.body.getReader()   // 拿个杯子，接一杯喝一杯
```

`res.body` 是 `ReadableStream`，`getReader()` 给一个读卡器，每次 `read()` 返回 `{ done, value }`，`value` 是二进制字节块——**和终端里的 `curl -N` 是同一个视角**。

**两个必须处理的"半截"问题**（本技术点真正的难点）：

```
网络给你的块：  ...data: 你\n\ndata: 好\n\ndata: 语
                                        ↑ 这块没切在帧边界上
UTF-8 中文字：  "语" = 3 个字节，这一块可能只给了前 2 个
```

于是要两件事：
1. 解字节带 `TextDecoder` 的 `{ stream: true }`，让它把半个字先留着
2. 切帧要维护**缓冲区**——像快递按"整车"发车，你必须按"包裹"签收：一车可能只装了半个包裹，先攒着，凑齐完整的一个包（`\n\n` 结尾）再签收，剩下的尾巴留到下一车

**任务文件**：`src/integration-practice-2/frontend/app.js`（`index.html` + CSS 由导师提供，学生只写 JS），文件头写明任务清单、验收标准、3 条提示、自测命令。

## 二、验收过程（5 轮迭代）

### 第 1 轮：核心链路正确，但两个致命 bug

**做对的**：真流式增量渲染（实测 40 次 DOM 更新）、`TextDecoder` 的 `stream` 选项、**缓冲区分帧（本技术点最难的一处，学生自己想到了）**、`event:`/`data:`/空行三态解析、`[DONE]` 识别、`app_error` 渲染、空输入拦截、CORS、Enter 发送。

**导师实测发现**：

```
① setAttribute('disabled', false) → 按钮永久锁死
   第 1 次点击：正常。第 2 次点击：毫无反应。
   getAttribute('disabled') === "false"  但  btn.disabled === true

② item.innerHTML += content → AI 回答里的尖括号被当 HTML 解析
   写入：这是 <div>hello</div> 标签，还有 <b>加粗</b>
   textContent：这是 hello 标签，还有 加粗    ← 用户看到的文字变少了，且多出 2 个真实 DOM 节点

③ 多行回答丢内容（后端帧格式错误 + 前端 join("")）
④ !response.ok 静默失败       ⑤ 网络异常静默 + 未捕获 rejection
⑥ 连点 3 次 = 3 个真实请求     ⑦ debugger; 没删
```

**正确答案**：

- `disabled` 是 **HTML 布尔属性**——只要属性存在就是 true，值是什么不管。`setAttribute('disabled', false)` 会把值转成字符串 `"false"`，属性还在 → 依然禁用。要用 **property**：`btn.disabled = false`
- AI 的输出是**外部输入**，`innerHTML` 会解析标签（也是 XSS 面），必须用 `textContent`

### 第 2 轮：修好两个致命 bug，引入一个新的致命回归

**学生改动**：`debugger` 删了、`property` 用对了、`textContent` 对了、`join("\n")` 对了、`try/catch` 加了、`!response.ok` 有提示了、连点防护生效了（3 次点击 = 1 个请求）。

**新回归**：`cooking = true` 提到了函数最开头，但**每条提前 return 的路都没复位**：

```
sendMessage()
  ├─ cooking = true             ← 上锁
  ├─ if (!inputBox) return      ← 没开锁
  ├─ if (!userText)  return     ← 空输入死在这，cooking 永远是 true
  ├─ try { if (!response.ok) { 提示; return } }   ← 没开锁
  └─ catch { 提示 }              ← 没开锁，断网死在这
```

**导师实测**：空输入一次 → 之后所有发送都没反应；断网一次 → 恢复网络后再发也没反应。

**讲解：`try / finally`**

`finally` 是 JS 里唯一"无论走哪条路都会执行"的地方——`return` 绕不过，`throw` 也绕不过。

> **类比**：`finally` 就是那个**守在门口的人**。上锁的人负责锁门，散场时不管你是从正门走、翻窗户走、还是被人抬出去，门都得给你打开——你不需要在每扇窗户旁边安排一个人。

（顺带埋坑：别在 `finally` 里写 `return`，会吞掉 `try` 里本该返回的值。）

**后端帧格式**：`yield f"data: {content}\n\n"` 里 content 含 `\n` 时，一个 `data:` 行塞了多行内容，违反 SSE 规范 → 前端按行切分时，换行后的那一段成了"没有 `data:` 前缀的裸行"，被静默丢弃。

### 第 3 轮：`finally` 用对了，但 `isDone` 放错层级

**学生改动**：`try/finally` 完全正确（两个卡死问题根治）、`isDone = false` 重置了、`if (!isDone)` 挪到了 `while` 循环**之后**。

**导师实测（真实接口）**：

```
首条消息（单行）:  气泡总数 27 = 用户气泡 + 空AI气泡 + 25 个「回答中断，请重试」
首条消息（多行）:  气泡总数 37 = 用户气泡 + 空AI气泡 + 35 个「回答中断，请重试」
第二条消息:        AI 正常渲染（但那是因为 isDone 已经是 true 了的假象）
```

**讲解：信号是有层级的**

| 变量 | 它回答的问题 | 层级 | 一次回答里变化几次 |
|------|------------|------|:---:|
| `cooking` | 当前有没有请求在跑？ | **函数级** | 1 次 |
| `isDone` | 这一次回答说完了没有？ | **流级** | 1 次 |
| `processEvent` | 处理一个事件 | **事件级** | **几十次** |

把**流级**的判断塞进**事件级**的函数里 → 每来一个 token 就问一次"整条流结束了没有？"→ 当然没结束 → 每次都喊"回答中断"。

> **类比**：在电影院里，每放一帧画面就问一次"电影放完了吗？"——没放完，于是**每一帧都播报一次"放映中断"**。正确做法是等片尾字幕出来后问一次。

**后端还差一个字符**：`yield f"data: {line}\n\n"` —— 每一行都补了两个换行，等于**把每一行都变成了一条独立消息**，行与行之间的换行信息就没了。应该是 `data: {line}\n`（行分隔）+ 循环外补一个 `\n`（消息结束）。

### 第 4 轮：两处都改对了，但踩响了一个从第 1 版就埋下的雷

**学生改动**：`isDone` 位置对了（首条消息错误气泡归零）、后端帧格式对了（内容不再丢）。

**导师实测**：内容 45 个字完整到达浏览器，**但渲染出 0 个字**。抓原始 SSE 和网络块边界：

```
原始 SSE 正文:  45 字（完整到达）
第 1 块:  "data: Token\n"
第 2 块:  "\n"                    ← 帧的结束空行，单独一块
第 3 块:  "data:  是\n"
第 4 块:  "\n"
...
第 45 块: "data: [DONE]\n\n"       ← 只有这条碰巧是完整一块
```

**根因**：

```js
while (true) {
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop();          // ← 跨块保住了"半截行"，做对了

    let eventType = "";            // ← 💀 声明在循环里
    let dataLines = [];            // ← 💀 声明在循环里
    ...
}                                   // ← 循环一结束，dataLines 被丢弃
```

**每一个 token 都在"数据行在这一块、结束空行在下一块"之间被清空了。**

**为什么之前没暴露**：网关的切片方式会变。之前它把整帧（或一大批帧）一次给过来，`dataLines` 在同一块里就凑齐空行、当场渲染。这次改成一行一块，就全炸了。**这是最阴的一类 bug：时好时坏，本地跑没事。**

**讲解：同一个知识点的第二次考试**

学生在**行**这一层想明白了（一行可能跨多个网络块 → 用 `buffer` 兜着），但漏了**帧**这一层：一个帧（`data:` 行 + 结束空行）同样可能跨多个网络块。

> **原则：凡是"跨 `read()` 块"的状态，都必须声明在 `while` 循环外面。**
> `buffer` 管半截**行**，`eventType` / `dataLines` 管半截**帧**——它们是同一类东西，得住在同一个地方。

**因果链**：前端这个 bug 从第 1 版就存在；它一直没暴露，是因为后端恰好每个完整帧一次 `yield`。第 4 轮为了修多行而把帧拆成两次 `yield`（`data: X\n` + `\n`），**刚好把前端这个雷踩响了**。

### 第 5 轮：通过

**学生改动**：`eventType` / `dataLines` 提到 `while` 循环外；后端把整个 chunk 的帧拼成一次 `yield`。

**导师实测（全绿）**：

```
① 一块只给一行       → ai[1. 第一行2. 第二行]            ✅ 内容不丢
② 切在字中间         → ai[1. 第一行2. 第二行]            ✅ 跨块拼接正确
③ 一字节一块（极端） → ai[你好\n世界]                    ✅ 连换行都还原了
④ 无 [DONE]          → ai[说到一半] + error[回答中断，请重试] ✅ 中断检测正确
⑤ 空输入后           → 之后还能正常提问                   ✅
⑥ 网络异常后         → 恢复后还能正常提问                 ✅
⑦ 连点 3 次          → 实际发出 1 个请求                  ✅
⑧ 非 2xx（501字）    → error[服务异常 422]                ✅
⑨ 真实接口_单行      → 51 字，27 次增量更新，错误气泡 0    ✅
⑩ 真实接口_多行      → 「1. ...\n2. ...\n3. ...」换行数 2  ✅
⑪ 同页面第二条       → 58 字正常                          ✅
```

### 面试话术沉淀

**问：你的 AI 应用为什么用 fetch 不用 EventSource？**

> EventSource 只支持 GET，而聊天必须把对话内容 POST 过去，还要带 temperature、历史消息，所以生产环境的 AI 应用基本都走 `fetch` + 手动解析 SSE。另外 EventSource 是浏览器自动重连，AI 场景里反而麻烦——你不想让它把同一个问题悄悄重问一遍。

**问：流式接口的边界情况你踩过哪些坑？**

> 三个。第一，**帧边界和网络块边界没关系**：SSE 的一帧是"data: 内容 + 空行"，但网络可能把 `data: xxx\n` 和 `\n` 分成两次给你，所以"行缓冲区"和"帧状态"都必须声明在读取循环外面，否则整个回答会被丢掉。第二，UTF-8 中文字占 3 字节，可能被切成两半，`TextDecoder` 要开 `stream: true`。第三，流式响应头已经以 200 发出去了，出错改不了状态码，只能靠流里的自定义事件 + `data: [DONE]` 终止信号告诉前端。

**问：`[DONE]` 这个哨兵能不能省？**

> 不能。HTTP 状态码在响应开始时就钉死了，浏览器分不清"正常读完"和"连接断掉"——两种情况 `reader.read()` 都返回 `{ done: true }`。所以要在应用层补一个"我说完了"的信号，前端循环结束后检查有没有见过它，没见过就当异常处理。
