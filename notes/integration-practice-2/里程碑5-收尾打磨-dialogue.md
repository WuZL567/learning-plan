## 三、追问对抗：5 道变形题（答案不在文档里，必须推）

### 检测 1：一次 `/chat/stream` 请求，哪些是启动时做好的，哪些是每次请求都要重做的？

**学生答**：✅ 分界答对了（"启动时创建知识库的向量化" vs "请求时接收问题→向量化→检索→过滤→拼 prompt→调 LLM→转 SSE"）。
**缺**：Pydantic 校验、`sources` 帧在调 LLM **之前**发、拒答分支未提。
**最关键的缺失——"所以呢"**：

| | 离线（启动时） | 在线（每次请求） |
|---|---|---|
| 跑几次 | **1 次** | **每个用户每次提问** |
| 慢了会怎样 | 部署时多等 3 秒，**能忍** | **每个用户都慢 3 秒**，并发上来 CPU 直接满 |
| 优化手段 | 分批 + 并发，慢慢跑 | 上 ANN 索引、缓存、减少往返 |

**同一句"3 秒"，放在离线是"能接受"，放在在线是"事故"。**

### 检测 2：知识库里有，但最高分 0.48 < 阈值 0.5 → 拒答了。怎么处理？

**首轮答**：⚠️ 诊断根因对（切块切碎 / 语义鸿沟），但**漏了最关键的一步——先问"这是不是个例"**。
**补考答**：✅ 完整答对。

**正确答案**：

1. **先量化影响面，别凭单个案例动手**：拿正例集跑一遍看分数分布。只有这一个是这样 → **别动阈值**（动了会放进 0.513 那类噪声）；大量正例落在 0.45~0.5 → 阈值确实高了。
2. **核心认知：阈值只有"往哪边错"的选择，没有"不错"的选项**
   - 调低 → 漏检少，但噪声多（0.513）
   - 调高 → 噪声少，但漏检多（本案例）
   - **这就是 precision / recall 的取舍点**
3. **语义鸿沟光调阈值治不了**：切块问题 → 调参数；语义鸿沟（"账号登不上" vs "密码重置流程"）→ **query 改写**；分界带重叠 → 上 **rerank**。

> C11 是"该拒答却答了"，检测 2 是"该答却拒答"——**同一个知识点的正反两面**。

### 检测 3：老板说"直接微调一个模型不就行了"，你怎么讲？

**学生答**：✅ 四个技术要点齐（成本、溯源、更新不便、治幻觉）。
**缺**：① "微调只是修改语气格式"表述偏——微调还能注入知识/压缩成本/固化格式，准确说法是"**微调擅长教「怎么说话」，不擅长可靠注入「会变的知识」**"；② 没换成老板语言。

**老板语言示范**：
> 「**一是钱和时间**：微调要标注数据 + 租 GPU，一次几天、几万起。产品文档每天更新，难道每天重训？RAG 重跑一次向量化，**几分钟、几分钱**。
> **二是责任**：客服答错了谁担？RAG 能给出出处，用户能自己核对；微调答错了，**你连它从哪学的都查不到**。
> 而且不冲突：**要固定话术风格可以微调，要知识准确必须 RAG。**」

**金句**：微调教模型"怎么说话"，RAG 教模型"说什么"。

### 检测 4：`overlap` 改成 290 会怎样？

**首轮答**：⚠️ 现象对了一半（token/context 暴涨），**没答到机制**。
**补考答**：✅ 完整答对（step=10、块数暴涨、引用资料都指向一块地方）。

**正确答案**：题眼是 `step = chunk_size - overlap = 300 - 290 = 10`——**每切一块只前进 10 个字**。

| # | 后果 |
|---|------|
| 1 | **chunk 数量爆炸**：1000 字 → 约 100 块（原来约 4 块）；10 万字 → 1 万块 |
| 2 | **⚠️ top-k 返回同一段话的多个副本**：相邻块向量几乎相同、分数几乎一样，排序后**全挤在前三名**——等于只拿到一条信息，却占了 3 个 context 槽位 |
| 3 | **信号稀释**：prompt 里塞 3 份相同内容 |
| 4 | token 消耗暴涨 |

**隐藏的雷**：`overlap < chunk_size` 校验能过（290 < 300）→ **不报错，静默产生灾难结果**。
**与 4A 的"死代码 break"是同一种危险——防御看起来在，实际防不住。这个模式已踩两次。**

### 检测 5：断线后刷新要能"接着上次位置继续生成"，怎么实现？

**学生答**：⚠️ 方向对（保存位置 + 把已生成内容当上下文续写），但太浅，没碰到核心矛盾。

**正确答案——三道墙**：

1. **状态存哪？** 需要一个**有状态的服务端**，而我的后端是无状态的——**这就是本题的核心矛盾**。存内存？多进程部署就废了。存 Redis？要引入新组件。key 用请求 id 还是 session id？
2. **前端怎么告诉服务端"从哪继续"？** 标准做法是 **SSE 的 `Last-Event-ID`**：给每个 token 帧编 `id:`，浏览器重连时自动带上。
   **——这正是 `EventSource` 自动重连的原生配套设计。** 所以"自动重连是麻烦"的准确说法是：**它给了你断点续传的钩子，但服务端不实现，它就退化成"重新问一遍"。**
3. **LLM 不是确定性的**：把已生成内容发回去续写有两个问题——① 模型接着写**不保证自然衔接**（尤其断在半个词中间）；② **已花掉的 token 钱不退**，续写是二次计费。所以很多产品**选择重新生成**（维护状态的复杂度 > 重新生成的成本）。

**推荐答法（折中）**：缓存已生成内容，重连时**先回放缓存给用户（不重新调模型）**，再继续生成剩下的。只有缓存丢了才降级为重新生成。

## 四、其他批改要点

### 追问预案的订正（首轮暴露的错误）

| 题 | 学生原答 | 正确 |
|---|---------|------|
| A2-3 自动重连 | "算好事"（**与自己的 `app.js` 注释矛盾**） | **麻烦**：静默重发 + `Last-Event-ID` 需服务端实现 + 无状态后端会当成新对话 → **一定会重问一遍** |
| A3-2 10 万条哪里崩 | "向量化先卡住" | **在线检索**：内存（`list[list[float]]` 约 3.3GB）+ O(n) 纯 Python 循环延迟 |
| B6-2 向量长度 | "代表文本多长" | **与文本长短无关**，是训练出来的，语义上无可靠含义 |
| B6-3 何时余弦=欧氏 | "完全一样的句子" | **向量归一化后**（单调等价，故向量库常归一化后只算内积） |
| C9 生产做法 | 第 3 条没写 | 补评测集（`recall@k` / `MRR` / RAGAS）+ rerank + 混合检索 |
| D-2 反问 | "录用我你有什么顾虑" | **有风险**（会当场被列缺点），改问"希望我前三个月解决什么问题" |

### 从代码里挖出的加分点

- **引用卡片在答案下方**（`renderSources` 用 `appendChild`、`renderMarkdown` 用 `item.prepend`）——学生答对了。
  加分讲法：**数据的到达顺序 ≠ 视觉的展示顺序**。`sources` 帧先到，但用户要先看答案再看出处，所以后到的正文用 `prepend` 插到最前面。
- **`VectorStore` 的 docstring 里学生自己写了 HNSW 和"100 万条"的例子**——写代码时懂，面试答不出来，说明**理解没转成话术**。
