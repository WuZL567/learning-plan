# 对话记录：手写 Promise.allSettled

日期：2026-08-17

## 教学过程

### 为什么需要它

你已经写过 all 和 race 了。想想 all 的痛处：**一票否决**。批量请求 5 个接口，只要 1 个失败，整个 Promise 变成 rejected，你连另外 4 个成功的结果都拿不到了——只能走 catch，然后发现根本不知道是哪个挂了。

但真实业务里经常是这种场景：**我需要所有请求的结果，好坏都要**。比如批量上传 10 个文件，你要的是一个列表：哪些传成功了、哪些传失败了、失败原因是什么——然后 UI 上挨个展示。而不是"有一个失败，全部显示失败"。

allSettled 就是为这个场景存在的：**等全班交卷，好坏都记录，绝不整班否决**。

### 一句话说清楚

Promise.allSettled 等所有 Promise 都落定（无论成功还是失败），返回一个数组，每个元素是 `{status: 'fulfilled', value}` 或 `{status: 'rejected', reason}`。

### 核心原理

对比表（all / race / allSettled）：

| | all | race | allSettled |
|---|---|---|---|
| 触发时机 | 全部**成功**才落定 | 第一个落定就落定 | 全部落定（无论成败） |
| 失败处理 | 第一个失败 → 整体 reject，丢弃其余结果 | 第一个失败 → 整体 reject | **永不 reject**，失败记录进结果 |
| 空数组 | resolve `[]` | 永远 pending | resolve `[]` |
| 结果形式 | 值数组 | 单个值 | 对象数组（带状态标签） |

写它的思路和写 all 完全同构，只有两处不同：

1. **不用 reject 分支了**——每个输入项 `.then` 成功写 `fulfilled`，`.catch` 失败写 `rejected`，但两个分支都是往结果数组里填东西，外层 promise 永远只 `resolve`。
2. **所有输入项填完才算完**——需要一个计数器（和 all 一样），但这里计数器减到 0 表示"全部落定"，直接 resolve 结果数组。

类比：all 是毕业答辩的**一票否决制**——一个评委打不过就全组不通过；allSettled 是**记分牌**——每个评委的打分都记下来，最后给你一张完整成绩单。

### 练习任务说明

在 `src/module-01-javascript/1.26-手写Promise.allSettled/index.js` 里实现 `promiseAllSettled`。文件已创建，头部注释写明验收标准和自测用例。

三个边界别漏：空数组、非 promise 普通值、**结果顺序必须跟输入顺序一致**（跟落定先后无关——最容易写错的一点，别用 push，要用下标直接写）。

验收标准：代码跑通、永不 reject、顺序一致、注释用自己的话。

## 验收过程

### 第一次提交（评分 7 分，补一个点）

**学生提交的核心代码**：

```js
function promiseAllSettled(iterable) {
    return new Promise((resolve, reject) => {
        const newArray = Array.from(iterable);
        const result = new Array(newArray.length);
        let count = 0;
        newArray.forEach((item, index) => {
            Promise.resolve(item).then(
                value => { result[index] = { status: "fulfilled", value: value }; count++; },
                error => { result[index] = { status: "rejected", reason: error}; count++; },
            );
        });
        if (count === newArray.length) {
            resolve(result);
        }
    });
};
```

**测试结果**：case3（空数组）✅ resolve `[]`；case1、case2、case4（非空数组）❌ 全部永远 pending，2 秒超时。

**导师追问（原话）**：你的计数器检查 `if (count === newArray.length)` 写在了 forEach 之后的同步代码里，但 `count` 是在 `then` 回调里才更新的。那么问题来了——`then` 回调什么时候执行？是 forEach 跑完之前还是之后？

**学生回答**：无（未作答，直接进入修改环节）。

**评判**：致命 bug。`Promise.resolve(item).then(...)` 的回调是异步微任务，`forEach` 跑完那一刻 `count` 还是 0，检查不成立；之后微任务逐个执行、`count` 涨到 `length` 时，再也不会有人去检查了。正确做法：把 `count === newArray.length` 的检查放进 then 回调内部，每次落定一个就检查一次"这是不是最后一个"。这背后是 1.20 事件循环的知识：同步代码永远看不到微任务回调的成果。

**扣分项**：
- 代码正确性扣 2 分（3分制得1分）：非空数组永远 pending。
- 概念理解扣 0.5 分（4分制得3.5分）：allSettled 语义理解准确，但对回调异步性的认知有漏洞——默认"forEach 结束后 count 已更新完毕"。
- 边界处理扣 0.5 分（2分制得1.5分）：空数组误打误撞对，普通值、保序、失败分支处理正确，但主流程挂了。
- 表达清晰度满分：注释全是自己的话。
