日期：2026-08-18

## 一、教学过程

### 为什么需要它

学生写了 5 年 Vue，`import xxx from 'xxx'` 天天写，但三个问题可能没想过：
1. 为什么 `import` 必须写在文件最顶层，不能写在 `if` 里面？
2. 为什么 webpack/vite 打包后文件变小了？"tree-shaking" 到底摇的是什么？
3. 为什么 Node.js 那边用了几十年的 `require`，反而被 ESM 逐渐取代？

这三点背后都是同一个核心概念：**静态分析**。搞懂它，就同时搞懂了 tree-shaking、循环依赖、还有 ESM 和 CommonJS 的全部区别。面试官问"ESM 和 CommonJS 的区别"，只说"一个用 import 一个用 require"直接扣一半分。

### 一句话说清楚

ESM 是 JS 官方的模块化标准，因为 `import`/`export` 只能写在顶层、结构完全固定，引擎在**运行之前**就能把模块之间的依赖关系全部看清楚（这就是静态分析），由此带来了 tree-shaking、live binding 等特性。

### 核心原理（类比 + 对比表）

**类比：ESM 像"先签合同再发货"，CommonJS 像"现场点单"。**
- **CommonJS（require）是现场点单**：代码跑到 `require()` 这一行，才去加载那个文件、执行它、把结果拿回来。依赖关系只有**运行时**才知道，所以 `require` 可以写在函数里、写在 `if` 里都行。
- **ESM（import）是先签合同**：整个文件的 import/export 关系必须在开头就定死（编译期），所以不能写在条件里。引擎拿到文件先"读合同"，把整个依赖图理清楚，然后再执行。

对比表：

| | CommonJS（require） | ESM（import） |
|---|---|---|
| 时机 | 运行时加载，执行到才加载 | 编译时静态分析，执行前确定依赖 |
| 位置 | 任何地方都能写 | 只能写在顶层 |
| 拿到的东西 | **值拷贝**（require 那一刻的 snapshot） | **实时绑定**（live binding，改的是同一个变量） |
| 浏览器 | 不支持（原本是 Node 的东西） | 原生支持 |
| tree-shaking | **做不到** | 可以做 |
| 循环依赖 | 容易拿到 undefined | 因为绑定是实时的，表现更好 |

**tree-shaking 为什么只有 ESM 能摇？** 因为依赖图在编译期就确定了，打包器（webpack/rollup/vite）可以**静态地**看：`export function a()` 被哪个文件 import 了？没有？那这个函数就是"死代码"，摇掉。CommonJS 不行：`require` 是运行时才执行，打包器根本不知道 require 回来的是个什么玩意儿（可能是对象、函数、变量名还是动态拼接的路径），没法安全地删——删错了运行时就崩。

**live binding（实时绑定）演示代码：**

```js
// counter.js
export let count = 1;
export function add() { count++; }

// main.js
import { count, add } from './counter.js';
console.log(count); // 1
add();              // counter.js 内部把 count 变成了 2
console.log(count); // 2 —— 不是 1！你看到的是同一个变量
```

CommonJS 下 `const { count } = require('./counter.js')` 拿到的是**那一刻的拷贝**，`add()` 之后手里的 `count` 还是 1。ESM 的 import 相当于一个**活的指针**，永远指向源模块里那个变量本身。

## 二、验收过程

### 学生提交笔记的核心内容

**一句话说清楚：** "ESM是JS的模块化标准，固定在顶层使用import/export，因此在JS引擎执行之前就能知道各模块之间的相互依赖关系，这样可以在编译时就知道哪些未被引用的死代码，从而通过tree-shaking摇掉" —— ✅ 抓住静态分析、编译时依赖图、tree-shaking 关联，链路完整。

**核心原理：**
- 静态分析类比："每个仓库都有一张明细表在门口，我只需要在门口看下明细表就知道什么货物在这仓库里，不需要进去转一圈" —— ✅ 讲清"不运行就知道内容"。
- live binding 代码场景：a.js 导出 status 和 switchStatus，b.js import 后 switchStatus() 再打印 status 变 true —— ✅ 正确且证明力强。
- tree-shaking："编译时就知道模块之间的依赖关系，没有依赖关系的就会被删掉" —— 方向对，表述略不精确（准确说法：未被任何模块引用的导出被删）。

**和 CommonJS 的区别：** 写了 6 个维度（加载时机、书写位置、值的传递方式、浏览器支持、循环依赖、能否 tree-shaking），总结"都依赖静态分析特性"。

### 批改发现的问题

1. ❌ **循环依赖表述错误**："ESM编译时就能获取模块之间的依赖关系，并指出循环依赖，而CommonJS则无法识别循环依赖"。
   - 错误一：ESM **不会**"指出循环依赖"——不会报错，循环依赖在 ESM 里照样能跑（只是要小心 TDZ）。
   - 错误二：CommonJS **不是**"无法识别"——Node 完全能跑循环 require，不会报错。
   - 正确区别：两者都能跑循环依赖，区别是拿到什么值——CommonJS 值拷贝，a 没执行完时 b 拿到的是部分导出甚至 undefined；ESM 是 live binding，拿到活的引用，等对方执行完再访问就能拿到真值。一句话记：**循环依赖两边都能跑，区别是"值拷贝 vs 实时绑定"决定了你拿到的会不会是 undefined。**
2. ❌ **第四部分写"暂时没有"**：模板明确要求"写'没有'不算数"。如实写出不确定点比假装全懂更有价值。

### 三层追问（完整问答记录）

**追问一（白话复述）：** 30 秒，用自己的话串一遍：一个 ESM 模块从"被引用"到"被执行"，整个过程发生了什么？重点说"静态分析"发生在哪个阶段、它带来了什么好处？

**学生回答：** "ESM模块通过export暴露变量的引用地址，被另外的模块通过import引入进去，此时这两个模块之间的依赖关系就出来了，编译时就知道这两个模块被引用了，到执行代码时，使用到这个引用变量时，通过引用地址找到原本模块中的原始变量进行使用；静态分析发生在JS引擎读取文件顶部结构时，带来的好处是更快，并且清晰依赖关系，支持tree-shaking；"

**评判：** 主干对 ✅——编译时确定依赖、live binding 引用地址、tree-shaking 都讲到了。小瑕疵："静态分析发生在读取文件顶部结构时"不准——静态分析发生在**代码执行之前**，引擎/打包器只做语法解析和依赖图构建，**不运行任何代码**；"好处是更快"太笼统，核心好处是 tree-shaking 和 live binding。

**追问二（对比理解）：** a.js 和 b.js 互相引用（a require b，b require a），在 CommonJS 里 b 可能拿到什么？换成 ESM 又可能拿到什么？为什么会有这个差别？

**学生回答：** "b可能拿到a也可能是undefined；ESM因为是live binding，所以执行完a之后b可以拿到真的a；因为CommonJS是值拷贝，而ESM是实时绑定；"

**评判：** 基本通过 ✅——方向对，原因（值拷贝 vs 实时绑定）说对，说明笔记里循环依赖的错误已经吸收修正。小提醒：CommonJS 拿到什么取决于 require 那一刻 a 执行到哪了——没执行完就是空壳/undefined，执行完了就是真值。

**追问三（场景应用）：** utils.js 里导出了 add 和 unused 两个函数，index.js 只 import { add }。用 webpack 打包后 unused 还在吗？为什么？如果 utils.js 改成 CommonJS（module.exports）、index.js 改成 require，情况会怎样？

**学生回答：** "还在，因为 import add 时就表示了index和utils的依赖关系了。不知道；"

**评判：** 首次回答"还在"（误以为是问 utils 文件在不在）→ **学生主动澄清：看错题目**。确认题目指"unused 函数"，学生纠正后的回答完全正确：`unused` **会被摇掉**（没有任何消费者，静态分析确认是死代码后删除）；`utils` **模块本身还在**（`add` 仍被引用，模块保留）；CommonJS 下 `require` 只要存在就整体加载，打包器无法静态判断对象怎么被用（如 `utils[something]` 动态访问），**摇不掉**。判定通过 ✅。
- 反思：真实面试中"看错题"没有第二次机会，考官只记"没答上来"。读题先划关键词（"摇掉的是 unused 函数还是 utils 文件"）。
- 追问二第二个问"不知道"已补上：CommonJS 无法摇树的原因（运行时动态加载）。
