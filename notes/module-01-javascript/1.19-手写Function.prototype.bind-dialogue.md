### 为什么需要它

你在 Vue 里写过这种代码吗：

```js
// 事件回调里 this 丢了
const obj = {
  name: '小王',
  sayHi() { console.log('我是' + this.name) }
}
setTimeout(obj.sayHi, 1000) // 1秒后打印 "我是undefined"
```

`obj.sayHi` 传进 setTimeout 时，函数和 obj 分家了，等它执行时 this 指向了全局。

你说：这简单，用 call 解决——`setTimeout(() => obj.sayHi.call(obj), 1000)`。可以，但每次调用都得手动 call，烦。

React 类组件时代你肯定见过更狠的写法：

```js
// 构造函数里
this.handleClick = this.handleClick.bind(this)
```

为什么不在渲染时直接 `onClick={this.handleClick.call(this)}`？因为 call 是**立即执行**，还没点击就触发了。

你需要一个方法：**不立即执行，先把这个函数和 this 焊死，得到一个"带着 this 出厂"的新函数，之后随便什么时候调、谁来调，this 都不会变**。这就是 bind。

### 一句话说清楚

call/apply 是"租借"——当场执行、用完就还；bind 是"买断"——不执行，返回一个永久绑好 this 的新函数，以后任何时候调用 this 都是绑定的那个对象。

### 核心原理

bind 做的事情，本质是**闭包包一层**：

```js
Function.prototype.myBind = function (context, ...bindArgs) {
  const self = this            // 原函数
  return function (...callArgs) {
    // 调用时：绑定参数 + 调用参数 拼起来
    return self.myApply(context, bindArgs.concat(callArgs))
  }
}
```

核心骨架就这么点。但有三个坑，一个比一个深：

**坑1：柯里化传参。** bind 时可以先传一部分参数，真正调用时再传剩下的。`add.myBind(null, 1)(2)` 要返回 3。参数是两次拼接的：`bindArgs.concat(callArgs)`。

**坑2：new 的优先级高于 bind。** 回忆 1.16 学的 this 指向规则——new 绑定 > 显式绑定。所以绑好的函数被 new 调用时，**this 不能是绑定对象，必须是 new 出来的新实例**。

```js
function Person(name) { this.name = name }
const BoundPerson = Person.myBind({ hack: true }, '小王')
const p = new BoundPerson()   // p.name 是 '小王'，而且 this 指向 p，不是 { hack: true }
```

怎么判断"我是不是被 new 调用的"？提示：new 出来的实例，其原型链上能找到原函数的 prototype，可以用 instanceof 判断。

**坑3：原型链继承。** new 出来的实例要通过 instanceof 检查，绑定函数的 prototype 就得继承原函数的 prototype（回忆 1.15 的 Object.create）。

## 二、验收过程（第一次提交）

### 学生提交的代码核心内容

```js
Function.prototype.myBind = function (context, ...args) {
    const originThis = this;
    context = context == null ? globalThis : context;
    if (typeof context !== 'object' && typeof context !== 'function') {
        context = Object(context);
    }
    const bindFn = function (...otherArgs) {
        const truthyThis = this instanceof bindFn ? this : context;
        return originThis.apply(truthyThis, [...args, ...otherArgs]);
    }
    if (originThis.prototype) {
        bindFn.prototype = Object.getPrototypeOf(originThis.prototype);
    }
    return bindFn;
}
```

测试用例：普通绑定（makeFood 例子）、柯里化两次传参、`Math.max.myBind(null, [1,2,3,4,5,6])`（只绑定未调用）。

### 检查发现

**发现1：实际运行输出错误。** 运行 `node index.js` 实际输出：

```
undefined做了红烧肉和麻婆豆腐
undefined做了红烧肉和麻婆豆腐
undefined做了红烧肉和糖醋里脊
```

期望是"老王饭馆做了…"，实际 this 指向了全局对象。

**发现2：new 场景验证失败。** 用学生的实现补测 new 场景：

```
p.name: 小王
p instanceof Person: false (期望 true)
p.sayHi(): TypeError: p.sayHi is not a function (期望 hi 小王)
globalThis instanceof Object: true
```

### 评判与错误分析

**核心 bug：`bindFn.prototype = Object.getPrototypeOf(originThis.prototype)`。**

`Object.getPrototypeOf` 拿到的是原函数 prototype 的**父级**（对 makeFood 来说是 Object.prototype），把原函数 prototype 本身丢了。正确做法是用 Object.create 创建一个新对象，让新对象的原型链上能找到原函数的 prototype。

这个 bug 引发两条连锁故障：

1. **普通调用 this 丢失**：Node 非严格模式下，普通调用 `WangMakeFood('麻婆豆腐')` 时函数内 this 是 globalThis。因为 bindFn.prototype 被设成了 Object.prototype，而 `globalThis instanceof Object === true`（实测），所以 `this instanceof bindFn` 返回 true，被误判成"被 new 调用"，truthyThis 用了 globalThis 而不是老王饭馆。这说明 instanceof 判断 new 的方法依赖 prototype 链设置正确——正确写法下 bindFn.prototype 是 Object.create 出来的新对象，不在 globalThis 的原型链上，普通调用才安全。
2. **new 场景原型链断裂**：`new BoundPerson()` 实例的原型是 bindFn.prototype = Object.prototype，链上找不到 Person.prototype，所以 `p instanceof Person === false`、`p.sayHi` 是 undefined。

**做得对的部分**：
- 闭包包一层、返回新函数的方向正确
- instanceof 判断 new 调用的思路正确（代码结构对，只是 prototype 链设置错导致判断失灵）
- 柯里化参数拼接 `[...args, ...otherArgs]` 正确
- new 时参数拼接正确（实测 p.name === '小王'）
- null/undefined context 处理正确（`context == null`）
- 原始类型装箱处理正确
- 用 apply 传递 this 而不是往 context 上挂临时属性，不污染 context

**测试覆盖问题**：
- new 场景（本次最重要考点）完全没测
- 返回值没测
- null/undefined context、原始类型 context 没测（代码处理了但没验证）
- `Math.max.myBind(null, [1,2,3,4,5,6])` 只绑定未调用等于没测；且该例子本身设计错误——bind 会把数组整体作为单个参数，`Math.max([1,2,3])` 是 NaN
- 注释里写了 ✅ 但实际输出错误，说明没跑过就提交了

**概念注释问题**：
- 只写了"怎么用 instanceof 判断"，没写为什么 new 场景 this 要指向新实例（new 绑定优先级 > 显式绑定，见 1.16）

## 四、课中提问记录

**学生提问：** "在 bindFn 函数中，this instanceof bindFn 中的 this 是不是指调用 bindFn 时的 this？"

**导师解答：** 对，理解完全正确。bindFn 函数体内的 this，就是"调用 bindFn 时的 this"。因为 bindFn 是普通函数（不是箭头函数），它的 this 完全按 1.16 的四条规则动态决定：

| 调用方式 | 函数体内的 this |
|---|---|
| `WangMakeFood('麻婆豆腐')` 普通调用 | globalThis（非严格模式）或 undefined（严格模式） |
| `new BoundPerson()` | new 出来的新实例 |
| `obj.WangMakeFood()` 作为方法调用 | obj |
| `WangMakeFood.call(xxx)` 显式绑定 | xxx |

所以 `this instanceof bindFn` 的意思是："这次调用我的 this，原型链上有没有我的 prototype？" new 调用时 this 是新实例，其原型就是 bindFn.prototype → true；普通调用时 this 是 globalThis，链上通常没有 bindFn.prototype → false。

这也串起了第一次验收的 bug：bindFn.prototype 被错设成 Object.prototype，而 globalThis 的原型链上正好有 Object.prototype（globalThis instanceof Object === true），所以普通调用被误判成 new 调用。prototype 链一设对，判断自然恢复正常。

延伸：为什么 bindFn 不能写成箭头函数？箭头函数没有自己的 this（从外层词法作用域继承），而且箭头函数不能 new，所以必须用普通函数声明，this instanceof bindFn 才有意义。
