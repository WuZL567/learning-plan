# 1.29 ES6 模块化（ESM）原理与特性

## 一句话说清楚

（用一句白话解释 ESM 是什么。提示：抓住"静态分析"这个核心——import/export 为什么必须写在顶层，和这一点带来什么好处）
ESM是JS的模块化标准，固定在顶层使用import/export，因此在JS引擎执行之前就能知道各模块之间的相互依赖关系，这样可以在编译时就知道哪些未被引用的死代码，从而通过tree-shaking摇掉；

## 核心原理

（用类比或图解或对比表讲清楚。提示：这里是重点，要求覆盖以下三个机制）

1. **静态分析**：为什么 import 不能写在 if 或函数里？用"先签合同再发货"或你自己的类比解释。
因为写在顶层是为了编译时就定死各模块之间的依赖关系，等于说我每个仓库都有一张明细表在门口，我只需要在门口看下明细表就知道什么货物在这仓库里，不需要进去转一圈才知道这里有什么货物；
2. **live binding（实时绑定）**：import 进来的变量是"拷贝"还是"活的引用"？想一个代码场景证明它。
ESM通过import进来的变量是引用，主体还在它本来的文件模块里；
// a.js
export let status = false;
export function switchStatus() { status = !status; }
// b.js
import {status, switchStatus} from './a.js';
console.log(status); // false
switchStatus();
console.log(status); // true
3. **tree-shaking**：为什么打包器能删掉没用到的 export？这个能力和 ESM 的哪个特性强相关？
通过ESM的静态分析，编译时就知道模块之间的依赖关系，没有依赖关系的就会被删掉；

## 和 CommonJS 的区别
（至少写 4 个区别点。提示：可以从这几个维度对比——加载时机、书写位置、值的传递方式、浏览器支持、循环依赖、能否 tree-shaking。每个区别都要写清"为什么"，而不是只列现象。建议用对比表）

加载时机：ESM是编译时，而CommonJS是运行时；
书写位置：ESM仅支持在文件顶部使用，而CommonJS则支持任意地方书写；
值的传递方式：ESM是传递了原始值的引用，而CommonJS则是在require那一瞬间的拷贝值；
浏览器支持：ESM支持浏览器，而CommonJS不支持，仅支持Node；
循环依赖：ESM的import是live binding，即使循环依赖，你拿到的也是活的引用，等对方执行完，再访问就能拿到真值，而require 是值拷贝，发生在"那一刻"。如果 a 刚 require b、b 又回头 require a，此时 a 还没执行完，b 拿到的就是 a 的部分导出甚至 undefined；
能否tree-shaking：ESM能通过依赖关系在编译时tree-shaking删除未使用的模块，而CommonJS则无法tree-shaking；
这些ESM的功能都依赖它自身的静态分析特性，意思是引擎编译时就知道模块之间的依赖关系；而CommonJS则无法支持这些功能，它运行时才去读取对应的require，把它当做普通逻辑代码；

## 我的理解中不确定的部分

（诚实写出没完全搞懂的点。提示：比如"live binding 具体在引擎层面怎么实现的"、"动态 import() 为什么不受静态分析限制"、"ESM 在浏览器里的加载过程"。写"没有"不算数）

模块通过export暴露变量的引用，然后其它模块通过import来引入这个变量，在实际逻辑代码中，使用到这个变量时，通过引用地址找到原本的文件中的原始值进行操作。

动态import不写在顶部结构，而是在业务代码中，通过条件判断之后进行决定是否引入，所以编译时无法读取；

ESM在浏览器加载过程不太清楚；
