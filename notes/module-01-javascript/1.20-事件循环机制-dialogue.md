# 对话记录：1.20 事件循环机制

日期：2026-08-13

## 一、教学过程

### 为什么需要它

学生写 Vue 时肯定干过这种事：改完 data 马上去读 DOM，结果读到的是旧值，必须 `await nextTick()`。还有这种经典题：`setTimeout(fn, 0)` 和 `Promise.resolve().then(fn)` 谁先执行？答错的大有人在。

JS 是单线程的——就一个调用栈，同一时刻只能干一件事。但页面又得同时应付定时器、网络请求、用户点击。如果等 fetch 返回期间主线程傻等着，页面直接卡死。所以浏览器搞了一套"排班系统"：主线程先把同步的活干完，异步的活挂到队列里排队，等主线程有空了再按规则取出来干。这套排班规则，就是事件循环。它是理解所有异步行为的底层地图，也是面试 P0 必考题。

### 一句话说清楚

事件循环是浏览器给单线程 JS 排班的调度系统：同步代码先干完，然后优先清空微任务队列，再取下一个宏任务，如此循环。

### 核心原理

用餐厅类比。主厨 = 调用栈，一次只能做一道菜（单线程）。顾客下单 = 调用 setTimeout/Promise 等异步 API。订单本 = 任务队列。主厨永远不会在做菜的途中停下来接单，只有做完手头这道菜（清空调用栈），才去看订单本。

三个角色：

1. **调用栈**：同步代码在这里排队执行，后进先出，函数嵌套就是栈叠栈。
2. **宏任务队列**（Task Queue）：setTimeout、setInterval、I/O、点击事件。**一次只取一个**执行。
3. **微任务队列**（Microtask Queue）：Promise.then/catch/finally、queueMicrotask、MutationObserver。**一次清空全部**——包括清空过程中新产生的微任务，直到队列彻底空。

循环流程：

```
执行一个宏任务（同步代码）
    ↓
清空整个微任务队列（新产生的微任务也一起清完）
    ↓
浏览器可能渲染（宏任务之间、微任务之后）
    ↓
取下一个宏任务，重复
```

两个关键认知：

- **微任务不是"更小的任务"，而是"当前宏任务的收尾工作"**。一个宏任务干完后，它的所有微任务都干完，才算真正结束。
- **渲染插在宏任务之间**。所以如果你在一个宏任务里写死循环，页面连微任务都执行不了，直接冻住。

结合学生熟悉的 Vue：Vue 3 的 `nextTick` 默认就是 `Promise.then`（微任务）。data 变了不立即更新 DOM，而是把组件更新函数塞进微任务队列，等同步代码全跑完再批量更新——一次改 10 个响应式变量，DOM 只更新一次。这也是为什么改完 data 立刻读 DOM 读到旧值。

## 二、验收过程

### 第一轮提交（笔记初版）

**学生笔记核心内容：**
- 一句话说清楚：JS 是单线程，一次只能执行一件事，但浏览器和 node 存在很多异步任务，需要机制协调"同步任务"和"异步任务"执行顺序，这就是事件循环
- 核心原理：写了 4 步文字流程（同步执行完 → 清空微任务 → 取一个宏任务 → 循环），**没有画 ASCII 原理图**，缺调用栈和渲染时机
- 微任务：Promise.then/catch/finally、queueMicroTask、await 后面的代码；宏任务：setTimeout/setInterval、事件监听回调、requestAnimationFrame（**rAF 归错类**）
- 第四部分疑问："为什么会有清空 vs 取一个的差别？"
- 单线程理解："并不是同时，只是执行太快导致感觉是同时的"（**理解错误**）

**初查指出的问题（追问前）：**
1. 原理图没画，流程漏了调用栈和渲染时机
2. requestAnimationFrame 不算宏任务——它有自己的队列，挂在渲染阶段之前执行
3. "单线程却同时处理"不是"执行太快像同时"——定时器计时、网络请求是浏览器别的线程（定时器线程、网络线程）干的，JS 主线程只负责从队列取回调执行

**三层追问：**

第一层（白话复述）："假设你妈问你'事件循环是啥'，用餐厅后厨或银行叫号的类比，30 秒讲清楚。不许用'队列''任务'这些词。"

学生回答："厨师一次只能做一件事，洗菜，切菜，炖汤这三件事，厨师立刻完成洗菜，然后炖汤需要1小时，但是不会等1小时后再去切菜，而是将炖汤交给灶台，自己去切菜，等切菜完了就等待炖汤完成，炖好之后告诉厨师，厨师就拿到回调去执行；"

评判：抓住了单线程 + 异步外包给"灶台" + 回调执行的本质，基本合格。但没讲出"排队"和"循环调度"，后经笔记修订补充了队列概念。

第二层（对比理解）："为什么微任务是清空全部，宏任务是一次取一个？再补一个：同一段 script 里 Promise.then 和 setTimeout 都注册了，Promise 是为什么先执行的？用'整体 script 是第几个宏任务、宏任务结束后先干什么'这条链路讲。"

学生回答（第一轮）："我没理解"——诚实，未答出。

导师给出答案：
- 微任务清空全部：微任务定位是"当前宏任务的收尾工作"，宏任务执行完，名下所有微任务（包括新产生的）必须全部结清才算真正结束。硬性保证：微任务一定在下一个宏任务之前全部跑完。
- 宏任务一次取一个：宏任务之间浏览器要渲染、响应交互。一次清空会一直闷头跑 JS，页面不能重绘不能点击，直接卡死。

学生回答（修订轮）："微任务是宏任务的收尾工作，每一个宏任务执行完之后，先要清空名下所有的微任务才算结束，然后才能开始下一个宏任务。"——微任务半答对；宏任务"一次取一个"的原因仍未答出。

第三层（场景应用）："Vue 里连改 3 次 data.count，然后 await nextTick() 再读 DOM。DOM 更新了几次？如果 nextTick 用的是宏任务（setTimeout）而不是微任务，会出现什么问题？"

学生回答（第一轮）："DOM更新了一次；DOM会渲染更新3次"

评判：第一问对（批量更新合并为 1 次 DOM 树修改）；第二问错——混淆了"DOM 更新"和"渲染"。纠正：
- DOM 更新 = 改真实 DOM 树，Vue 改 3 次 data 只更新 1 次
- 渲染 = 浏览器把 DOM 树画到屏幕，DOM 树改完渲染 1 次
- nextTick 用微任务：回调在渲染之前执行，用户看到画面前能拿到最新 DOM、做测量、再改数据，看不到中间态
- nextTick 用宏任务：回调推迟到渲染之后，用户已看到新画面，回调里再读 DOM 改数据 → 又触发更新+渲染 → 画面闪两下

学生回答（修订轮）："nextTick用宏任务会导致DOM更新时机不对，正常用户更新数据后在界面上看到的是更新后的数据，而使用宏任务时，会在渲染后界面又更新一次，导致界面闪烁。"——修订后理解正确 ✓

**6 道输出题：**

第1题（正确）：
```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
```
正确答案：1 → 4 → 3 → 2。学生答对。

第2题（正确）：
```js
setTimeout(() => console.log('A'), 0);
new Promise((resolve) => {
  console.log('B');
  resolve();
}).then(() => {
  console.log('C');
  Promise.resolve().then(() => console.log('D'));
});
console.log('E');
```
正确答案：B → E → C → D → A。学生答对（微任务中产生的新微任务本轮清空）。

第3题（第一轮错误，修订后正确）：
```js
async function foo() {
  console.log('a');
  await bar();
  console.log('b');
}
async function bar() {
  console.log('c');
}
foo();
Promise.resolve().then(() => console.log('d'));
console.log('e');
```
正确答案：a → c → e → b → d。
第一轮学生答 a → e → c → b → d——把 bar 的 c 当成异步执行。
错因诊断：以为 async 函数调用是异步的。
纠正要点：async 函数第一个 await 之前的代码全部同步执行；await 右侧表达式（bar()）同步执行，await 下一行开始才是微任务。
学生追问："同步代码包括 await 这一行吗？"
导师回答：await 这行拆两半——右边表达式同步执行完、foo 挂起；下一行开始是微任务。延伸：await 右边是 Promise 时要等 settled 才进队列，永远 pending 则后面永不执行；await 普通值会包成 Promise.resolve 再走 then，照样延迟到微任务。

第4题（正确）：
```js
setTimeout(() => console.log('1'), 0);
setTimeout(() => {
  console.log('2');
  Promise.resolve().then(() => console.log('3'));
}, 0);
Promise.resolve().then(() => {
  console.log('4');
  setTimeout(() => console.log('5'), 0);
});
```
正确答案：4 → 1 → 2 → 3 → 5。学生答对（含多宏任务按注册顺序排队）。

第5题（正确）：
```js
console.log('start');
setTimeout(() => console.log('timeout'), 0);
new Promise((resolve, reject) => {
  console.log('promise');
  resolve();
})
  .then(() => console.log('then1'))
  .then(() => console.log('then2'));
console.log('end');
```
正确答案：start → promise → end → then1 → then2 → timeout。学生答对。

第6题（第一轮错误，修订后正确）：
```js
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}
async function async2() {
  console.log('async2');
}
console.log('script start');
setTimeout(function() {
  console.log('setTimeout');
}, 0);
async1();
new Promise(function(resolve) {
  console.log('promise1');
  resolve();
}).then(function() {
  console.log('promise2');
});
console.log('script end');
```
正确答案：script start → async1 start → async2 → promise1 → script end → async1 end → promise2 → setTimeout。
第一轮学生把 async2 放进了微任务（与第3题同错因），修订后正确，理由："await的下一行才是微任务，右侧的表达式还是同步执行"。

### 中途提问记录

**问：setTimeout(fn, 0) 真的是 0 毫秒后执行吗？最短间隔是多少？**

导师回答：
- 不是。0 的意思是"尽快执行"而非"0 毫秒后执行"
- 真实延迟来源一：排队时间——0 只是"计时器到期，回调进宏任务队列"，进队列不等于执行，要等调用栈清空、微任务清完、前面宏任务跑完
- 真实延迟来源二：浏览器钳制——嵌套超过 5 层最小延迟强制 4ms；后台标签页定时器被节流，最小间隔拉长到 1000ms
- 前端意义：定时器只保证不早于、不保证准时；统计时长用 Date.now() 差值或 performance.now()；动画节拍用 rAF（跟着渲染走）
