# 对话记录：手写 Promise.any

日期：2026-08-17

## 教学过程

### 为什么需要它

你已经写过 all 和 race 了。想想 all 的痛处：**一票否决**。批量请求 5 个接口，只要 1 个失败，整个 Promise 变成 rejected，你连另外 4 个成功的结果都拿不到了——只能走 catch，然后发现根本不知道是哪个挂了。

但真实业务里经常是这种场景：**只要有一个人成功，就算赢。**

典型场景：**CDN 资源兜底**。前端加载某个 JS 或字体文件时，同一份资源有多个 CDN 地址（主 CDN、备用 CDN、本地静态目录）。你不用等所有 CDN 都响应，只要**任意一个**能下载成功，页面就用它。这跟 race 不一样——race 是"谁先响应用谁"，但如果先响应的是主 CDN 超时失败，race 整个就 reject 了；你要的是"跳过失败的，继续等下一个成功的"。

还有：**多语言翻译接口降级**、**同时请求多个候选接口谁先返回用谁**。都是"失败不是终点，直到全部失败才算失败"。

### 一句话说清楚

Promise.any 等**第一个成功**的输入项，用它的结果 resolve；如果**全部**都失败了，才 reject，并抛出包含所有失败原因的 AggregateError。

### 核心原理

四兄弟对比表（all / race / allSettled / any）：

| | all | race | allSettled | **any** |
|---|---|---|---|---|
| 落定时机 | 全部**成功** 或 第一个失败 | 第一个落定（不管成败） | 全部落定 | **第一个成功 或 全部失败** |
| 成功时给什么 | 值数组（保序） | 单个值 | 对象数组 | **第一个成功的单个值** |
| 失败时给什么 | 第一个失败原因 | 第一个失败原因 | 永不 reject | **AggregateError（含所有原因，保序）** |
| 空数组 | resolve `[]` | 永远 pending | resolve `[]` | **reject AggregateError** |

**any 和 all 正好是对偶关系**：
- all：成功要**集齐**（全部成功才成功），失败是**一票否决**（第一个失败就整体失败）
- any：成功是**一票通过**（第一个成功就整体成功），失败要**集齐**（全部失败才整体失败）

**写它的思路 = allSettled 的失败收集器 + race 的提前退出**：

```
每个输入项（先 Promise.resolve 包裹）：
  ├─ 成功 → 外层 promise 立即 resolve(该值)   ← 这就是"提前退出"，跟 race 同款
  └─ 失败 → errors[i] = 原因（用下标保序），计数器 +1
             如果 计数器 === 长度 → 外层 promise reject(new AggregateError(errors))
```

三个边界，一个都不能漏：
1. **空数组** → 直接 reject 一个空的 AggregateError（这是四兄弟里唯一空数组会 reject 的，别按 allSettled 的惯性写）
2. **非 Promise 普通值** → `Promise.resolve` 包裹后视为立即成功，直接 resolve 它
3. **errors 保序** → 用 `errors[i] = reason` 按下标写，不能用 `push`（失败落定顺序 ≠ 输入顺序，push 会把顺序打乱，然后你数组长度对了、位置全错）

新面孔 **AggregateError**（ES2021）——它是 Error 的子类，多带一个 `errors` 属性存放原因数组：

```js
const err = new AggregateError(['原因1', '原因2'], 'All promises were rejected');
err.errors    // ['原因1', '原因2']
err.message   // 'All promises were rejected'
```

类比：**海投简历找工作**。你同时投了几十家公司，只要有一家发 offer，你就是"上岸"（any resolve）——失败的拒信先堆在抽屉里，不急着难过；只有当**所有**公司都拒了你，才收到一封总结信，里面列着全部拒信的原因（AggregateError）。

## 验收过程

### 第一次提交（评分 9.5 分，通过）

**学生提交的核心代码**：

```js
function promiseAny(iterable) {
    return new Promise((resolve, reject) => {
        const newArray = Array.from(iterable);
        const errors = new Array(newArray.length);
        let count = 0;

        if (newArray.length === 0) {
            // 直接reject空的AggregateError
            reject(new AggregateError([], "promise is empty!"));
            return;
        }

        newArray.forEach((item, index) => {
            Promise.resolve(item).then(
                value => {
                    resolve(value);
                },
                error => {
                    errors[index] = error;
                    count++;
                    if (count === newArray.length) {
                        reject(new AggregateError(errors, "all promises were rejected"));
                    }
                },
            );
        });
    });
}
```

**测试结果**（全部 ✅）：
- case1：`resolve: 1`（跳过先失败的 Error('a')，取成功的 1）
- case2：`reject: AggregateError = true, errors = ["x","y"]`（保序正确）
- case3：`reject: AggregateError = true, message = "promise is empty!"`（空数组直接 reject）
- case4：`resolve: 1`（普通值直接成功，慢的失败不影响）
- case5：`resolve: fast`（跳过先落定的 'fail'，等 10ms 后成功的 'fast'）

**评判**：全部正确。1.26 两次打回的两个 bug 这次全部规避——计数器检查写在回调内部（`count++` 后紧跟 `count === newArray.length` 判断）、空数组条件方向正确（`length === 0` 才 reject）。保序用 `errors = new Array(length)` 预分配 + 下标写入，是四兄弟里最稳的一次。另外学生正确理解了一个隐蔽点：成功 resolve 后，残留失败项继续 count++ 最终触发 reject 是安全的——promise 状态已定，reject 是 no-op，不会炸。这是对 Promise 状态机（1.22）知识的正确迁移。

**扣分项**：
- 表达清晰度扣 0.5 分（1分制得0.5分）：注释只有"直接reject空的AggregateError"一句描述性注释，没有解释三个关键设计决策——为什么成功分支直接 resolve 就能提前退出、为什么失败分支只攒不 reject、为什么 errors 用下标写而不是 push。面试官问"你这三行为什么不写在一起"时，要能答出理由；注释就是给自己留的答案提纲。
- 其余维度满分：概念理解 4/4（any 语义完全准确：一票通过、失败集齐才 reject）；代码正确性 3/3（五用例全绿）；边界处理 2/2（空数组、普通值、保序、计数器位置全对）。
