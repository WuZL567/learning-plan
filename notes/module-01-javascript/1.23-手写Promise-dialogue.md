### 一句话说清楚

手写 Promise 就是把 1.22 学的那张状态机图，翻译成一个 class：存状态、存值、存回调，then 负责"排队或执行"，resolve 负责"解锁发牌"。

### 核心原理

一个 Promise 对象内部只需要装四样东西：

```
状态(status)   值(value)   失败原因(reason)   回调队列(callbacks)
```

整个实现就是三件事：

**① resolve/reject 是"锁"** —— 只有 PENDING 状态能开门，开门后状态立刻上锁。`resolve(1)` 再 `reject(2)`，第二个进来发现锁已经开了，直接无视。这就是状态不可逆。

**② then 是"排队"** —— then 被调用时，状态可能是 PENDING（比如 setTimeout 里才 resolve）。这时候回调不能执行，只能先存进队列，等 resolve 开门时再依次取出来执行。这就是为什么异步 resolve 场景回调也能跑。

**③ then 返回新 Promise 是"接力"** —— 每个 then 内部 new 一个新的 MyPromise 返回。回调的返回值决定新 Promise 怎么开门：return 普通值就 resolve(它)；return Promise 就跟随它（它 resolve 我再 resolve——这就是值解包）；throw 就 reject(它)。链就是这么一环扣一环接起来的。

再加一个细节：回调要异步执行。真实 Promise 的 then 回调进微任务队列，手写版用 `setTimeout(fn, 0)` 模拟（学生实际用了 queueMicrotask，更精准，加分），保证 then 回调不抢在同步代码前面跑。

### 验收标准

5 个用例：
1. 链式调用：`resolve(1).then(v => v + 1).then(v => v + 1)` 最终输出 3
2. 状态锁定：resolve(1) 后再 reject(2)，最终状态 fulfilled、值 1
3. 异步 resolve：setTimeout 里才 resolve，then 回调仍能拿到值
4. 错误传递：then 里 throw，链尾 catch 接住
5. 状态跟随：then 里 return 新 MyPromise，链上拿到它的 resolve 值

## 补充复习（验收后，学生要求逐行讲解）

### 逐行讲解核心（8 个代码块）

1. 三状态常量：防拼写错误。
2. constructor 四个属性：status 标签、value/reason 货物、双册子（登记册）——解决"then 先调用、resolve 后发生"。
3. resolve/reject 四步：锁检查（`status !== PENDING` return）→ 换标签 → 存货 → forEach 照册子打电话。箭头函数钉住 this（第一轮踩的坑）。
4. executor 同步执行，try/catch 包住：executor 抛错等价 reject。
5. then 开头参数透传：`v => v` 值穿透、`e => { throw e }` 错误穿透——错误穿透的实现就藏在这两行。
6. handleFoo：闭包记住 res/rej；queueMicrotask 延迟执行 callback（try/catch 写在微任务内部才能捕到 callback 的错）；循环引用检查；值解包分支（result instanceof MyPromise ? result.then(res, rej) : res(result)，状态跟随的机械实现）。
7. 三分支：已 fulfilled/rejected 立即 handleFoo；pending 则塞包装层入册（塞包装层保证唤醒时值是最新的）。
8. catch = then(null, callback)；finally 成功返回原值、失败重新 throw 原错误；静态 resolve 对已有 Promise 短路返回。

### 综合例子走读（时间线 + 状态快照）

例子：`new MyPromise(res => setTimeout(() => res(1), 0)).then(v => v + 1).then(v => v + 1).then(v => { throw new Error('boom') }).catch(e => console.log('捕获:', e.message))`

步骤 1-4（同步阶段）：p pending、executor 挂 setTimeout 宏任务；①②③④ 依次被调用，各自的包装层入各自主人的册子（③ 的 newPromise3 两本册子各塞一张：fulfilledList 塞透传包装层、rejectedList 塞 catch 包装层 D）。
步骤 5（宏任务）：resolve(1) 开锁、换标签、存货、照册子打电话 → handleFoo 挂微任务 M1。
步骤 6-7（微任务 M1/M2）：callback 返回普通值 → res(2)/res(3) 接力 → 下一棒开锁 → 打下一个电话。
步骤 8（微任务 M3）：callback throw → handleFoo 内 try/catch 接住 → rej(boom) 锁死 newPromise3 → 照 rejectedList 打电话唤醒 D（fulfilledList 里落空的册子永远不唤醒）。
步骤 9（微任务 M4）：catch 回调打印"捕获: boom"。

核心三句话：then 只负责登记（pending 入册）或挂微任务（已定状态）；resolve/reject 只负责开锁 + 照册子打电话；handleFoo 只负责拿返回值决定 next 是 res 还是 rej。

### 追问 1：③ 里 throw 的错，为什么能被 ④ 的 catch 接住？

学生回答（第一版）：③ 的 onFulfilled 是 throw 函数，handleFoo 中执行 callback 时通过 try/catch 捕获，走了 rej(e)。

评判：只答对第一跳，漏了第二跳。补讲错误三连跳：callback throw → handleFoo 的 try/catch 接住 → rej(e) 锁死 newPromise3（rejected）→ newPromise3 照 rejectedList 打电话 → ④ 的包装层 D 醒来 → catch 回调执行。关键理解：错误不是"跳"到 ④ 的，是"落"到 newPromise3 头上，再顺着登记册"流"到 ④ 的。每个 then 返回的新 Promise 都是错误路上的中转站，rejected 是转发指令，rejectedList 是转发表。

### 追问 2：② 和 ③ 之间插一个空 then()，③ 的错还能到 ④ 吗？

学生回答：能到，then 函数一开始会做处理，如果不是函数则透传，所以会往下走，而 then() 则透传了 v => v 和 e => { throw e }。

评判：✓ 完全正确。错误穿透的机械实现——每个中转站都在转发，直到有人接。
