# 对话记录：1.30 ESM 与 CommonJS 的核心差异

日期：2026-08-18

## 一、教学过程

### 为什么需要它

你刚学完 1.29 的 ESM 原理，但面试官不会单独问 ESM——他一定会问"ESM 和 CommonJS 有什么区别？"，而且要求你从加载方式、值传递、循环依赖三个角度答。

这个对比能答好，说明你真懂了模块系统的本质。你 5 年 Vue 经验里其实两种模块都见过：webpack.config.js、老的 Vue 2 脚手架里全是 module.exports，而 Vite 项目、组件文件里全是 import。只是你以前没想过为什么 Node 老项目用 require，新项目用 import——这节课就是把这个"以前没想过"补上。

### 一句话说清楚

ESM 是"先看完整菜单再点菜"（编译时静态分析），CommonJS 是"边做菜边加菜"（运行时逐行执行），这个根本差异导致了两者在值传递和循环依赖上的表现完全不同。

### 核心原理

核心就抓三组对比，先讲透每组里的"为什么"，面试时按这个顺序答就行。

#### 对比一：加载方式——静态 vs 动态

```
ESM（静态）：   import 必须写在顶层 → 引擎执行代码前就把整个依赖图建好了
CJS（动态）：   require 是普通函数调用 → 可以写在 if、函数里，执行到才加载
```

为什么 require 能写在条件里而 import 不行？因为 require 就是一个函数，它内部做的事情是"读文件 → 执行模块代码 → 返回 module.exports"，这套动作发生在运行时。而 import 是语法，引擎在编译阶段就要解析出依赖关系，所以必须放顶层。

顺带的推论：ESM 能被 tree-shaking（1.29 学过），CJS 不行，根源就是静态分析这个能力。

#### 对比二：值传递——活的绑定 vs 快照拷贝

```js
// CJS：require 拿到的是"那一刻的快照"
// counter.js
let count = 1;
module.exports = { count };
setTimeout(() => { count = 2; }, 1000);

// main.js
const { count } = require('./counter');
console.log(count);          // 1
setTimeout(() => {
  console.log(count);        // 还是 1，模块内部已经变 2 了，但你手里的还是旧值
}, 1500);
```

```js
// ESM：import 拿到的是"活的引用"
// counter.mjs
export let count = 1;
setTimeout(() => { count = 2; }, 1000);

// main.mjs
import { count } from './counter.mjs';
console.log(count);          // 1
setTimeout(() => {
  console.log(count);        // 2！实时反映模块内部的变化
}, 1500);
```

为什么：CJS 的 module.exports 是一个对象，require 时把对象返回给你，你解构出的 count 是对象上那个属性的值拷贝——它只是"那一刻"的 1，之后模块内部把变量重新赋值，跟你手里的旧值没关系。而 ESM 的 export 声明了"这个变量是公共出口"，import 处通过 live binding 直接绑定到模块内部的变量本身，所以内部一变，外部立刻能感知。

#### 对比三：循环依赖——经典坑 vs 优雅处理

```js
// CJS 循环依赖：谁先被 require，谁吃亏
// a.js
const b = require('./b');
console.log('a 里访问 b.foo:', b.foo);   // undefined！
exports.foo = 'a的foo';

// b.js
const a = require('./a');
console.log('b 里访问 a.foo:', a.foo);   // 正常 'a的foo'，因为 a 先执行完了
exports.foo = 'b的foo';
```

执行流程：node a.js → a 执行到 require('./b') → b 开始执行 → b 执行到 require('./a') → 发现 a 正在执行中，直接返回 a 的"半成品" module.exports（此时 a 还没执行到 exports.foo 那行）→ 所以 b 拿到的 a.foo 是 undefined。

为什么 ESM 能优雅处理？两个原因叠加：第一，ESM 的依赖图在编译时就完整建好了，执行顺序被安排成"深度优先、谁被依赖先执行谁"，不会出现"执行到一半才发现对方也要加载"的情况；第二，live binding 保证你访问的是活的引用，所以只要在对方模块执行完之后再访问，就能拿到真值。

```js
// ESM 循环依赖：安全，只要访问时机在对方执行完成之后
// a.mjs
import { b } from './b.mjs';
export const a = 'a的foo';
console.log('a 里访问 b:', b);   // 'b的foo'

// b.mjs
import { a } from './a.mjs';
export const b = 'b的foo';
console.log('b 里访问 a:', a);   // TDZ 报错
```

#### 其他小差异

| 维度 | ESM | CJS |
|---|---|---|
| 浏览器 | 原生支持 | 不支持（需要打包器） |
| 顶层 this | undefined | module.exports |
| 严格模式 | 自动开启 | 需要手动 "use strict" |
| 异步 | 支持 import() 动态导入（返回 Promise） | require 同步读取 |

### 教学纠错（教学过程中发现的示例错误）

教学时给出的 ESM 循环依赖示例注释"b 模块先执行完，这里能拿到 'b的foo'"有误。学生提问触发验证，实测 node a.mjs 与 node b.mjs 两种入口都会报 TDZ 错，只是报错位置不同。导师当场纠正：环上总有一个模块先执行，先执行的模块在顶层访问对方（对方未初始化）必报 TDZ。教学结论修正为：顶层立即访问必炸一个；把访问延迟到函数内部（双方都执行完后再调用），live binding 才能拿到真值。

## 二、验收过程

### 学生提问与导师解答（完整记录）

**学生问**：// ESM 循环依赖：安全，只要访问时机在对方执行完成之后 …这里为什么呢？是因为node a.mjs了吗？如果node b.mjs呢？

**导师答**（经实际运行验证）：两种入口都会报错，只是报错位置不同：
- node a.mjs：b 先执行 → b 访问 a（a 未初始化）→ b.mjs 报 Cannot access 'a' before initialization
- node b.mjs：a 先执行 → a 访问 b（b 未初始化）→ a.mjs 报 Cannot access 'b' before initialization

规则：ESM 求值顺序是"深度优先 + 后序"——执行一个模块前先把它所有依赖执行完，遇到正在执行中的（环）跳过。所以不是入口选谁的锅，环上总有一个模块先执行，先执行的那个顶层碰对方必炸。

安全模式：把访问推迟到函数内部（运行时），等双方模块都执行完，live binding 就能拿到真值。实测 safe 版本输出：b 模块执行完 → a 模块执行完 → a 延迟读 b: b的foo → a 延迟读 a(来自b): a的foo，零报错。

总结：CJS 对循环依赖是"忍着给半成品"，ESM 是"要么报错、要么给真值"。

**学生问**：node safe-a.mjs 输出（正常运行，零报错）…这里是怎么处理的？为啥node a.mjs时会先执行完b呢？

**导师答**：规则只有一条——执行一个模块前，先把它的所有依赖全部执行完，遇到正在执行中的模块（环）就跳过。"开会点名发言"类比：a 说"我依赖 b"→ 引擎叫 b → b 说"我依赖 a"→ a 正在排队（求值中），不重复叫 → b 先发言完毕 → 轮回 a。

safe 版关键：顶层不再"读取"对方的值，只"声明函数"；函数体的代码到调用时才真正执行。三个机制叠加：① 函数体延迟执行；② live binding 实时取值（调用时直接到变量"活地址"上取当前值，与 import 写在哪个文件无关）；③ 求值顺序确定（深度优先后序保证被依赖者先执行完）。类比：live binding 像微信转账余额实时可见；CJS 快照像打印好的纸质账单。

布置验证任务：把 safe-b.mjs 顶层加一行 console.log('b 顶层读 a:', getAFromB())，跑 node safe-a.mjs，验证"函数体 + 调用时机晚于对方初始化，两者缺一不可"。

4 处需要修改：
① ESM 值传递代码跑不通（硬伤）：export count; 语法错误、this.count 在 ESM 顶层是 TypeError。应改为 export let count = 0; setTimeout(() => { count = 10; }, 1000);
② CJS 的 exports 机制理解错："exports 是拷贝值"归因错误。事实：module.exports 是一个对象，require 返回的是这个对象的引用，不是拷贝。拷贝发生在"把值放进对象的那一刻"，不是 require 那一刻。模块内部写 module.exports = { count } 是把当时的值塞进对象；之后 count = 10 只是改模块作用域变量，没更新对象。
③ 循环依赖"谁报错"表述颠倒：准确表述是"先执行的那个模块（对方还没初始化）在顶层访问就报错"。
④ .js 默认模块系统答错："以前 CJS 现在 ESM"是错的。.js 的类型由 package.json 的 "type" 字段决定：type: "commonjs"（或没写）→ CJS；type: "module" → ESM。默认依然是 CJS。

### 三层追问（完整问答记录）

**第一层 · 白话复述**：用你自己的话，30 秒说清——CJS 里 require('./counter') 拿到的到底是一个"拷贝"还是一个"对象的引用"？为什么模块内部变量变了、解构出来的还是旧值？

**学生答**：是一个对象的引用，拷贝发生在模块中把值放进对象中的那一刻，而不是require函数执行的那一刻；模块内部变量变了只是改变了这个作用域中的变量，而不是更新了对象，所以解构还是旧值。

**评判**：✅ 通过。把"拷贝的时机"讲清楚了——这是 90% 的人说不清的点。

**第二层 · 对比理解**：还是你笔记里那个 a/b 互引的例子——node a.js 和 node b.js 两种入口，执行顺序分别是什么？CJS 里谁会拿到 undefined？ESM 里谁先执行、谁报 TDZ 错？

**学生答**：node a.js在CJS中，先执行a，然后碰到require b模块，转而执行b，在b模块中遇到require a，暂时跳过，继续执行b，执行完之后再执行a，所以此时b模块中会先拿到a，此时是半成品，则打印undefined；node b.js则相反；node a.mjs在ESM中，先执行a，碰到import b时，进入b模块执行，又遇到import a模块，此时跳过，继续执行b，打印时没有a变量，所以此时b模块TDZ报错；node b.mjs则相反；

**评判**：✅ 基本通过。一个用词修正：CJS 里遇到 require(a) 不是"跳过"——跳过是 ESM 的机制（求值阶段发现模块正在求值中，不重复求值）。CJS 是：Node 的模块缓存里已有 a 的"半成品 module 对象"（正在执行中），require 直接把未完成的 module.exports（空对象）返回给你——它没有跳过，它给了你一个未完工的货。

**第三层 · 场景应用**：你的 Vue 3 + Vite 项目里，vite.config.js 是个 CJS 文件，但代码里你用 ESM 的 import 语法——这是怎么回事？Vite/打包器为什么能"假装"它是 ESM？Node 直接跑 .js 和 Vite 跑 .js，判断模块类型的依据一样吗？

**学生答**：不知道，我猜测是因为vite或打包器会通过插件将js转成mjs来执行；然后node那边通过type：module来判断模块的类型是不是ESM；

**评判**：⚠️ 部分对。Node 侧（type 字段判断）✅ 正确；Vite 侧猜偏了。正确答案：
- 核心认知：源码里写 import ≠ 运行时就是 ESM。打包器是"翻译官"：读源码时按 ESM 语法解析（拿到静态依赖图做 tree-shaking），执行和输出时可以转成任何格式。import 是"书写格式"，和"执行环境"是两码事。
- Vite 加载 vite.config.js：内部用 esbuild 预打包配置，CJS 配置会被打包后以 ESM 形式加载，所以配置里写 import 也能跑。关键不是"转成 mjs"，而是"打包器有自己的模块解析体系，配置文件的加载方式是打包器说了算，不归 Node 管"。
- webpack 读 webpack.config.js：按 CJS 读（module.exports = {...}）；webpack 5 支持 ESM 写法但会先额外构建一次。
- Node 直接跑 .js：由 package.json 的 type 字段决定。
