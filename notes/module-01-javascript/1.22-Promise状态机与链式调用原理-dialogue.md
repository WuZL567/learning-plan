# 对话记录：1.22 Promise 状态机与链式调用原理

日期：2026-08-14

## 教学过程

### 为什么需要它

你刚学完事件循环，知道 setTimeout 是宏任务。现在想象一个场景：你封装了一个 `getUserInfo` 接口，它依赖 `getUserId`，而 `getUserId` 又依赖登录接口。用回调写，就是经典的回调地狱——三层嵌套起步，错误处理要在每一层都写一遍 `if (err)`，代码像楼梯一样向右斜着长。

你在 Vue 项目里天天用 `axios.get().then()`，但你可能没深究过：`.then()` 为什么能一直链下去？为什么 `.catch()` 写在最后也能接住前面任意一步的错误？Promise 官方定义为"异步操作的结果"，但面试官真正想听的是：**它是一个状态机**。

### 一句话说清楚

Promise 就像一个外卖订单：下单后状态是"配送中"（pending），最后只会变成"送达"（fulfilled）或"取消"（rejected）二选一，而且一旦定了，永远不能再改回配送中。

### 核心原理

**1. 三态单向流转**

```
        resolve(value)
pending ────────────────► fulfilled (成功)
   │
   │ reject(reason)
   └─────────────────────► rejected  (失败)
```

两个关键点：
- **只能从 pending 走向 settled**（fulfilled 或 rejected），不能反向，也不能在 fulfilled 和 rejected 之间横跳。`resolve(1)` 之后再调 `reject(2)`，后面的 reject 直接被忽略。
- 状态的改变是"第一次调用生效，后面全部无效"。

**2. then 为什么能链式调用**

核心一句话：`then` 返回的是一个**新的 Promise**，不是你原来的那个。就像接力赛，每一棒都是新的人，但传递的是接力棒（数据）。

新 Promise 的状态由 then 回调的**返回值**决定，规则就一条，类比为"你处理完订单后说了什么"：

| 回调里做了什么 | 新 Promise 的状态 |
|---|---|
| `return 普通值` | fulfilled，值为该普通值 |
| `return 一个 Promise` | **跟随**那个 Promise 的状态和值（状态传递） |
| 抛异常 | rejected，异常为 reason |
| 什么都不写 | fulfilled，值为 `undefined` |

**3. 错误穿透**

`reject` 会沿着 `.then()` 链一路往下找，跳过所有只写了 onFulfilled 的 then，直到遇到 `.catch()` 或 then 的第二个参数 onRejected。所以 `.catch()` 写在最后能接住前面任意一环的错。

**4. 和 1.20 的衔接**：then 的回调进的是**微任务**队列，这也是为什么 `Promise.resolve().then()` 永远排在 `setTimeout` 前面执行。

### 补充讲解：catch 和 then 的第二个参数的区别

catch 本质就是 `.then(undefined, onRejected)` 的语法糖，但两者的"管辖范围"不一样。

then 的第二个参数 onRejected，只负责上一个 Promise 的 reject，不管同一个 then 里 onFulfilled 抛出的错。就像包裹的本人签收——他只管自己的包裹有没有送来，不管别人转交给他的包裹弄丢了没。

catch 站在链的后面，管的是它前面所有环节没被处理的错误。就像物业代收点——链上任何一步出了错没人管，最后都归它兜着。

| | then 的第二个参数 | 链尾的 catch |
|---|---|---|
| 管谁 | 只上前一个 Promise 的 reject | 前所有环节的 reject 和抛错 |
| 能接住同级 onFulfilled 抛的错吗 | ❌ 不能 | ✅ 能 |
| 处理完 reject 后 | 错误被消化，链恢复 fulfilled 继续走 | 同样消化，后面再接 then 也能走 |

什么时候用 then 第二参数？极少。只有当你想"为某一个具体步骤单独处理失败、处理完还继续走链"时才用。日常统一用链尾 catch 兜底。
