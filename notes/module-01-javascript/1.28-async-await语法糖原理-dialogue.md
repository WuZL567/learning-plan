## 一、教学过程

### 为什么需要它

学生刚手写完成 Promise 四兄弟（all / race / allSettled / any）。面试官在 Promise 专题的最后一击通常是："async/await 底层是怎么实现的？它跟 Generator 有什么关系？" 这是陷阱题——很多人写了三年 async/await，却以为它天生就有。实际上 async/await 是 2017 年加进 JS 的语言特性，底层就是 Generator + Promise 自动执行器，执行器最早来自 co 库（TJ 写的）。把它当语法糖理解，一次答出：语言演进、设计思想、底层实现。

### 一句话说清楚

async/await 就是把"用 Generator 写异步 + 用自动执行器驱动它"这套手工流程，包装成语法，让语言自己干。

### 核心原理（类比 + 代码）

**第一块：Generator —— 能暂停的函数。** 普通函数像自动售货机，一口气跑完。Generator 像手动挡汽车：`next()` 踩油门走一段，`yield` 是刹车。每次 `next()` 只跑到下一个 `yield` 就停。Generator 函数加括号不会执行函数体，需要调用 next() 才真正跑。演示代码（manualCar 汽车类比、runner 跑步传值）。

**关键点：yield 是双向通道。** `yield 值` 交出值放进 next() 返回的 `{value, done}` 里；下一次 `next(参数)` 的参数成为这个 yield 表达式的值，赋给左边变量。demo：cashier 收银员例子。

**第二块：自动执行器（co）。** Generator 要手动反复 next()，于是有自动执行器：

```js
function run(gen) {
  const g = gen();
  function step(arg) {
    const res = g.next(arg);
    if (res.done) return res.value;
    Promise.resolve(res.value).then(step);
  }
  step();
}
```

yield 一个 Promise → 等它 resolve → 把值传回 yield 的位置 → 继续走到下一个 yield → 再等 → 再传，直到 done。类比：co 是"自动读档器"，Generator 是游戏（会存档、等你读档）。

**第三块：async/await 语法糖。** 把 run 内置进语言，yield 换 await、function* 换 async function。语言版额外内置三件事：错误处理（throw 自动抛给外层 try/catch）、返回值包装（async 函数永远返回 Promise）、非 Promise 值包装（await 普通值自动 Promise.resolve）。

## 二、验收过程

### 补充教学 1：学生对 Generator 整体没理解

**学生：** "这部分我还是没有理解，毕竟我都不理解你说的Generator和yield以及next这些。"

**教学回应：** 承认跳太快，单独把 Generator 讲透，不讲 async/await：
- 普通函数 = 自动售货机；Generator = 手动挡汽车。next() 踩油门走一段，yield 刹车停住。
- 关键点一：manualCar() 加括号不执行函数体，只造"可驾驶实例"，要 next() 才跑。
- 关键点二：每次 next() 只跑到下一个 yield 就停。
- 用 node 跑 manualCar 演示输出：起步 / 换2挡 / 到终点，三行分别对应三次 next()。
- 第二个关键点：yield 是双向通道。yield 左边的变量收到的是下一次 next() 传的参数（不是这一次）。用 runner 例子 + node 演示：
  - `{ value: '第一圈跑完', done: false }`
  - `我收到了: 一瓶水` / `{ value: '第二圈跑完', done: false }`
  - `我收到了: 一条毛巾` / `{ value: '全程跑完', done: true }`
- 总结：Generator = 手动挡的车。next() 踩油门，yield 刹车；刹车可交出去一个值，下次踩油门可带一个值回来。每次 next() 返回 { value: 交出去的值, done: 是否跑完 }。
- 布置小练习：makePizza 例子，先预测输出再看实际输出。

### 补充教学 2：学生对执行流程还不清楚

**学生：** "这里还是没搞清楚，怎么打印的，打印了什么，yield是会返回和接受吗？next是返回什么？逐步带我过一遍"

**教学回应：** 用 cashier 例子逐步走查四次调用：
- 大前提：p.next() 被调用时函数才往前跑；yield 一出现函数立刻停住等下一次 next()。
- A行 makePizza()：什么都没发生，函数体没跑，没有打印。Generator 加括号不执行函数体。
- B行 console.log(p.next())：先执行 p.next() → 打印"开始和面" → 遇到 yield '面团好了' 交出、暂停（topping 还没赋值）→ 返回 { value: '面团好了', done: false } → 外层打印。
- C行 next('芝士')：从暂停点恢复，'芝士' 成为 yield 值 → topping = '芝士' → 打印"收到配料: 芝士" → yield '放入烤箱' 暂停 → 返回 { value: '放入烤箱', done: false }。
- D行 next('烤10分钟')：oven = '烤10分钟' → 打印"收到指令: 烤10分钟" → return '披萨出炉' → 返回 { value: '披萨出炉', done: true }。
- 回答三个问题：① 打印分两种（函数体打印 和 外层打印 next() 返回值对象），交替出现；② yield 双向：交出（进 {value}）收进（next 参数成为 yield 表达式的值）；③ next 每次返回 { value: 本次 yield 交出的值或 return 的值, done: 是否结束 }。
- 核心一句话：yield 停住、把东西交出去；下一次 next(参数) 把它唤醒、把参数收进来。

### 小测验：学生手动写输出

**题目：** cashier 收银员代码（三次 next：无参 / 10 / '雪碧'），写出完整屏幕输出。

**学生回答：**
"第一个c.next走到yield '请付钱'暂停，外部打印：{value:'请付钱',done:false};
第二个c.next(10)从money恢复，传入的10给到了money，所以函数体打印：收到10元，走到yield '可乐还是雪碧？'暂停，外部打印：{value:'可乐还是雪碧？',done:false};
第三个c.next('雪碧')从drink恢复，传入的雪碧给到drink，所以函数体打印：给你一杯雪碧，走到最后return结束，外部打印：{value:"欢迎下次光临",done:true};"

**评判：** 完全正确 ✅。node 验证输出与答案一字不差。特别表扬：注意到第一、二次 next() 没有函数体打印——说明理解了"yield 只是交出值不打印"，暂停点意识准确。

### 补充教学 3：yield 后面放 Promise + 自动执行器

- yield 后面改交 Promise：`const user = yield fetchUser()` 写起来像同步赋值，实际等异步结果回来才拿到。类比：取号排队，yield 是取号，窗口叫到（Promise resolve）才办事。
- 大麻烦：谁来做"等 Promise 完成 → 把结果传回"？3 个异步步骤要手动写 3 次。于是有自动执行器 run(gen)，把"拿到 Promise → 等 resolve → 传回 → 继续"自动化循环。
- 任务：把 run(gen) 跑起来驱动 login Generator，看"你好 张三"和订单数打印出来。

**学生理解 run 函数：**
"我理解了run函数，传入的gen函数是login，在内部会创建g这个实例，然后创建内部函数step，调用g的next；第一次主动执行的step，没有传参数，所以res就是第一次的fetchUser的promise，res获取到的next返回的是{value: promise, done:false}，此时判断如果done是true就直接结束了，否则就是resolve这个promise，然后继续用step函数，传入的就是这个promise的值:{id:1,name:"张三"}，此时继续走step，知道最后返回done为true结束。"

**评判：** 核心链路正确 ✅（等 Promise → 把结果传回 → 再走下一步 → 直到 done）。纠正一个表述偏差：res 不是 Promise 本身，res 是 g.next() 返回的对象 {value: promise, done: false}，res.value 才是 Promise，Promise.resolve(res.value) 等的是 res.value。补充：Promise.resolve 的隐藏功能——yield 普通值（如 yield 5）会自动包装成已完成的 Promise，执行器照常工作。

### 教学 4：最后一层窗户纸——语法替换

对照表：function* → async function（内置 run 执行器）；yield promise → await promise（等价）；return 自动包成 Promise；最关键增强：手写执行器遇到 Promise reject 就断链没人管，语言版内置 .catch 分支把错误当异常抛回函数里，所以能用 try/catch 像写同步代码一样处理错误。async/await 没有发明任何新机制，只是把 Generator + 自动执行器 + Promise 这套"手动挡异步"包装成"自动挡"，所以叫语法糖。

### 三层追问（完整问答记录）

**追问一（白话复述）：** 用 30 秒把 async/await 完整机制串一遍：从 async function 声明开始，到 await 拿到值，再到 return，这条链路每一步发生什么？

**学生回答：** "从async function开始，await右侧的结果通过Promise.resolve处理后的结果赋值给左侧的变量；然后可能参与下一个await的右侧函数，最后又获取一个新的Promise.resolve处理后的结果，最终返回出去"

**评判：** 部分通过。链路主干对（await 右侧处理 → 赋值左边 → 参与下一步），但缺灵魂——"暂停/恢复"全程没出现。await 的本质动作是"函数在这里挂起，Promise 完成后才恢复"，复述漏了"挂起"。

**追问二（对比理解）：** 同样是两个互不依赖的请求，用 await 写是串行还是并行？要改成并行应该怎么写？为什么两种写法耗时不一样？

**学生回答：** "await写的话是串行，要等待上一个执行完毕后才会执行await下一行的代码。改成并行可以单独定义两个async/await的函数，然后同步写就好了。"

**评判：** 串行对 ✅。并行错 ❌——"定义两个 async 函数"不是并行的原因，在外层 await fn1(); await fn2(); 照样串行。正确答案：先发起、后等待——`const pa = fetchA(); const pb = fetchB(); const a = await pa; const b = await pb;` 两个请求在等待期间并行跑。金句：await 本身不产生耗时，耗时发生在"发起请求"那一刻。

**追问三（场景应用）：** `async function foo() { await 5; console.log('done') }` 会怎样？await 5 会发生什么，console.log('done') 能执行吗？

**学生回答：** "会打印done"

**评判：** 通过 ✅。await 5 被 Promise.resolve(5) 包装成已完成的 Promise，done 一定会打印。补充细节：要等当前同步代码跑完、进微任务队列才打印，但一定会打。

**薄弱点记录（供周复盘出题）：** ① async 无 return 的返回值状态；② await 是否阻塞、阻塞谁；③ 并行的"先发起后等待"写法；④ yield 传值方向（value 类型）。

**改进建议（需修改笔记的 5 处）：**
1. 无 return 的 async 函数返回**已完成的 Promise、值为 undefined**，不是 pending。
2. await 不阻塞任何人，只是挂起当前 async 函数自身、把后续代码变微任务。
3. value 不一定是 Promise，yield 右侧跟什么就是什么。
4. await 只能在 async 里用：async 函数 = Generator + 内置执行器，await 依赖挂起/恢复机制，普通函数没有。
5. 并行写法：先发起、后等待（`const pa = fetchA(); ... await pa`），补进笔记第三部分。
