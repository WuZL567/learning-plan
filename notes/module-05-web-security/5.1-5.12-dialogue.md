### 关键追问与正确答案

**追问：反射型和DOM型的本质区别是什么？**
- 学生答：是否经过服务器请求
- 评判：✅ 正确
- 正确答案：反射型经过服务器（URL参数 → 服务器返回HTML → 浏览器执行），DOM型不经过服务器（URL参数 → 前端JS直接读取 → DOM操作）

**场景判断错误纠正：**
- 场景B（前端 innerHTML 渲染 URL 参数）：学生答反射型 ❌ 正确答案：DOM型
- 场景C（后端拼接 URL 参数返回HTML）：学生答DOM型 ❌ 正确答案：反射型

### 改进建议

### 关键追问与正确答案

**追问：escapeHTML 代码会有二次转义问题吗？**
- 学生答：不会，因为不是 replaceAll ❌
- 正确答案：不会二次转义的原因是 `replace` 一次性遍历整个字符串，每个字符只匹配一次，新生成的 `&amp;` 不会再参与后续匹配

**场景：富文本渲染应该用哪种方案？**
- 学生答：方案C（DOMPurify过滤） ✅
- 正确解释：escapeHTML 会转义所有标签（包括安全的 `<p>`），富文本需要用白名单过滤库保留安全标签、移除危险标签

### 改进建议
代码补充边界处理：`if (str == null || str === '') return '';`

## 第三组验收：5.7+5.8+5.9 CSRF攻击与防御

### 验收结果
- 分数：8.5分
- 判定：通过

### 关键追问与正确答案

**追问：CSRF 攻击的核心原理是什么？攻击者需要知道 Cookie 内容吗？**
- 学生答：利用浏览器自动携带Cookie的特性；攻击者不需要知道Cookie内容 ✅
- 正确解释：HttpOnly 防止 JS 读取 Cookie（防XSS），但防不了 CSRF，因为浏览器仍然自动携带 Cookie

**追问：CSRF Token 放在请求体和请求头，防御效果一样吗？**
- 学生答：不清楚
- 正确答案：效果相同，核心是攻击者无法获取 Token 值（同源策略限制）。请求体适合表单提交，请求头适合 AJAX 请求

**追问：攻击者在表单里也加了 csrf_token 字段（瞎猜的值），能成功吗？**
- 学生答：几乎不可能，猜不中 value ✅
- 补充：name 属性通常是公开的（如 csrf_token），真正防御的是 value 的随机值

- escapeHTML 函数逻辑正确，所有测试用例通过
- validateCSRFToken 函数正确处理了所有边界情况

### 验收结果

2. 场景应用扣1分：5个场景判断错了2个

### 关键追问与正确答案

**追问：ads.bank.com → bank.com 是跨站请求吗？SameSite=Strict 能防住吗？**
- 学生初次答：是跨站，能防住 ❌
- 正确答案：是**同站**（eTLD+1 相同都是 bank.com），SameSite=Strict **无法防住**子域名攻击
- 核心结论：**必须配合 CSRF Token 使用，双重防御**

**场景判断错误纠正：**
- 场景C（http://example.com → https://example.com）：学生答跨站 ❌ 正确答案：同站（协议差异不影响"同站"判断）
- 场景E（blog.github.io → docs.github.io）：学生答同站 ❌ 正确答案：跨站（github.io 是公共后缀，两者 eTLD+1 不同）

**追问：第三方支付回调场景，SameSite=Strict 会出现什么问题？**
- 学生答：支付宝回调时无法识别用户 ✅
- 推荐方案：用 SameSite=Lax（允许顶级导航携带Cookie）或用 URL 参数传递状态（最佳）

### 改进建议
补充笔记中"SameSite 只防跨站，不防同站攻击"，举例说明子域名攻击场景
