# 11.1.7 通义千问 API + 11.1.8 Claude API + 11.1.9 多 Provider 统一封装

## 一句话说清楚

**这里用一句白话解释这三个技术点的核心：**
（例如：通义千问和 Claude 是两个不同的 LLM 服务商，调用方式和 DeepSeek 类似但有细节差异；统一封装就是用适配器模式把它们包成一套接口，业务代码不用改）
通义千问和 Claude 是两个不同公司的 LLM 服务，调用方式和 DeepSeek 差不多但细节不同（比如 Claude 的 system 是单独参数）。统一封装就是写一个父类定义接口，每个 Provider 子类自己内部转换格式，业务代码只写一次 provider.chat()，切换模型只改配置。

## 核心要点

### 要点 1：通义千问 API 的特殊之处

**这里写通义千问 API 和 DeepSeek API 的主要差异：**
（例如：SDK 名称、模型名格式、返回值结构、result_format 参数等）
SDK名称：通义千问来自dashscope，DeepSeek来自deepseek控制台；

### 要点 2：Claude API 的特殊之处

**这里写 Claude API 和其他 API 的主要差异：**
（例如：system prompt 是单独参数不在 messages 里、返回结构是 content[0].text、max_tokens 必填等）
Claude在messages中没有role为system的，system是单独参数和messages同层级；

### 要点 3：统一封装的设计思路

**这里写如何用适配器模式封装多个 Provider：**
（例如：定义统一的输入输出格式、每个 Provider 子类负责格式转换、工厂函数根据配置返回对应 Provider、业务代码只写一次等）
统一用户输入格式，接受相同参数输入；
统一API返回格式，输出相同返回值结构；
在每个provider中，每个子类都自己内部处理转换，把统一的输入格式转成自己API的输入格式，把自己的API输出，转成统一的API返回值格式；

**和前端封装的类比：**
（例如：类似前端的 Axios 封装，切换 baseURL 只改一行配置）
前端的API封装，封装类中，定义baseURL是传入的参数，所有的请求都直接使用传入的参数就好，改动baseURL只需要改动输入参数；
