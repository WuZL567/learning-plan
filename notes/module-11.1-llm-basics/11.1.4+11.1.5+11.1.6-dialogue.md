#### 11.1.4 Context Window

**第一层追问（白话复述）：**
问：假设我和AI聊了10轮对话，每轮用户说100 tokens、AI回200 tokens，现在窗口是4096 tokens。第11轮我再问问题，会发生什么？

答：10轮对话下来，总共消耗了context window是 (100+200)*10=3000 Tokens，余量还有1096tokens，所以再问问题，就只能用户问的问题+LLM回复在1096Tokens以内才行。

评判：✓ 正确。理解了窗口是累计消耗的概念。

**第二层追问（对比理解）：**
问：Context Window 和你前端的什么机制最像？是 localStorage 的 5MB 限制、还是浏览器的并发请求数限制、还是 Vue 组件的 props 传递深度限制？

答：我觉得和localStorage的内存大小限制差不多，超出时就写不进去了。

评判：✓ 正确。类比准确，都是容量上限的概念。

**第三层追问（场景应用）：**
问：你在做一个 AI 客服系统，用户可能连续聊 50 轮。你会选择哪种溢出策略（截断、摘要、滑动窗口、压缩）？如果换成 AI 代码助手（用户让 AI 持续修改同一个文件），策略会变吗？

答：客服系统没有那么强的上下文关联，可以采用摘要的策略，如果换成AI代码助手，需要强的上下文关联，所以应该用滑动窗口或者压缩的策略。

评判：✓ 正确。理解了不同场景的上下文关联强度决定策略选择。补充：客服场景更常用滑动窗口（保留最近5-10轮），因为每轮相对独立，摘要成本高且不必要。

#### 11.1.5 Max Tokens

**第一层追问（白话复述）：**
问：如果我设置 max_tokens=100，但LLM只用了50个tokens就说完了，finish_reason会返回什么？

答：这不会截断，所以finish_reason返回stop表示正常结束对话。

评判：✓ 正确。理解了 finish_reason 的两种取值含义。

**第二层追问（对比理解）：**
问：Max Tokens 和 Context Window 是什么关系？如果我设置 max_tokens=2000，但 Context Window 只剩 500 tokens，最终 LLM 能回复多少 tokens？

答：Context Window包含Max Tokens，最多回复500Tokens。

评判：✓ 正确。理解了包含关系，且 Context Window 的剩余空间是硬上限。

**第三层追问（场景应用）：**
问：你在做一个"AI 生成商品标题"功能，要求标题必须在 20 字以内。你会把 max_tokens 设置成多少？

答：差不多20吧，根据实际的业务容忍度来调整就好。

评判：✗ 错误。**扣1分**

**正确答案：** 中文 1 个字约等于 1.5-2 个 tokens（因为分词算法会把汉字拆开）。如果要求"20 字以内"，max_tokens 应该设置 **40-50** 才保险。设 20 的话，LLM 可能只输出 10-12 个汉字就被截断了。

**记住：** max_tokens 设置成目标字数的 2-2.5 倍（中文场景）。英文可以按 1:1 或 1:1.5。

#### 11.1.6 DeepSeek API

**第一层追问（白话复述）：**
问：LLM API和你前端调/api/login有什么本质不同？入参的messages数组和普通JSON有什么特殊之处？

答：本质就是发送HTTP请求获取返回值。

评判：回答太泛。补充教学后重新追问。

**重新追问：**
问：messages数组里，system、user、assistant这三个role的顺序必须怎么排列？如果我写成 user → user → assistant 会报错吗？

答：必须system->user-assistant->user->assistant...，system必须在第一个，并且后面的对话应该是一轮一轮的；如果是user->user->assistant可能会报错，也可能会覆盖第一个user的提问内容，LLM只会回答第二个user的输入。

评判：✓ 正确。理解了交替规则。

**第二层追问（对比理解）：**
问：为什么 messages 数组要设计成 user 和 assistant 交替，而不是像普通数组一样随便塞？这个设计和 LLM 的什么特性有关？

答：因为对话就是一问一答的形式，随便塞就不是这样设计了；LLM不会主动发送消息，而是基于用户的输入后回复。

评判：✓ 正确。理解了 LLM 的被动响应特性。

**第三层追问（场景应用）：**
问：你现在要调用 DeepSeek API 实现一个功能：用户输入一段代码，AI 找出 bug 并解释。请口述你会怎么构造 messages 数组。

答：
```python
[
  {"role": "system", "content": "你现在是一个高级程序员，非常擅长在代码中找到BUG进行解析解释，协助用户完成BUG理解和分析。"},
  {"role": "user", "content": "阅读代码，并找出代码中可能存在的BUG以及解释理由。"},
  {"role": "assistant", "content": "好的，这段代码中xxx"}
]
```

评判：✗ 错误。**扣1分**

**问题：** 多了一条 `assistant` 的回复。用户第一次请求时，messages 数组里**不应该包含 assistant 的回复**，因为这是 AI 还没回复的状态。

**正确构造：**
```python
messages = [
    {"role": "system", "content": "你是一个高级程序员，擅长找代码bug并解释原因"},
    {"role": "user", "content": "请找出以下代码的bug并解释：\n\n[用户粘贴的代码]"}
]
```

只有当你想做**多轮对话**（比如用户追问"还有其他bug吗？"），才需要在 messages 里加上之前的 assistant 回复。
