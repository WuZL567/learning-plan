# 部署运维：Nginx + Docker 的 5 个跟练 Demo

## 学习路线图

~~~
Demo 1: Nginx 基础 — 反向代理 + 跨域 + 静态托管（20分钟）
  ↓
Demo 2: Nginx 进阶 — 负载均衡 + HTTPS（20分钟）
  ↓
Demo 3: Docker 基础 — 打包你的应用成容器（20分钟）
  ↓
Demo 4: Dockerfile — 分别打包 FastAPI 和 Vue3（20分钟）
  ↓
Demo 5: docker-compose — 一键启动完整项目（20分钟）
~~~

---

## 核心策略：5 个知识点

1. **Nginx 反向代理** → 用户访问 Nginx，Nginx 转发给后端，前端不需要知道后端地址
2. **Nginx 负载均衡** → 多个后端实例，Nginx 分配请求
3. **Docker 容器** → 把应用和环境打包成一个"箱子"，在哪台机器都能跑
4. **Dockerfile** → "打包说明书"，告诉 Docker 怎么构建这个"箱子"
5. **docker-compose** → 一键启动多个"箱子"（前端 + 后端 + 数据库 + ...）

## Demo 1：Nginx 基础 — 反向代理 + 跨域

### 学习目标

- 理解正向代理 vs 反向代理
- 用 Nginx 做 API 反向代理（解决跨域）
- 用 Nginx 托管前端静态文件

### 1.1 安装 Nginx

~~~bash
# macOS
brew install nginx

# Ubuntu/Debian
sudo apt update && sudo apt install nginx -y

# 验证
nginx -v
# 输出 ✅ nginx version: nginx/1.24.x

# 启动
sudo nginx

# 访问 http://localhost:80 看到 Nginx 欢迎页即成功

# 停止
sudo nginx -s stop

# 重新加载配置（修改配置后执行，不需要重启）
sudo nginx -s reload
~~~

### 1.2 正向代理 vs 反向代理

~~~
正向代理（帮客户端）：
  客户端 → 代理 → 互联网
  场景：VPN、科学上网
  代理代表"客户端"去访问

反向代理（帮服务端）：
  客户端 → 代理 → 后端服务器
  场景：Nginx
  代理代表"服务端"接收请求

前端开发者最常接触的是反向代理：
  浏览器 → Nginx(:80) → FastAPI(:8000)
  浏览器以为自己在和 Nginx 通信（没有跨域问题）
  Nginx 悄悄把请求转发给后端
~~~

### 1.3 Nginx 反向代理配置

创建配置文件 `demo1_反向代理.conf`：

~~~nginx
# ========== demo1_反向代理.conf
# Nginx 配置文件结构：
#   全局配置
#   events { ... }        → 连接相关
#   http { ... }           → HTTP 相关
#       server { ... }     → 一个虚拟主机（一个网站）
#           location / {}  → URL 匹配规则

worker_processes 1;

events {
    worker_connections 1024;
}

http {
    # ========== 反向代理：/api 开头的请求转发给后端
    server {
        listen 80;                    # 监听 80 端口
        server_name localhost;        # 域名

        # 前端静态文件（Vue3 打包后的 dist 目录）
        location / {
            root /usr/share/nginx/html;   # 静态文件目录
            index index.html;             # 默认文件
            try_files $uri $uri/ /index.html;  # SPA 路由回退（重要！）
        }

        # API 反向代理
        location /api/ {
            proxy_pass http://127.0.0.1:8000/;  # 转发给后端
            proxy_set_header Host $host;         # 传递原始域名
            proxy_set_header X-Real-IP $remote_addr;     # 传递客户端真实 IP
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }

        # SSE 流式接口特殊配置
        location /api/聊天 {
            proxy_pass http://127.0.0.1:8000/聊天;
            proxy_set_header Host $host;
            proxy_buffering off;          # 关闭缓冲（SSE 必须）
            proxy_cache off;              # 关闭缓存
            proxy_read_timeout 300s;      # 长连接超时 5 分钟
        }
    }
}
~~~

**前端类比理解：**

~~~
没有 Nginx 时（开发环境用 Vite 代理）：
  前端 localhost:5173 → Vite dev server → 代理到 → localhost:8000

有 Nginx 时（生产环境）：
  前端 localhost:80 → Nginx → 代理到 → localhost:8000

本质一样：都是反向代理解决跨域
Vite 的 proxy 配置 = 开发时的反向代理
Nginx = 生产时的反向代理
~~~

### 1.4 测试反向代理

~~~bash
# 1. 先启动你的 FastAPI 后端
uvicorn main:应用 --port 8000

# 2. 加载 Nginx 配置
sudo nginx -c $(pwd)/demo1_反向代理.conf

# 3. 测试
curl http://localhost/api/菜品      # 被 Nginx 转发到 http://localhost:8000/菜品
curl http://localhost/api/          # 转发到 http://localhost:8000/
~~~

**Demo 1 学完你应该掌握：**
- 反向代理 = Nginx 代表服务器接收请求，转发给后端
- `proxy_pass` 转发请求，`try_files` 处理 SPA 路由
- `proxy_buffering off` 是 SSE 流式接口必须的配置

## Demo 2：Nginx 进阶 — 负载均衡 + HTTPS

### 学习目标

- 配置负载均衡（多个后端实例分配请求）
- 理解 HTTPS 和证书配置

### 2.1 负载均衡

~~~nginx
# ========== 负载均衡配置

http {
    # 定义后端服务器组
    upstream 后端集群 {
        # 负载均衡策略（选一种）

        # 策略1：轮询（默认，按顺序轮流分配）
        server 127.0.0.1:8001;
        server 127.0.0.1:8002;
        server 127.0.0.1:8003;

        # 策略2：加权轮询（按权重分配，性能好的多分）
        # server 127.0.0.1:8001 weight=3;   # 权重3，接收更多请求
        # server 127.0.0.1:8002 weight=2;   # 权重2
        # server 127.0.0.1:8003 weight=1;   # 权重1

        # 策略3：IP Hash（同一 IP 总是访问同一后端，解决 Session 问题）
        # ip_hash;
        # server 127.0.0.1:8001;
        # server 127.0.0.1:8002;

        # 策略4：最少连接（把请求发给当前连接数最少的后端）
        # least_conn;
        # server 127.0.0.1:8001;
        # server 127.0.0.1:8002;
    }

    server {
        listen 80;

        location /api/ {
            proxy_pass http://后端集群/;    # 转发到服务器组
        }
    }
}
~~~

**三种策略对比：**

| 策略 | 原理 | 适用场景 |
|---|---|---|
| 轮询 | 按顺序轮流 | 后端性能一致，无状态服务 |
| 加权轮询 | 按权重比例分配 | 后端性能不同（如机器配置不同） |
| IP Hash | 同一 IP 固定到同一后端 | 需要 Session 粘性的场景 |
| 最少连接 | 发给连接数最少的后端 | 请求处理时间差异大 |

### 2.2 HTTPS 配置

~~~nginx
# ========== HTTPS 配置

server {
    listen 443 ssl;                   # HTTPS 端口
    server_name api.你的域名.com;

    # 证书文件（从域名服务商或 Let's Encrypt 获取）
    ssl_certificate     /etc/nginx/ssl/cert.pem;      # 证书
    ssl_certificate_key /etc/nginx/ssl/key.pem;        # 私钥

    # SSL 优化
    ssl_protocols TLSv1.2 TLSv1.3;   # 只允许安全的 TLS 版本
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;

    location / {
        proxy_pass http://127.0.0.1:8000;
    }
}

# HTTP 自动跳转 HTTPS
server {
    listen 80;
    server_name api.你的域名.com;
    return 301 https://$server_name$request_uri;
}
~~~

**免费 HTTPS 证书（Let's Encrypt）：**

~~~bash
# 安装 certbot
sudo apt install certbot python3-certbot-nginx -y

# 自动获取并配置证书
sudo certbot --nginx -d api.你的域名.com

# 证书自动续期（certbot 会自动设置 cron job）
sudo certbot renew --dry-run
~~~

## Demo 3：Docker 基础 — 打包应用成容器

### 学习目标

- 理解 Docker 的核心概念（镜像、容器、仓库）
- 学会基本的 Docker 命令
- 把一个简单的应用打包成容器

### 3.1 核心概念

~~~
Docker 核心概念对照：

镜像（Image）= 安装光盘
  → 一个只读的模板，包含应用代码 + 运行环境 + 依赖
  → 类比：Vue 项目打包后的 dist 文件夹，但包含了整个运行环境

容器（Container）= 运行中的程序
  → 从镜像启动的一个实例
  → 类比：`npm run dev` 启动的开发服务器

仓库（Registry）= 镜像商店
  → 存放和分发镜像的地方
  → 公共：Docker Hub（类似 npm）
  → 私有：阿里云容器镜像服务

Dockerfile = 打包说明书
  → 告诉 Docker 怎么构建镜像
  → 类比：package.json + 构建脚本

docker-compose.yml = 启动编排文件
  → 一键启动多个容器
  → 类比：同时启动前端 + 后端 + 数据库的脚本
~~~

### 3.2 安装 Docker

~~~bash
# macOS：下载 Docker Desktop
# https://www.docker.com/products/docker-desktop/

# Ubuntu
sudo apt update
sudo apt install docker.io docker-compose-plugin -y
sudo usermod -aG docker $USER
# 重新登录终端

# 验证
docker --version
docker compose version
~~~

### 3.3 基本命令

~~~bash
# ========== 镜像相关
docker images                        # 列出本地镜像
docker pull nginx:1.24               # 拉取镜像（类似 npm install）
docker rmi nginx:1.24                # 删除镜像

# ========== 容器相关
docker run -d --name 容器名 -p 80:80 nginx:1.24
# -d          后台运行
# --name      容器名称
# -p 80:80    端口映射（宿主机端口:容器端口）
# nginx:1.24  使用的镜像

docker ps                            # 查看运行中的容器
docker ps -a                         # 查看所有容器（包括已停止的）
docker stop 容器名                    # 停止容器
docker start 容器名                   # 启动已停止的容器
docker rm 容器名                      # 删除容器
docker logs 容器名                    # 查看容器日志
docker exec -it 容器名 /bin/bash      # 进入容器内部（调试用）
# exec -it   交互式执行
# /bin/bash  打开 bash 终端

# ========== 实际操作
# 1. 运行一个 Nginx 容器
docker run -d --name 我的nginx -p 8080:80 nginx:1.24
# 访问 http://localhost:8080 看到 Nginx 欢迎页

# 2. 查看日志
docker logs 我的nginx

# 3. 停止并删除
docker stop 我的nginx
docker rm 我的nginx
~~~

## Demo 4：Dockerfile — 分别打包 FastAPI 和 Vue3

### 学习目标

- 编写 Dockerfile 打包 Python FastAPI 应用
- 编写 Dockerfile 打包 Vue3 前端应用
- 理解多阶段构建

### 4.1 打包 FastAPI 后端

创建文件 `backend.Dockerfile`：

~~~dockerfile
# ========== backend.Dockerfile
# 打包 Python FastAPI 后端应用

# 第1步：选择基础镜像（就像选择操作系统 + 预装软件）
FROM python:3.12-slim
# python:3.12-slim = 精简版 Python 3.12（体积小，够用）
# python:3.12     = 完整版（体积大，一般不需要）
# slim = 精简版，去掉了不必要的系统工具

# 第2步：设置工作目录（容器内的目录）
WORKDIR /app
# 类似 cd /app

# 第3步：先复制依赖文件（利用 Docker 缓存机制）
COPY requirements.txt .
# 只要 requirements.txt 不变，这一层就不会重新构建
# 比直接 COPY . . 更快（依赖没变就不需要重新 pip install）

# 第4步：安装依赖
RUN pip install --no-cache-dir -r requirements.txt
# --no-cache-dir = 不缓存 pip 下载的包（减小镜像体积）

# 第5步：复制项目代码
COPY . .
# 复制当前目录所有文件到容器的 /app

# 第6步：暴露端口
EXPOSE 8000
# 这只是声明，实际映射在 docker run -p 时指定

# 第7步：启动命令
CMD ["uvicorn", "main:应用", "--host", "0.0.0.0", "--port", "8000"]
# --host 0.0.0.0 很重要！让容器外也能访问
# 如果只写 127.0.0.1，只有容器内部能访问
~~~

构建并运行：

~~~bash
# 构建镜像
docker build -f backend.Dockerfile -t 餐厅后端:1.0 .
# -f   指定 Dockerfile 文件名
# -t   镜像名称:标签
# .    构建上下文（当前目录）

# 运行容器
docker run -d --name 后端 -p 8000:8000 \
  -e OPENAI_API_KEY=你的密钥 \
  -e OPENAI_BASE_URL=https://api.openai.com/v1 \
  餐厅后端:1.0
# -e 传入环境变量

# 查看日志
docker logs -f 后端
# -f 实时跟踪日志

# 访问
curl http://localhost:8000/
~~~

### 4.2 打包 Vue3 前端（多阶段构建）

创建文件 `frontend.Dockerfile`：

~~~dockerfile
# ========== frontend.Dockerfile
# 多阶段构建：先构建，再用 Nginx 托管
# 阶段1 → 编译 Vue3 项目
# 阶段2 → 用 Nginx 托管编译结果

# ========== 阶段1：构建阶段
FROM node:20-alpine AS 构建阶段
# AS 构建阶段 → 给这个阶段起个名字

WORKDIR /app

# 先复制依赖文件（利用缓存）
COPY package.json package-lock.json ./

# 安装依赖
RUN npm ci
# npm ci 比 npm install 更快更严格（严格按 lock 文件安装）

# 复制源代码
COPY . .

# 构建
RUN npm run build
# 输出到 /app/dist

# ========== 阶段2：运行阶段
FROM nginx:1.24-alpine AS 运行阶段

# 从阶段1复制构建结果
COPY --from=构建阶段 /app/dist /usr/share/nginx/html

# 复制 Nginx 配置
COPY nginx.conf /etc/nginx/conf.d/default.conf

# 暴露端口
EXPOSE 80

# Nginx 默认前台运行
CMD ["nginx", "-g", "daemon off;"]
# daemon off → 前台运行（Docker 要求主进程在前台）
~~~

配套的 `nginx.conf`：

~~~nginx
server {
    listen 80;
    server_name localhost;
    root /usr/share/nginx/html;
    index index.html;

    # SPA 路由回退（Vue Router 的 history 模式必须）
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://后端:8000/;
        # 注意：这里用"后端"作为主机名
        # 在 docker-compose 网络中，容器名就是主机名
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # SSE 流式接口
    location /api/聊天 {
        proxy_pass http://后端:8000/聊天;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
    }

    # 静态资源缓存
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
        expires 30d;                   # 缓存30天
        add_header Cache-Control "public, immutable";
    }

    # Gzip 压缩
    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml;
    gzip_min_length 1024;
}
~~~

构建并运行：

~~~bash
# 构建
docker build -f frontend.Dockerfile -t 餐厅前端:1.0 .

# 运行
docker run -d --name 前端 -p 80:80 餐厅前端:1.0

# 访问
curl http://localhost/
~~~

**Demo 4 学完你应该掌握：**
- Dockerfile 的 7 步模板：FROM → WORKDIR → COPY 依赖 → RUN 安装 → COPY 代码 → EXPOSE → CMD
- 多阶段构建：先用 Node 编译，再用 Nginx 托管（最终镜像很小）
- `--host 0.0.0.0` 让容器外能访问
- `nginx -g "daemon off;"` 前台运行

## Demo 5：docker-compose — 一键启动完整项目

### 学习目标

- 用 docker-compose 编排多个容器
- 一键启动 前端 + 后端 + PostgreSQL + pgvector
- 理解容器间通信

### 5.1 项目结构

~~~
餐厅AI助手/
├── frontend/                 # 前端项目
│   ├── src/
│   ├── package.json
│   ├── nginx.conf
│   └── frontend.Dockerfile
├── backend/                  # 后端项目
│   ├── main.py
│   ├── requirements.txt
│   └── backend.Dockerfile
├── docker-compose.yml        # 编排文件（核心！）
└── .env                      # 环境变量
~~~

### 5.2 docker-compose.yml

创建文件 `docker-compose.yml`：

~~~yaml
# ========== docker-compose.yml
# 一键启动：前端 + 后端 + PostgreSQL + pgvector

version: "3.8"  # compose 文件版本

services:
  # ========== PostgreSQL 数据库
  数据库:
    image: pgvector/pgvector:pg16  # 带 pgvector 扩展的 PostgreSQL
    container_name: 餐厅数据库
    environment:
      POSTGRES_DB: 餐厅数据库       # 自动创建的数据库名
      POSTGRES_USER: postgres       # 用户名
      POSTGRES_PASSWORD: password   # 密码（生产环境要改成强密码！）
    ports:
      - "5432:5432"                 # 端口映射
    volumes:
      - 数据库存储:/var/lib/postgresql/data  # 数据持久化（容器删了数据还在）
    healthcheck:                    # 健康检查
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s                  # 每5秒检查一次
      timeout: 5s
      retries: 5

  # ========== FastAPI 后端
  后端:
    build:
      context: ./backend            # 构建上下文目录
      dockerfile: backend.Dockerfile
    container_name: 餐厅后端
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://postgres:password@数据库:5432/餐厅数据库
      # 注意：这里用"数据库"作为主机名 → docker-compose 会自动解析为数据库容器的 IP
      OPENAI_API_KEY: ${OPENAI_API_KEY}   # 从 .env 文件读取
      OPENAI_BASE_URL: ${OPENAI_BASE_URL}
    depends_on:
      数据库:
        condition: service_healthy  # 等数据库健康检查通过后再启动
    restart: unless-stopped         # 除非手动停止，否则自动重启

  # ========== Vue3 前端
  前端:
    build:
      context: ./frontend
      dockerfile: frontend.Dockerfile
    container_name: 餐厅前端
    ports:
      - "80:80"
    depends_on:
      - 后端                        # 等后端启动后再启动
    restart: unless-stopped

# 数据卷（持久化存储）
volumes:
  数据库存储:                        # 命名卷，Docker 管理存储位置
~~~

### 5.5 后端数据库连接调整

~~~python
# backend/database.py
# 从环境变量读取数据库地址（docker-compose 会通过环境变量注入）
import os
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, DeclarativeBase

数据库地址 = os.getenv(
    "DATABASE_URL",
    "postgresql://postgres:password@localhost:5432/餐厅数据库"  # 本地开发默认值
)

引擎 = create_engine(数据库地址)
会话工厂 = sessionmaker(bind=引擎)

class 模型基类(DeclarativeBase):
    pass

def 获取数据库会话():
    会话 = 会话工厂()
    try:
        yield 会话
    finally:
        会话.close()
~~~

### 5.6 一键启动

~~~bash
# ========== 一键启动整个项目
docker compose up -d --build

# up        = 创建并启动所有容器
# -d        = 后台运行
# --build   = 重新构建镜像（代码有改动时需要）

# 查看所有容器状态
docker compose ps
# 输出 ✅
# NAME          STATUS          PORTS
# 餐厅数据库    Up (healthy)    0.0.0.0:5432->5432/tcp
# 餐厅后端      Up              0.0.0.0:8000->8000/tcp
# 餐厅前端      Up              0.0.0.0:80->80/tcp

# 查看日志
docker compose logs -f 后端       # 查看后端日志
docker compose logs -f 前端       # 查看前端日志
docker compose logs -f            # 查看所有日志

# 访问
# http://localhost      → 前端页面
# http://localhost:8000  → 后端 API
# http://localhost:8000/docs → Swagger 文档

# ========== 常用操作
docker compose down               # 停止并删除所有容器
docker compose down -v            # 同时删除数据卷（清空数据库）
docker compose restart 后端       # 重启单个容器
docker compose up -d --build 后端 # 只重新构建后端

# ========== 只改了代码，快速更新
git pull                          # 拉取最新代码
docker compose up -d --build      # 重新构建并启动
~~~

### 5.7 容器间通信

~~~
在 docker-compose 中，容器之间用"服务名"作为主机名通信：

  后端代码中：
    数据库地址 = "postgresql://postgres:password@数据库:5432/..."
    #                                              ↑
    #                                    这里的"数据库"就是 docker-compose.yml 中的服务名

  前端 nginx.conf 中：
    proxy_pass http://后端:8000/;
    #                   ↑
    #          这里的"后端"就是 docker-compose.yml 中的服务名

docker-compose 自动创建一个网络，所有容器在同一个网络中
容器之间用服务名互相访问，就像局域网内的主机名
~~~

## 高频面试题

### Q1：Nginx 的反向代理和 Vite 的 proxy 有什么区别？

~~~
Vite proxy（开发环境）：
  代码 → Vite dev server → 代理到 → 后端
  仅开发时有效，生产打包后不存在

Nginx 反向代理（生产环境）：
  代码 → Nginx → 代理到 → 后端
  生产环境使用，性能高，功能强大

两者解决同一个问题（跨域），但用在不同阶段
~~~

### Q2：Docker 和虚拟机有什么区别？

~~~
虚拟机：
  模拟整个操作系统（Windows/Linux）
  体积大（几 GB）、启动慢（分钟级）
  完全隔离

Docker 容器：
  共享宿主机内核，只打包应用和依赖
  体积小（几十 MB）、启动快（秒级）
  进程级隔离

简单说：虚拟机是"装了完整系统的电脑"，Docker 是"只装了应用的轻量箱子"
~~~

### Q3：docker-compose 中 depends_on 和 healthcheck 的作用？

~~~
depends_on：控制启动顺序
  后端 depends_on 数据库 → 数据库先启动，后端后启动
  但只保证"容器启动了"，不保证"服务准备好了"

healthcheck + condition: service_healthy：
  真正等到服务准备好了再启动下一个
  比如等 PostgreSQL 能接受连接了，后端才启动

最佳实践：数据库用 healthcheck，其他服务用 depends_on
~~~

### Q4：Nginx 负载均衡策略怎么选？

~~~
后端无状态（推荐）→ 轮询 或 最少连接
后端有 Session → IP Hash（同一用户总是访问同一后端）
后端性能不同 → 加权轮询（配置好的多分请求）

现在大多数项目用 JWT 无状态认证 → 轮询就够了
~~~

## 终极记忆卡片

1. **Nginx 反向代理** → `proxy_pass http://后端:端口/`，解决跨域
2. **SPA 路由** → `try_files $uri $uri/ /index.html`，history 模式必须
3. **SSE 配置** → `proxy_buffering off` + `proxy_read_timeout 300s`
4. **负载均衡** → `upstream` 定义服务器组，轮询/加权/ip_hash/最少连接
5. **HTTPS** → 443 端口 + ssl_certificate + Let's Encrypt 免费证书
6. **Dockerfile 7 步** → FROM → WORKDIR → COPY 依赖 → RUN 安装 → COPY 代码 → EXPOSE → CMD
7. **多阶段构建** → 阶段1 Node 编译，阶段2 Nginx 托管，最终镜像小
8. **docker-compose** → services 定义容器，volumes 持久化，depends_on 控制顺序
9. **容器间通信** → 用服务名作为主机名，docker-compose 自动组网
10. **一键部署** → `docker compose up -d --build` 启动全部，`docker compose down` 停止全部

## 启动命令速查

~~~bash
# ========== Nginx
sudo nginx                        # 启动
sudo nginx -s stop                # 停止
sudo nginx -s reload              # 重新加载配置
sudo nginx -t                     # 测试配置文件语法

# ========== Docker
docker build -f Dockerfile -t 镜像名:标签 .   # 构建镜像
docker run -d --name 容器名 -p 宿主:容器 镜像名  # 运行容器
docker ps                          # 查看运行中的容器
docker logs -f 容器名               # 查看日志
docker exec -it 容器名 /bin/bash    # 进入容器
docker stop 容器名 && docker rm 容器名  # 停止并删除

# ========== docker-compose
docker compose up -d --build       # 一键启动（构建+启动）
docker compose down                # 停止并删除
docker compose ps                  # 查看状态
docker compose logs -f 服务名      # 查看日志
docker compose restart 服务名      # 重启单个服务
docker compose exec 服务名 /bin/bash  # 进入某个服务容器
~~~
