# 前端工程化：从 Webpack 到 Vite 的完整思考路径

## 核心策略：工程化的 6 个套路

~~~
套路1：构建工具原理      → Webpack 的核心流程 / Vite 为什么快
套路2：模块化            → CommonJS / ESM / 打包原理
套路3：Loader 与 Plugin  → Webpack 的两个核心概念
套路4：代码优化          → Tree Shaking / 代码分割 / 懒加载
套路5：工程化实践        → Babel / ESLint / Git 规范 / CI/CD
套路6：Monorepo 与包管理 → pnpm workspace / 硬链接符号链接 / lock 文件
~~~

## 套路一：构建工具原理

### 为什么需要构建工具？

~~~
浏览器不认识的东西：
  1. import / export（旧浏览器不认识 ESM）
  2. JSX（React 的语法，浏览器不认识）
  3. TypeScript（浏览器不认识）
  4. Less / Sass（浏览器不认识）
  5. Vue 单文件组件（浏览器不认识 .vue 文件）
  6. 高级 ES 语法（旧浏览器不认识）

构建工具做的事：
  把浏览器不认识的东西 → 转换成浏览器认识的东西
  同时做优化（压缩、拆分、Tree Shaking）
~~~

### Webpack 的核心流程

**手写口诀：从入口开始，递归分析依赖，打包成 bundle**

~~~
1. 初始化：读取配置（webpack.config.js）
2. 编译：从 entry 入口开始
3. 递归分析依赖：遇到 import/require 就解析，构建依赖图
4. 转换：用 Loader 处理每个模块（JS/TS/CSS/图片等）
5. 输出：把所有模块打包成 bundle.js
~~~

~~~
Webpack 的工作流程（用餐厅比喻）：

  入口（entry）= 菜单
    从菜单开始，找到每道菜需要的食材

  依赖分析 = 列出所有食材清单
    红烧肉需要：五花肉、酱油、糖
    五花肉需要：猪肉
    递归列出所有依赖

  Loader = 食材加工
    猪肉 → 切块（ES6 → ES5）
    酱油 → 开瓶（TS → JS）
    蔬菜 → 洗净（Less → CSS）

  Plugin = 厨房管理
    清理厨房（CleanWebpackPlugin）
    生成菜单（HtmlWebpackPlugin）
    压缩食材体积（TerserPlugin）

  输出（output）= 成品菜
    所有食材加工完毕 → 端上桌（bundle.js）
~~~

### Vite 为什么比 Webpack 快？

**手写口诀：Webpack 先打包再启动，Vite 先启动再按需编译**

~~~
Webpack 的问题：
  1. 启动时要打包所有模块（模块越多越慢）
  2. 改一个文件要重新打包（热更新慢）
  3. 项目越大越慢

Vite 的优势：
  1. 利用浏览器原生 ESM（import/export）
  2. 不打包，直接让浏览器按需请求模块
  3. 用 esbuild（Go 语言写的）预构建依赖，比 Webpack 快 10-100 倍
  4. 热更新只更新变化的模块（不重新打包）
~~~

~~~
Webpack 的启动过程：
  1. 从入口开始
  2. 递归分析所有依赖
  3. 把所有模块打包成一个/几个文件
  4. 启动开发服务器
  → 模块越多，启动越慢

Vite 的启动过程：
  1. 启动开发服务器（瞬间完成）
  2. 浏览器请求入口文件
  3. 遇到 import → 浏览器向 Vite 请求那个模块
  4. Vite 按需编译那个模块 → 返回给浏览器
  → 不管项目多大，启动都是瞬间的
~~~

### Webpack vs Vite 对比

| | Webpack | Vite |
|---|---|---|
| 启动速度 | 慢（先打包） | 快（按需编译） |
| 热更新 | 慢（重新打包） | 快（只更新变化的模块） |
| 生产构建 | 成熟稳定 | 基于 Rollup，同样稳定 |
| 生态 | 非常丰富 | 快速成长 |
| 配置 | 复杂 | 简单 |
| 适用场景 | 大型老项目 | 新项目首选 |
| 底层打包 | Webpack 自己 | esbuild（预构建）+ Rollup（生产） |

### Vite 插件机制与 HMR

~~~
Vite 插件的原理：
  Vite 插件基于 Rollup 的插件接口，扩展了 Vite 特有的钩子
  插件可以拦截模块请求、转换代码、注入全局变量等

Vite HMR 的原理：
  1. 文件变化 → Vite 的文件系统监听器检测到
  2. 只重新编译变化的模块（不是整个项目）
  3. 通过 WebSocket 通知浏览器
  4. 浏览器用 import() 请求新模块 → 替换旧模块
  5. 不刷新页面，保持状态

HMR 的核心：只更新变化的模块，不重新打包整个项目
~~~

~~~javascript
// ========== 手写 Vite 插件（简化版） ==========
// vite-plugin-菜名.js
export default function 菜名插件(选项 = {}) {
  return {
    name: "vite-plugin-菜名",  // 插件名

    // 钩子1：转换 HTML（在 HTML 被发送到浏览器之前）
    transformIndexHtml(html) {
      return html.replace(
        "</head>",
        `<meta name="author" content="${选项.author || "老王"}" />\n</head>`
      );
    },

    // 钩子2：转换模块代码（类似 Webpack 的 Loader）
    transform(代码, id) {
      if (id.endsWith(".js")) {
        return {
          code: `// 菜名插件处理\n${代码}`,
          map: null
        };
      }
    },

    // 钩子3：配置开发服务器
    configureServer(server) {
      // 添加自定义中间件
      server.middlewares.use((req, res, next) => {
        if (req.url === "/api/菜名") {
          res.end(JSON.stringify({ 菜名: "红烧肉" }));
        } else {
          next();
        }
      });
    },

    // 钩子4：构建时的钩子
    buildStart() {
      console.log("开始构建...");
    },
    buildEnd() {
      console.log("构建完成！");
    }
  };
}

// vite.config.js 中使用
import 菜名插件 from "./vite-plugin-菜名";

export default defineConfig({
  plugins: [
    vue(),
    菜名插件({ author: "老王" })
  ]
});
~~~

## 套路二：模块化

### 模块化的演进

~~~
1. 全局变量（远古时代）
   → 变量污染、依赖顺序问题

2. IIFE（立即执行函数）
   → 解决变量污染，但依赖管理困难

3. CommonJS（Node.js）
   → require 导入，module.exports 导出
   → 同步加载，服务端用

4. AMD / CMD（浏览器）
   → require.js / sea.js
   → 异步加载，浏览器用

5. ESM（现代标准）
   → import / export
   → 浏览器和 Node.js 都支持
   → 静态分析（支持 Tree Shaking）
~~~

### CommonJS vs ESM

| | CommonJS | ESM |
|---|---|---|
| 语法 | require / module.exports | import / export |
| 加载方式 | 同步加载（运行时） | 异步加载（编译时） |
| 值的拷贝 | ✅ 值的拷贝 | ✅ 值的引用（活绑定） |
| Tree Shaking | ❌ 不支持 | ✅ 支持 |
| 动态导入 | ✅ require 可以在任何地方 | ✅ import() 动态导入 |
| this 指向 | 当前模块 | undefined |
| 适用环境 | Node.js | 浏览器 + Node.js |

~~~javascript
// ========== CommonJS ==========
// 导出
const 做菜 = (菜名) => `${菜名}做好了`;
module.exports = { 做菜 };
// 或
exports.做菜 = 做菜;

// 导入
const { 做菜 } = require("./做菜");
做菜("红烧肉");

// ========== ESM ==========
// 导出
export const 做菜 = (菜名) => `${菜名}做好了`;
export default class 餐厅 { }

// 导入
import { 做菜 } from "./做菜.js";
import 餐厅 from "./餐厅.js";

// ========== 动态导入（代码分割） ==========
const 模块 = await import("./做菜.js");
模块.做菜("红烧肉");

// 或
import("./做菜.js").then(模块 => 模块.做菜("红烧肉"));
~~~

### 活绑定 vs 值拷贝

~~~javascript
// ========== CommonJS：值的拷贝 ==========
// counter.js
let 计数 = 0;
function 加一() { 计数++; }
module.exports = { 计数, 加一 };

// main.js
const { 计数, 加一 } = require("./counter");
加一();
加一();
console.log(计数);  // 0 ❌（拿到的是导出时的拷贝，不是最新值）

// ========== ESM：值的引用（活绑定） ==========
// counter.js
export let 计数 = 0;
export function 加一() { 计数++; }

// main.js
import { 计数, 加一 } from "./counter.js";
加一();
加一();
console.log(计数);  // 2 ✅（活绑定，始终拿到最新值）
~~~

### 循环依赖处理

~~~
CommonJS 的循环依赖：
  模块A require 模块B，模块B require 模块A
  CommonJS 遇到循环依赖时，返回当前已经执行的部分（不完整的导出）
  → 可能拿到 undefined 或不完整的对象

ESM 的循环依赖：
  ESM 使用"活绑定"，即使有循环依赖，也能拿到最终的值
  但在模块执行顺序上，可能在访问时模块还没执行完
  → 建议：避免循环依赖，重构代码结构
~~~

## 套路三：Loader 与 Plugin

### Loader 是什么？

**手写口诀：Loader 是转换器，把 A 类型的文件转换成 B 类型**

~~~
Loader 的本质：一个函数
  输入：源文件内容
  输出：转换后的文件内容

常见 Loader：
  babel-loader     → ES6+ → ES5
  css-loader       → CSS → JS 模块
  style-loader     → JS 模块 → <style> 标签
  less-loader      → Less → CSS
  ts-loader        → TypeScript → JavaScript
  vue-loader       → .vue → JS 模块
  file-loader      → 文件 → URL
  url-loader       → 小文件 → Base64
~~~

~~~javascript
// ========== 手写一个简单的 Loader ==========
// my-loader.js
module.exports = function(source) {
  // source 是文件的原始内容
  // 对内容进行转换
  const result = source.replace(/红烧肉/g, "糖醋里脊");
  return result;
  // 返回转换后的字符串
};

// webpack.config.js
module.exports = {
  module: {
    rules: [
      {
        test: /\.js$/,
        use: [
          {
            loader: path.resolve("./my-loader.js"),
            options: { 替换: "糖醋里脊" }  // 传参
          }
        ]
      }
    ]
  }
};
~~~

### Plugin 是什么？

**手写口诀：Plugin 是扩展器，在构建的特定时机执行自定义逻辑**

~~~
Plugin 的本质：一个类
  必须有一个 apply 方法
  apply 方法接收 compiler 对象
  通过 compiler.hooks 在特定时机执行逻辑
~~~

~~~javascript
// ========== 手写一个简单的 Plugin ==========
class 打包日志Plugin {
  apply(compiler) {
    // 在打包开始时
    compiler.hooks.compile.tap("打包日志Plugin", () => {
      console.log("开始打包...");
    });

    // 在每次编译完成后
    compiler.hooks.done.tap("打包日志Plugin", (stats) => {
      console.log(`打包完成！耗时：${stats.endTime - stats.startTime}ms`);
    });

    // 异步钩子
    compiler.hooks.emit.tapAsync("打包日志Plugin", (compilation, callback) => {
      console.log("正在输出文件...");
      callback();
    });
  }
}

// webpack.config.js
module.exports = {
  plugins: [
    new 打包日志Plugin()
  ]
};
~~~

### Loader vs Plugin

| | Loader | Plugin |
|---|---|---|
| 作用 | 转换文件内容 | 扩展构建功能 |
| 本质 | 函数（接收源码，返回转换后的代码） | 类（apply 方法监听钩子） |
| 执行时机 | 模块加载时 | 构建的各个生命周期 |
| 配置位置 | module.rules | plugins |
| 举例 | babel-loader, css-loader | HtmlWebpackPlugin, CleanWebpackPlugin |

## 套路四：代码优化

### Tree Shaking（摇树）

**手写口诀：ESM 静态分析，删除没用的代码**

~~~
Tree Shaking 的前提：
  1. 必须用 ESM（import/export）
  2. 不能 CommonJS（require/module.exports）
  3. 生产模式（mode: "production"）

Tree Shaking 的原理：
  编译时分析 import/export
  标记哪些导出被使用了
  删除没有被使用的导出
~~~

~~~javascript
// ========== Tree Shaking 示例 ==========
// utils.js
export function 做菜(菜名) { return `${菜名}做好了`; }
export function 洗菜(菜名) { return `${菜名}洗干净了`; }
export function 切菜(菜名) { return `${菜名}切好了`; }

// main.js
import { 做菜 } from "./utils.js";
做菜("红烧肉");

// 打包后：
// 做菜 函数被保留 ✅
// 洗菜、切菜 函数被删除 ✅（没有被使用）

// ========== CommonJS 不能 Tree Shaking ==========
// utils.js
const 做菜 = (菜名) => `${菜名}做好了`;
const 洗菜 = (菜名) => `${菜名}洗干净了`;
module.exports = { 做菜, 洗菜 };

// 打包后：
// 做菜 和 洗菜 都被保留 ❌（CommonJS 是动态的，无法静态分析）
~~~

### 代码分割（Code Splitting）

**手写口诀：入口分割 / 动态导入 / SplitChunks**

~~~
三种代码分割方式：

方式1：多入口
  entry: { main: "./src/index.js", admin: "./src/admin.js }

方式2：动态导入（最常用）
  import("./模块.js") → 自动分割成独立的 chunk

方式3：SplitChunksPlugin（分割第三方库）
  把 node_modules 里的库打包成单独的 chunk
~~~

~~~javascript
// ========== 动态导入（路由懒加载） ==========
const 菜品页 = () => import("./views/Menu.vue");
const 关于页 = () => import("./views/About.vue");

// 打包后：
// main.js        → 主包
// Menu.xxx.js    → 菜品页的 chunk（访问时才加载）
// About.xxx.js   → 关于页的 chunk（访问时才加载）

// ========== SplitChunksPlugin 配置 ==========
// webpack.config.js
module.exports = {
  optimization: {
    splitChunks: {
      chunks: "all",              // 分割所有类型的 chunk
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,  // 第三方库
          name: "vendor",
          chunks: "all",
          priority: 10
        },
        common: {
          name: "common",
          minChunks: 2,            // 至少被 2 个 chunk 引用
          chunks: "all",
          priority: 5
        }
      }
    }
  }
};

// 打包后的文件：
// main.js      → 业务代码
// vendor.js    → vue, vue-router, axios 等第三方库
// common.js    → 多个页面共用的代码
// Menu.js      → 菜品页的代码
// About.js     → 关于页的代码
~~~

## 套路五：工程化实践

### Babel（ES6+ → ES5）

**手写口诀：Babel = 语法转换 + Polyfill（API 兼容）**

~~~
Babel 的工作流程：
  1. 解析（Parse）：源码 → AST（抽象语法树）
  2. 转换（Transform）：AST → 新的 AST
  3. 生成（Generate）：新的 AST → 新的代码
~~~

~~~javascript
// ========== Babel 配置 ==========
// babel.config.js
module.exports = {
  presets: [
    [
      "@babel/preset-env",       // 智能预设（根据目标环境自动确定需要哪些转换）
      {
        targets: "> 0.25%, not dead",  // 目标浏览器
        useBuiltIns: "usage",           // 按需引入 polyfill
        corejs: 3                       // core-js 版本
      }
    ],
    "@babel/preset-typescript",    // TypeScript 支持
    "@babel/preset-react"          // React JSX 支持
  ],
  plugins: [
    "@babel/plugin-proposal-decorators",  // 装饰器语法
    "@babel/plugin-proposal-class-properties"  // 类属性
  ]
};
~~~

~~~
Babel 的三个核心概念：

1. preset（预设）= 一组 plugin 的集合
   @babel/preset-env     → ES6+ → ES5
   @babel/preset-react   → JSX → React.createElement
   @babel/preset-typescript → TS → JS

2. plugin（插件）= 单个语法转换
   @babel/plugin-transform-arrow-functions → 箭头函数 → 普通函数
   @babel/plugin-transform-classes         → class → function

3. polyfill（垫片）= 补全缺失的 API
   Promise / Array.from / Object.assign 等
   @babel/polyfill（旧方案，整个引入）
   core-js + useBuiltIns: "usage"（新方案，按需引入）
~~~

### CI/CD（持续集成 / 持续部署）

**手写口诀：代码 push → 自动检查 → 自动构建 → 自动部署**

~~~
CI（持续集成）= Continuous Integration
  每次 push 代码 → 自动跑 lint + 测试 + 构建
  确保代码质量，尽早发现问题

CD（持续部署）= Continuous Deployment
  构建成功 → 自动部署到服务器
  减少人工操作，快速上线
~~~

~~~yaml
# ========== GitHub Actions 配置 ==========
# .github/workflows/deploy.yml

name: CI/CD Pipeline

on:
  push:
    branches: [main]       # push 到 main 分支时触发
  pull_request:
    branches: [main]       # PR 到 main 分支时触发

jobs:
  # ========== 第1个 Job：检查（CI） ==========
  check:
    runs-on: ubuntu-latest

    steps:
      # 拉取代码
      - name: Checkout code
        uses: actions/checkout@v4

      # 安装 Node.js
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: "pnpm"          # 缓存 pnpm 依赖

      # 安装 pnpm
      - name: Install pnpm
        uses: pnpm/action-setup@v2
        with:
          version: 8

      # 安装依赖
      - name: Install dependencies
        run: pnpm install

      # 代码检查
      - name: Lint
        run: pnpm lint

      # 单元测试
      - name: Test
        run: pnpm test

      # 构建
      - name: Build
        run: pnpm build

      # 上传构建产物
      - name: Upload build artifacts
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist

  # ========== 第2个 Job：部署（CD） ==========
  deploy:
    needs: check              # 依赖 check job（check 通过才执行）
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'  # 只在 main 分支部署

    steps:
      # 下载构建产物
      - name: Download build artifacts
        uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist

      # 部署到服务器（示例：用 rsync 同步到远程服务器）
      - name: Deploy to server
        uses: easingthemes/ssh-deploy@v4
        with:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          REMOTE_HOST: ${{ secrets.REMOTE_HOST }}
          REMOTE_USER: ${{ secrets.REMOTE_USER }}
          SOURCE: "dist/"
          TARGET: "/var/www/html/"

      # 通知（可选：发钉钉/飞书/Slack 通知）
      - name: Notify
        run: echo "部署完成！"
~~~

~~~
CI/CD 的完整流程：

  开发者 push 代码到 GitHub
    ↓
  GitHub Actions 自动触发
    ↓
  Job 1（check）：
    1. 拉取代码
    2. 安装依赖（pnpm install，带缓存）
    3. 代码检查（ESLint）
    4. 单元测试（Vitest）
    5. 构建（pnpm build）
    → 全部通过 → 继续
    → 有失败 → 停止，通知开发者
    ↓
  Job 2（deploy）：
    1. 下载构建产物
    2. 部署到服务器
    3. 发通知
    → 部署完成
~~~

### 前端监控

~~~
前端监控的三个方面：

1. 错误监控（异常捕获）
   - JS 运行时错误 → window.onerror
   - Promise 未捕获错误 → unhandledrejection
   - 资源加载错误 → addEventListener("error", ..., true)
   - Vue/React 错误边界

2. 性能监控
   - FCP（First Contentful Paint）→ 首次内容绘制
   - LCP（Largest Contentful Paint）→ 最大内容绘制
   - FID（First Input Delay）→ 首次输入延迟
   - CLS（Cumulative Layout Shift）→ 累积布局偏移

3. 行为监控
   - PV/UV（页面访问量/独立访客）
   - 点击事件
   - 页面停留时间
   - 接口请求成功率
~~~

~~~javascript
// ========== 错误监控（简化版） ==========
class 前端监控 {
  constructor(上报地址) {
    this.上报地址 = 上报地址;
    this.初始化();
  }

  初始化() {
    // 1. JS 运行时错误
    window.onerror = (消息, 文件, 行号, 列号, 错误) => {
      this.上报({
        类型: "js-error",
        消息,
        文件,
        行号,
        列号,
        堆栈: 错误?.stack
      });
    };

    // 2. Promise 未捕获错误
    window.addEventListener("unhandledrejection", (事件) => {
      this.上报({
        类型: "promise-error",
        消息: 事件.reason?.message || 事件.reason
      });
    });

    // 3. 资源加载错误
    window.addEventListener("error", (事件) => {
      if (事件.target.tagName) {
        this.上报({
          类型: "resource-error",
          标签: 事件.target.tagName,
          地址: 事件.target.src || 事件.target.href
        });
      }
    }, true);

    // 4. 性能监控
    this.性能监控();
  }

  性能监控() {
    // FCP
    new PerformanceObserver((列表) => {
      const entries =列表.getEntriesByName("first-contentful-paint");
      if (entries.length > 0) {
        this.上报({ 类型: "性能", 指标: "FCP", 值: entries[0].startTime });
      }
    }).observe({ type: "paint", buffered: true });

    // LCP
    new PerformanceObserver((列表) => {
      const entries = 列表.getEntries();
      const 最后一个 = entries[entries.length - 1];
      this.上报({ 类型: "性能", 指标: "LCP", 值: 最后一个.startTime });
    }).observe({ type: "largest-contentful-paint", buffered: true });
  }

  上报(数据) {
    const 完整数据 = {
      ...数据,
      页面: location.href,
      时间: Date.now(),
      用户代理: navigator.userAgent
    };

    // 用 sendBeacon 上报（不阻塞页面卸载）
    navigator.sendBeacon(this.上报地址, JSON.stringify(完整数据));

    // 或者用图片打点
    // new Image().src = `${this.上报地址}?data=${encodeURIComponent(JSON.stringify(完整数据))}`;
  }
}

// 使用
new 前端监控("https://monitor.example.com/report");
~~~

## 套路六：Monorepo 与包管理

### Monorepo（单一仓库管理多个项目）

**手写口诀：一个仓库，多个包，共享依赖，独立构建**

~~~
Monorepo vs Multirepo：

  Multirepo（传统方式）：
    项目A → 仓库A
    项目B → 仓库B
    共享代码 → 发 npm 包
    → 问题：共享代码改了要发版、各仓库同步麻烦

  Monorepo（现代方式）：
    根目录/
    ├── packages/
    │   ├── shared/          → 共享组件/工具库
    │   ├── web-app/         → 前端项目A
    │   └── admin-app/       → 前端项目B
    ├── package.json
    └── pnpm-workspace.yaml
    → 优势：共享代码直接引用、统一版本管理、统一构建流程
~~~

~~~
Monorepo 的核心工具链：

  1. pnpm workspace → 依赖管理（推荐）
     pnpm 原生支持 workspace，配置最简单

  2. Turborepo → 构建缓存和任务编排
     自动缓存构建结果，只重新构建变化的包
     支持并行构建多个包

  3. Nx → 类似 Turborepo，功能更丰富
     支持增量构建、依赖图分析
     适合超大型 Monorepo

  4. Lerna → 版本管理（旧方案，正在被替代）
     统一管理多个包的版本号
     批量发布到 npm
~~~

~~~javascript
// ========== pnpm workspace 配置 ==========
// pnpm-workspace.yaml
packages:
  - "packages/*"        // packages 目录下都是独立的包
  - "apps/*"            // apps 目录下都是独立的应用

// 根目录 package.json
{
  "name": "my-monorepo",
  "private": true,
  "scripts": {
    "dev": "pnpm --filter web-app dev",           // 只启动 web-app
    "build": "pnpm --filter ./packages/* build",  // 构建所有 packages
    "lint": "pnpm -r lint"                         // 递归执行所有包的 lint
  }
}

// ========== Turborepo 配置 ==========
// turbo.json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],     // 先构建依赖的包
      "outputs": ["dist/**"]       // 缓存这些输出文件
    },
    "lint": {
      "dependsOn": ["^build"]      // lint 依赖 build
    },
    "dev": {
      "cache": false               // dev 不缓存
    }
  }
}

// ========== 项目间引用 ==========
// packages/web-app/package.json
{
  "dependencies": {
    "@my-monorepo/shared": "workspace:*"  // 引用同仓库的 shared 包
  }
}

// 在代码中直接导入
import { 做菜 } from "@my-monorepo/shared";
// pnpm 会创建符号链接，直接指向 packages/shared
~~~

  my-monorepo/
  ├── apps/
  │   ├── web/              → 前端项目（Vue3 + Vite）
  │   │   ├── src/
  │   │   ├── package.json

  │   │   ├── package.json
  │   │   └── tsconfig.json
  │   ├── ui-components/    → 共享 UI 组件库
  │   │   ├── src/
  │   │   ├── package.json
  │   │   └── vite.config.ts
  │   └── eslint-config/    → 共享 ESLint 配置

### 包管理工具对比（npm vs pnpm vs yarn）

**手写口诀：pnpm 用硬链接 + 符号链接，最省磁盘空间**

~~~
三个包管理工具的安装方式对比：

  npm：
    node_modules/A/node_modules/B  → 每个项目都有一份 B 的副本
    → 嵌套安装，磁盘空间浪费
    → 可能出现"幽灵依赖"（能访问没在 package.json 声明的包）

  yarn：
    node_modules/B → 扁平安装，提升到顶层
    → 解决了嵌套问题
    → 但幽灵依赖问题依然存在

  pnpm：
    全局 store → 硬链接 → 项目 node_modules → 符号链接
    → 硬链接：同一份文件在磁盘上只存一份（最省空间）
    → 符号链接：项目只能访问自己声明的依赖（杜绝幽灵依赖）
~~~

~~~
硬链接 vs 符号链接：

  硬链接（Hard Link）：
    多个文件名指向同一个磁盘上的数据块
    删除其中一个文件名，数据不会被删除（还有其他引用）
    不能跨文件系统
    → pnpm 用硬链接把全局 store 的文件"链接"到项目的 node_modules

  符号链接（Symbolic Link / 软链接）：
    一个文件指向另一个文件的路径（类似快捷方式）
    删除原文件，符号链接就失效
    可以跨文件系统
    → pnpm 用符号链接让项目的 node_modules 里的包指向硬链接的实际位置
~~~

~~~
pnpm 的安装过程：

  1. 下载包到全局 store（~/.pnpm-store）
     ~/.pnpm-store/
     ├── A@1.0.0/
     └── B@2.0.0/

  2. 从 store 硬链接到项目的 node_modules/.pnpm/
     node_modules/.pnpm/
     ├── A@1.0.0/node_modules/A/ → 硬链接 → ~/.pnpm-store/A@1.0.0/
     └── B@2.0.0/node_modules/B/ → 硬链接 → ~/.pnpm-store/B@2.0.0/

  3. 用符号链接把项目能访问的包放到 node_modules/ 顶层
     node_modules/
     ├── A → 符号链接 → .pnpm/A@1.0.0/node_modules/A
     └（项目只能访问 package.json 声明的 A，不能访问 B）

  结果：
    10 个项目用同一个版本的 vue → 磁盘上只有 1 份 vue 文件
    项目 A 声明了 vue 但没声明 lodash → 不能 import lodash（杜绝幽灵依赖）
~~~

### lock 文件

~~~
lock 文件的作用：
  锁定依赖的精确版本，确保所有人安装的依赖版本一致

  npm → package-lock.json
  yarn → yarn.lock
  pnpm → pnpm-lock.yaml

为什么需要 lock 文件？
  没有 lock 文件：
    package.json: "vue": "^3.2.0"
    开发者A 安装 → vue@3.2.47
    开发者B 安装 → vue@3.3.0（新版本发布了）
    → 两个人的依赖版本不同 → 可能出现"我电脑上能跑"的问题

  有 lock 文件：
    lock 文件记录了 vue@3.2.47 的精确版本
    所有人安装 → 都是 vue@3.2.47
    → 版本一致，行为一致

lock 文件该不该提交到 Git？
  应用项目 → ✅ 必须提交（确保团队成员和 CI 环境一致）
  库项目   → ❌ 不提交（库的依赖由使用者的项目决定）
~~~

## 高频面试题

### 题目1：Loader 和 Plugin 的区别

~~~
Loader：
  本质是函数
  作用是转换文件（A → B）
  在 module.rules 里配置
  执行顺序：从右到左，从下到上

Plugin：
  本质是类（有 apply 方法）
  作用是扩展功能（在特定时机执行逻辑）
  在 plugins 里配置
  通过 compiler.hooks 监听构建事件
~~~

### 题目2：Webpack 的构建流程

~~~
1. 初始化：读取配置，创建 compiler 对象
2. 编译：从 entry 开始，递归分析依赖
3. 模块构建：每个模块用对应的 Loader 转换
4. 依赖图：构建完整的依赖关系图
5. 输出：根据配置生成 bundle 文件

关键概念：
  Entry → 入口文件
  Output → 输出配置
  Loader → 文件转换
  Plugin → 功能扩展
  Module → 每个文件都是一个模块
  Chunk → 一组模块的集合
  Bundle → 最终输出的文件
~~~

### 题目3：Webpack 热更新原理

~~~
HMR（Hot Module Replacement）的原理：

1. 启动 WebSocket 连接（dev server 和浏览器之间）
2. 文件变化 → Webpack 重新编译变化的模块
3. 通过 WebSocket 通知浏览器："有模块更新了"
4. 浏览器向 dev server 请求更新后的模块
5. HMR 运行时替换旧模块（不刷新页面）

为什么更新快？
  只重新编译变化的模块
  不需要重新打包整个项目
  不刷新页面（保持状态）
~~~

### 题目4：什么是 Source Map？

~~~
Source Map = 源码映射

问题：打包后的代码被压缩/转换了，报错时行号对不上
解决：Source Map 记录了打包后代码 → 源码的映射关系
      浏览器可以用它显示原始源码的报错位置

配置：
  devtool: "source-map"        → 完整映射（最慢，最准）
  devtool: "cheap-module-source-map" → 不映射列（更快）
  devtool: "eval-source-map"   → 用 eval（开发推荐）
  devtool: "hidden-source-map" → 不在 bundle 里引用（生产推荐）
  devtool: false               → 不生成（最快）

开发环境：eval-source-map（快速 + 准确）
生产环境：hidden-source-map（生成但不暴露源码）
~~~

### 题目5：Monorepo 是什么？为什么用 pnpm？

~~~
Monorepo = 单一仓库管理多个项目/包

优势：
  1. 共享代码直接引用，不需要发 npm 包
  2. 统一版本管理、统一构建流程
  3. 原子提交（一个 commit 改多个包，保证一致性）

为什么用 pnpm？
  1. pnpm 原生支持 workspace，配置最简单
  2. 硬链接 + 符号链接 → 最省磁盘空间
  3. 严格模式 → 杜绝幽灵依赖
  4. 安装速度快（全局 store 缓存）

工具选择：
  pnpm workspace → 依赖管理（推荐）
  Turborepo → 构建缓存和任务编排
  Nx → 超大型 Monorepo
  Lerna → 版本管理（旧方案）
~~~

### 题目6：pnpm 的硬链接和符号链接是什么？

~~~
硬链接（Hard Link）：
  多个文件名指向同一个磁盘数据块
  省空间：10 个项目用同一个版本的 vue → 磁盘上只有 1 份
  pnpm 把全局 store 的包硬链接到项目的 node_modules/.pnpm/

符号链接（Symbolic Link）：
  类似快捷方式，指向另一个文件的路径
  pnpm 用符号链接让项目只能访问 package.json 声明的依赖
  → 杜绝幽灵依赖（不能访问没声明的包）
~~~

### 题目7：CI/CD 是什么？

~~~
CI（持续集成）= Continuous Integration
  每次 push 代码 → 自动跑 lint + 测试 + 构建
  尽早发现问题，确保代码质量

CD（持续部署）= Continuous Deployment
  构建成功 → 自动部署到服务器
  减少人工操作，快速上线

常见工具：
  GitHub Actions → GitHub 原生 CI/CD
  GitLab CI → GitLab 原生 CI/CD
  Jenkins → 自建 CI/CD 服务器

GitHub Actions 的核心概念：
  Workflow → 工作流（一个 YAML 文件）
  Job → 任务（可以并行执行）
  Step → 步骤（Job 里的具体操作）
  Action → 复用的步骤（社区提供的）
~~~

## 终极记忆卡片

~~~
套路1：构建工具原理
  Webpack → 入口开始递归分析依赖 → Loader 转换 → Plugin 扩展 → 输出 bundle
  Vite → 利用浏览器原生 ESM → 不打包按需编译 → esbuild 预构建 → 启动飞快
  区别 → Webpack 先打包再启动，Vite 先启动再按需编译
  Vite 插件 → 基于 Rollup 钩子接口，transform/configureServer/buildStart

套路2：模块化
  CommonJS → require / module.exports → 同步加载 → 值的拷贝
  ESM → import / export → 异步加载 → 值的引用（活绑定）
  Tree Shaking → 只支持 ESM → 删除未使用的导出
  循环依赖 → CommonJS 返回不完整导出，ESM 用活绑定但可能执行顺序问题

套路3：Loader 与 Plugin
  Loader → 函数 → 转换文件（A→B）→ module.rules
  Plugin → 类 + apply → 扩展功能 → plugins + compiler.hooks

套路4：代码优化
  Tree Shaking → ESM 静态分析删除无用代码
  代码分割 → 动态 import / SplitChunksPlugin
  压缩 → Terser(JS) + CssMinimizer(CSS) + Gzip/Brotli

套路5：工程化实践
  Babel → AST 三步走（解析→转换→生成）+ preset-env 按需 polyfill
  ESLint → 代码规范 + Prettier 格式化
  Git 规范 → Conventional Commits + husky + lint-staged
  CI/CD → GitHub Actions（push → lint + test + build → deploy）
  前端监控 → 错误监控 + 性能监控 + 行为监控

套路6：Monorepo 与包管理
  Monorepo → 单仓库多项目，共享代码直接引用
  pnpm workspace → 硬链接省空间 + 符号链接杜绝幽灵依赖
  Turborepo → 构建缓存 + 任务编排
  lock 文件 → 锁定精确版本，确保一致性（应用项目必须提交）
  npm vs pnpm vs yarn → pnpm 最省空间、最快、最严格

高频面试题
  Loader vs Plugin → 函数转换文件 vs 类扩展功能
  Webpack 流程 → 初始化→编译→模块构建→依赖图→输出
  HMR → WebSocket 通知 + 模块替换（不刷新页面）
  Source Map → 源码映射（开发用 eval-source-map，生产用 hidden-source-map）
  Monorepo → 单仓库多项目（pnpm workspace + Turborepo）
  硬链接 vs 符号链接 → 同一数据块 vs 快捷方式
  CI/CD → push → 自动检查 → 自动构建 → 自动部署
~~~
