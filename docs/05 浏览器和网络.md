套路1：从输入 URL 到页面展示 → DNS / TCP / HTTP / 渲染

## 套路一：从输入 URL 到页面展示（必考）

### 整体流程（10 步）

~~~
1. 输入 URL → 浏览器判断是搜索还是 URL
2. DNS 解析 → 把域名翻译成 IP 地址
3. TCP 三次握手 → 建立连接
4. TLS 握手（HTTPS）→ 加密通道
5. 发送 HTTP 请求 → 拿到响应
6. 浏览器解析 HTML → 构建 DOM 树
7. 浏览器解析 CSS → 构建 CSSOM 树
8. 合成渲染树 → 确定布局
9. 绘制页面 → 像素上屏
10. JS 执行 → 可能修改 DOM/CSSOM → 重新渲染
~~~

### 第1步：DNS 解析（域名 → IP）

**手写口诀：浏览器缓存 → 系统缓存 → 路由器 → ISP → 根 DNS**

~~~
DNS 解析过程（逐级查找）：

  浏览器 DNS 缓存（chrome://net-internals/#dns）
    ↓ 没找到
  操作系统 DNS 缓存（hosts 文件）
    ↓ 没找到
  路由器 DNS 缓存
    ↓ 没找到
  ISP（运营商）DNS 缓存
    ↓ 没找到
  根域名服务器 → 顶级域名服务器 → 权威域名服务器
    ↓ 最终拿到 IP 地址

DNS 解析的结果：
  www.baidu.com → 110.242.68.3（IP 地址）
~~~

#### CDN 原理

~~~
CDN = Content Delivery Network（内容分发网络）

原理：把静态资源缓存到全球各地的边缘节点
用户访问时，从最近的节点获取资源（减少延迟）

CDN 缓存与回源：
  1. 用户请求资源 → DNS 解析到最近的 CDN 节点
  2. CDN 节点有缓存 → 直接返回（命中）
  3. CDN 节点没有缓存 → 向源站请求（回源）→ 缓存到节点 → 返回给用户

CDN 适合什么资源？
  静态资源：JS/CSS/图片/字体/视频
  不适合：API 接口（动态内容，缓存没意义）
~~~

### 第2步：TCP 三次握手

**手写口诀：客户端问"你在吗"，服务端答"我在，你在吗"，客户端说"我在"**

~~~
三次握手的过程：

  客户端 → SYN（你好，我要连接）         → 服务端
  客户端 ← SYN + ACK（收到，我也准备好了）← 服务端
  客户端 → ACK（好的，开始通信）          → 服务端

为什么是三次而不是两次？
  防止已失效的连接请求到达服务端
  如果只有两次：客户端发了一个旧的 SYN，服务端以为是新连接，白白等待

为什么是三次而不是四次？
  三次已经足够确认双方都能收发数据
  四次会浪费资源
~~~

### 第3步：TLS 握手（HTTPS 才有）

~~~
HTTPS = HTTP + TLS/SSL（加密）

TLS 握手过程（4 步）：
  第1步 客户端 → 服务端：发送支持的加密算法列表 + 随机数A
  第2步 服务端 → 客户端：选择算法 + 发送数字证书（含公钥）+ 随机数B
  第3步 客户端 → 服务端：验证证书 → 生成随机密钥（预主密钥）→ 用公钥加密后发送
  第4步 双方：用 随机数A + 随机数B + 预主密钥 生成会话密钥 → 对称加密通信

证书链验证过程：
  1. 服务端发送证书（含公钥 + 域名 + 有效期 + 签名）
  2. 浏览器检查证书是否过期
  3. 浏览器检查证书域名是否匹配
  4. 浏览器用 CA 的公钥验证证书签名
  5. 验证通过 → 信任这个证书

中间人攻击防御：
  HTTPS 通过数字证书 + 非对称加密 防止中间人攻击
  中间人没有服务端的私钥 → 无法解密预主密钥 → 无法伪造会话密钥

HTTP vs HTTPS：
  HTTP  → 明文传输（不安全）
  HTTPS → 加密传输（安全，但稍慢）
~~~

### 第4步：HTTP 请求与响应

~~~
请求报文：
  GET /api/菜品 HTTP/1.1
  Host: www.example.com
  Accept: application/json
  Cookie: session=abc123

响应报文：
  HTTP/1.1 200 OK
  Content-Type: application/json
  Cache-Control: max-age=3600
  Set-Cookie: session=abc123

  {"菜品": ["红烧肉", "麻婆豆腐"]}
~~~

### HTTP/1.1 vs HTTP/2 vs HTTP/3

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 连接 | 一个连接一个请求 | 一个连接多个请求（多路复用） | 基于 UDP（QUIC） |
| 头部 | 不压缩 | HPACK 压缩 | 压缩 |
| 服务器推送 | ❌ | ✅ | ✅ |
| 队头阻塞 | ✅ 有 | ✅ TCP 层有 | ❌ 没有 |
| 协议 | TCP | TCP | UDP（QUIC） |

~~~javascript
// ========== HTTP/1.1 的问题：队头阻塞 ==========
// 请求1: 菜品列表（慢，1秒）
// 请求2: 评价列表（快，100ms）
// 请求3: 推荐列表（快，200ms）

// HTTP/1.1：请求2和请求3要等请求1完成才能发送（队头阻塞）
// HTTP/2：三个请求同时发送，互不影响（多路复用）
// HTTP/3：基于 UDP，彻底解决队头阻塞
~~~

## 套路二：浏览器架构

### 浏览器多进程模型

**手写口诀：浏览器是多进程的，每个标签页通常是独立的渲染进程**

~~~
Chrome 的主要进程：

  1. 浏览器主进程（Browser Process）—— 只有 1 个
     - 负责：地址栏、书签、前进后退、网络请求、文件访问
     - 负责：创建和销毁其他进程
     - 负责：UI 渲染（工具栏、标签栏等浏览器界面）

  2. 渲染进程（Renderer Process）—— 每个标签页通常 1 个
     - 负责：解析 HTML/CSS、构建 DOM、执行 JS、布局、绘制
     - 核心线程：
       → 主线程（JS 执行、DOM 解析、布局、绘制）
       → 合成线程（Compositor Thread，分层合成）
       → 光栅化线程（Raster Thread，把图层转成位图）
     - 安全沙箱：渲染进程运行在沙箱中，不能访问硬盘、不能操作系统

  3. GPU 进程（GPU Process）—— 只有 1 个
     - 负责：3D CSS 变换、WebGL、页面合成
     - 负责：把渲染进程生成的位图输出到屏幕

  4. 网络进程（Network Process）—— 只有 1 个
     - 负责：所有网络请求（HTTP/HTTPS/WebSocket）
     - 以前在浏览器主进程里，后来独立出来

  5. 插件进程（Plugin Process）—— 每个插件 1 个
     - 负责：运行 Flash、PDF 阅读器等插件

为什么是多进程？
  1. 隔离性：一个标签页崩溃不影响其他标签页
  2. 安全性：渲染进程运行在沙箱中，恶意网页无法访问系统
  3. 性能：多进程可以利用多核 CPU

安全沙箱（Sandbox）：
  渲染进程被限制：不能读写硬盘、不能创建进程、不能访问网络（必须通过网络进程）
  即使网页有恶意代码，也无法危害用户系统
~~~

~~~
进程 vs 线程：
  进程 = 一个独立的程序（有自己的内存空间）
  线程 = 进程内的执行单元（共享进程的内存）

  一个进程可以有多个线程
  线程之间共享内存，进程之间不共享

  浏览器里：
    每个标签页 = 一个渲染进程（独立内存）
    渲染进程里的主线程 = JS 执行 + DOM 解析 + 布局 + 绘制（都是同一个线程）
    所以 JS 执行和布局/绘制是互斥的 → 长 JS 任务会阻塞页面渲染
~~~

### V8 引擎原理

**手写口诀：源码 → AST → 字节码 → 机器码（JIT 热点编译）**

~~~
V8 执行 JavaScript 的完整链路：

  源码（JavaScript 字符串）
    ↓  Parser（解析器）
  AST（抽象语法树）
    ↓  Ignition（解释器）
  字节码（Bytecode）
    ↓  执行字节码
  如果某段代码被频繁执行（热点代码）：
    ↓  TurboFan（优化编译器）
  机器码（Machine Code）→ 直接在 CPU 上执行，非常快
~~~

~~~
各阶段的作用：

  1. Parser（解析器）
     把 JS 源码解析成 AST（抽象语法树）
     两步：词法分析（Token）→ 语法分析（AST）

  2. Ignition（解释器）
     把 AST 转换成字节码
     字节码比源码更紧凑，但仍然是"中间代码"
     逐条解释执行字节码（比机器码慢，但启动快）

  3. TurboFan（优化编译器）
     把频繁执行的"热点"字节码编译成机器码
     机器码可以直接在 CPU 上执行（最快）
     如果类型假设失败（比如变量类型变了）→ 去优化 → 回退到字节码

为什么 JS 快？
  JIT（Just-In-Time）编译：不是一开始就编译所有代码
  而是先快速启动（解释执行），热点代码才编译成机器码
  兼顾了启动速度和执行速度
~~~

#### 测试

~~~javascript
// ========== V8 的优化和去优化 ==========
function 相加(a, b) { return a + b; }

// 第一次调用：a 和 b 都是数字 → TurboFan 优化成机器码
相加(1, 2);      // 数字 + 数字 → 优化
相加(3, 4);      // 数字 + 数字 → 继续优化
相加(5, 6);      // 热点函数 → 编译成机器码

// 突然传了字符串 → 类型假设失败 → 去优化（回退到字节码）
相加("红", "烧肉");  // 字符串 + 字符串 → 去优化，重新解释执行

// 启示：保持变量类型稳定，有助于 V8 优化
~~~

## 套路三：浏览器渲染机制

### 渲染流程（5 步）

**手写口诀：DOM + CSSOM → 渲染树 → 布局 → 绘制 → 合成**

~~~
1. 解析 HTML → 构建 DOM 树
2. 解析 CSS → 构建 CSSOM 树
3. DOM + CSSOM → 合成渲染树（Render Tree）
4. 布局（Layout/Reflow）→ 计算每个节点的位置和大小
5. 绘制（Paint）→ 把节点画到屏幕上
~~~

~~~
DOM 树：
  html
  ├── head
  └── body
      ├── div
      │   ├── h1 → "红烧肉"
      │   └── p → "38元"
      └── div
          └── p → "好吃"

CSSOM 树：
  body → { font-size: 14px }
  div → { margin: 10px }
  h1 → { color: red }

渲染树（只包含可见元素）：
  body
  ├── div
  │   ├── h1 → { color: red, 位置: (0,0), 大小: (100,30) }
  │   └── p → { 位置: (0,30), 大小: (100,20) }
  └── div
      └── p → { 位置: (0,60), 大小: (100,20) }

注意：display: none 的元素不在渲染树中
     visibility: hidden 的元素在渲染树中（占位但不可见）
~~~

### 重排（Reflow）和重绘（Repaint）

**手写口诀：重排必重绘，重绘不一定重排**

~~~
重排（Reflow）= 布局变了 → 重新计算位置和大小 → 性能影响大
  触发条件：
    - 元素尺寸变化（width/height/margin/padding/border）
    - 元素位置变化（float/position/display）
    - 内容变化（文字/图片大小变化导致容器尺寸变化）
    - 窗口大小变化（resize）
    - 读取布局属性（offsetWidth/offsetHeight/clientWidth/clientHeight/scrollTop）

重绘（Repaint）= 外观变了 → 重新绘制 → 性能影响小
  触发条件：
    - 颜色变化（color/background-color）
    - 阴影变化（box-shadow/text-shadow）
    - 可见性变化（visibility）
~~~

#### 测试

~~~javascript
// ========== 触发重排的例子 ==========
元素.style.width = "200px";   // 重排 + 重绘
元素.style.margin = "10px";   // 重排 + 重绘
元素.style.display = "none";  // 重排 + 重绘

// ========== 只触发重绘的例子 ==========
元素.style.color = "red";             // 只重绘
元素.style.backgroundColor = "blue";  // 只重绘
元素.style.visibility = "hidden";     // 只重绘

// ========== 避免强制同步布局（读写分离） ==========
// ❌ 读写交替 → 强制同步布局 → 多次重排
for (let i = 0; i < 100; i++) {
  const 高度 = 元素.offsetHeight;  // 读（触发重排）
  元素.style.height = 高度 + 1 + "px";  // 写（触发重排）
  // 每次循环都有一次读 + 一次写 = 100 次重排
}

// ✅ 先批量读，再批量写
const 高度们 = [];
for (let i = 0; i < 100; i++) {
  高度们.push(元素.offsetHeight);  // 只读
}
for (let i = 0; i < 100; i++) {
  元素.style.height = 高度们[i] + 1 + "px";  // 只写
}
// 只有 1 次重排
~~~

### 回流和重绘的优化策略

~~~
策略1：批量修改 DOM（减少重排次数）
  - 使用 DocumentFragment
  - 先 display:none，修改完再显示

策略2：使用 transform 代替 top/left
  - transform 只触发合成，不触发重排

策略3：使用 CSS contain 属性
  - contain: layout 限制重排范围

策略4：读写分离
  - 先批量读布局属性，再批量写

策略5：使用 will-change 提示浏览器
  - will-change: transform 提前优化
~~~

~~~javascript
// ========== DocumentFragment 批量插入 ==========
const fragment = document.createDocumentFragment();
for (let i = 0; i < 1000; i++) {
  const li = document.createElement("li");
  li.textContent = `菜品${i}`;
  fragment.appendChild(li);  // 不触发重排
}
document.querySelector("ul").appendChild(fragment);  // 只触发一次重排

// ========== transform vs top/left ==========
// ❌ top/left → 触发重排
元素.style.top = "100px";

// ✅ transform → 只触发合成（GPU 加速）
元素.style.transform = "translateY(100px)";

// ========== 先隐藏再显示 ==========
列表.style.display = "none";     // 隐藏
// ... 批量修改 DOM ...
列表.style.display = "block";    // 显示（只有一次重排）
~~~

## 套路四：浏览器缓存

### 缓存的分类

~~~
强缓存：不需要问服务器，直接用缓存
  浏览器直接从本地缓存读取，不发 HTTP 请求

协商缓存：要问服务器"缓存还能用吗"
  浏览器发请求问服务器，服务器说"没变" → 用缓存
  服务器说"变了" → 返回新内容

优先级：强缓存 > 协商缓存 > 正常请求
~~~

### 强缓存

**手写口诀：Cache-Control 是主力，Expires 是旧方案**

~~~
响应头：
  Cache-Control: max-age=3600    → 3600 秒内直接用缓存
  Expires: Thu, 01 Jan 2025...   → 到期时间（旧方案，有时区问题）

两者同时存在时，Cache-Control 优先级更高
~~~

~~~
强缓存的判断流程：

  1. 有 Cache-Control？
     → 有 max-age → 当前时间 < 过期时间？→ 是 → 直接用缓存 ✅
     → 有 no-cache → 跳过强缓存，走协商缓存
     → 有 no-store → 不缓存，每次都请求
  2. 没有 Cache-Control？
     → 有 Expires？→ 当前时间 < 到期时间？→ 是 → 直接用缓存 ✅
  3. 都没有？→ 走协商缓存
~~~

#### 测试

~~~javascript
// ========== Cache-Control 的常用值 ==========
"Cache-Control: max-age=3600"     // 缓存 1 小时
"Cache-Control: no-cache"         // 不用强缓存，走协商缓存
"Cache-Control: no-store"         // 完全不缓存
"Cache-Control: public"           // CDN 可以缓存
"Cache-Control: private"          // 只有浏览器可以缓存
"Cache-Control: max-age=31536000" // 缓存 1 年（适合静态资源）
~~~

### 协商缓存

**手写口诀：Last-Modified + If-Modified-Since 是旧方案，ETag + If-None-Match 是新方案**

~~~
协商缓存的过程（Last-Modified 方案）：

  第1次请求：
    服务器返回：Last-Modified: Thu, 01 Jan 2025 00:00:00 GMT
    浏览器记住这个时间

  第2次请求（缓存过期了）：
    浏览器发：If-Modified-Since: Thu, 01 Jan 2025 00:00:00 GMT
    服务器检查：文件修改时间变了吗？
      没变 → 304 Not Modified（用缓存）
      变了 → 200 OK + 新内容

协商缓存的过程（ETag 方案）：

  第1次请求：
    服务器返回：ETag: "abc123"（文件内容的哈希值）
    浏览器记住这个值

  第2次请求：
    浏览器发：If-None-Match: "abc123"
    服务器检查：文件内容的哈希值变了吗？
      没变 → 304 Not Modified（用缓存）
      变了 → 200 OK + 新内容（新 ETag）
~~~

### 完整缓存流程图

~~~
浏览器发请求
  │
  ├─ 有强缓存？（Cache-Control / Expires 未过期）
  │   → 是 → 直接用缓存（200 from cache，不发请求）
  │   → 否 ↓
  │
  ├─ 发请求，带 If-None-Match / If-Modified-Since
  │   │
  │   ├─ 服务器检查：资源变了吗？
  │   │   → 没变 → 304 Not Modified（用缓存）
  │   │   → 变了 → 200 OK + 新内容 + 新缓存头
  │   │
  │   └─ 服务器没有缓存相关头
  │       → 200 OK + 新内容
~~~

#### 测试

~~~javascript
// ========== 实际开发中的缓存策略 ==========

// HTML 文件：no-cache（每次都协商，确保拿到最新版本）
"Cache-Control: no-cache"

// CSS/JS 文件（带 hash）：max-age=31536000（缓存 1 年）
// 文件名变了 → 浏览器当新资源请求
// 文件名没变 → 直接用缓存
"Cache-Control: max-age=31536000, immutable"

// 图片：max-age=86400（缓存 1 天）
"Cache-Control: max-age=86400"

// API 接口：no-store（不缓存）
"Cache-Control: no-store"
~~~

## 套路五：浏览器存储与 Token 方案

### Cookie、localStorage、sessionStorage 的区别

| | Cookie | localStorage | sessionStorage |
|---|---|---|---|
| 大小 | 4KB | 5MB | 5MB |
| 有效期 | 可设置过期时间 | 永久（手动删除） | 关闭标签页就清除 |
| 发送到服务器 | ✅ 每次请求自动带上 | ❌ 不会 | ❌ 不会 |
| 访问限制 | 同源 | 同源 | 同源 + 同标签页 |
| API | document.cookie | localStorage.getItem/setItem | sessionStorage.getItem/setItem |

~~~javascript
// ========== Cookie 的常用属性 ==========
document.cookie = "name=红烧肉; max-age=3600; path=/; secure; samesite=lax; httponly"

// max-age / expires：过期时间
// path：可访问的路径
// domain：可访问的域名
// secure：只在 HTTPS 下发送
// samesite：限制跨站发送（strict/lax/none）
// httponly：JS 不能读取（防止 XSS 窃取）
~~~

### Token 存储方案：Cookie vs localStorage

**面试必答：JWT 存在哪里？两种方案的安全性权衡**

#### JWT 的结构

~~~
JWT（JSON Web Token）由三段用 "." 分隔的 Base64URL 编码组成：

  Header.Payload.Signature

  Header（头部）：
    { "alg": "HS256", "typ": "JWT" }
    → 指定签名算法和 Token 类型

  Payload（载荷）：
    { "userId": 123, "name": "老王", "exp": 1700000000 }
    → 存放用户信息 + 过期时间
    → 注意：Payload 只是 Base64 编码，不是加密，任何人都能解码看到内容

  Signature（签名）：
    用 Header 指定的算法，对 Header + Payload + 密钥 进行签名
    → 作用：防篡改（修改 Header 或 Payload 后签名就不对了）

前端使用方式：
  登录后后端返回 Token → 前端存起来
  后续请求在 Header 中带上：Authorization: Bearer <token>
  后端验证签名和过期时间 → 通过则返回数据
~~~

#### 方案1：JWT 存 Cookie

~~~
优点：
  - 自动携带（每次请求浏览器自动带上）
  - 可以设 HttpOnly → JS 无法读取 → 防止 XSS 窃取
  - 可以设 SameSite → 防止 CSRF

缺点：
  - 容易受到 CSRF 攻击（浏览器自动带上 Cookie）
  - 4KB 大小限制
  - 需要服务端配合设置

安全配置：
  HttpOnly: true   → JS 不能读取（防 XSS）
  Secure: true     → 只在 HTTPS 下发送
  SameSite: Lax    → 限制跨站发送（防 CSRF）
~~~

#### 方案2：JWT 存 localStorage

~~~
优点：
  - 不会自动发送 → 不受 CSRF 攻击
  - 5MB 大小，足够大
  - 使用简单（前端自己控制）

缺点：
  - JS 可以读取 → XSS 攻击可能窃取 Token
  - 不会自动携带 → 每次请求需要手动加到 Header 里

使用方式：
  localStorage.setItem("token", "eyJhbG...");
  // 每次请求带上
  fetch("/api/菜品", { headers: { Authorization: `Bearer ${token}` } });
~~~

#### 怎么选？

~~~
安全性要求高（金融/支付）→ Cookie + HttpOnly + SameSite + CSRF Token
一般项目 → localStorage + 防御 XSS（输入转义 + CSP）
最佳实践 → Cookie 存 Token（HttpOnly），前端不用管
~~~

## 套路六：跨域与安全

### 什么是跨域？

~~~
同源策略：协议 + 域名 + 端口，三者必须完全相同

同源：
  http://localhost:3000/page1 → http://localhost:3000/page2 ✅

跨域：
  http://localhost:3000 → https://localhost:3000  ❌（协议不同）
  http://localhost:3000 → http://localhost:4000   ❌（端口不同）
  http://localhost:3000 → http://example.com:3000  ❌（域名不同）
~~~

### 跨域的 6 种解决方案

**手写口诀：CORS 是正道，代理是开发用，JSONP 是老方案**

#### 方案1：CORS（正道）

~~~
CORS = Cross-Origin Resource Sharing
服务端设置响应头，告诉浏览器"允许跨域"

简单请求：
  GET/POST/HEAD + 简单头部 → 浏览器直接发
  服务端返回：Access-Control-Allow-Origin: http://localhost:3000

预检请求（复杂请求）：
  PUT/DELETE/自定义头部/JSON Content-Type
  → 浏览器先发 OPTIONS 请求询问服务端是否允许
  → 服务端返回允许 → 浏览器再发真正的请求
~~~

~~~javascript
// ========== 服务端设置 CORS ==========
// Node.js (Express)
app.use((req, res, next) => {
  res.header("Access-Control-Allow-Origin", "http://localhost:3000");
  res.header("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE");
  res.header("Access-Control-Allow-Headers", "Content-Type, Authorization");
  res.header("Access-Control-Allow-Credentials", "true");  // 允许携带 Cookie
  if (req.method === "OPTIONS") {
    return res.sendStatus(200);  // 预检请求直接返回
  }
  next();
});
~~~

#### 方案2：开发代理（开发环境最常用）

~~~javascript
// ========== Vite 配置代理 ==========
// vite.config.js
export default {
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:8080",  // 后端地址
        changeOrigin: true,               // 修改请求头的 Origin
        rewrite: (path) => path.replace(/^\/api/, "")
      }
    }
  }
};

// 前端请求：fetch("/api/菜品")
// Vite 代理：转发到 http://localhost:8080/菜品
// 不跨域了（同源请求）
~~~

#### 方案3：JSONP（老方案，只能 GET）

~~~javascript
// ========== JSONP 原理 ==========
// 利用 <script> 标签不受同源策略限制

function jsonp(url, callback) {
  return new Promise((resolve) => {
    const 函数名 = "callback_" + Date.now();
    window[函数名] = (数据) => {
      resolve(数据);
      document.head.removeChild(script);
      delete window[函数名];
    };
    const script = document.createElement("script");
    script.src = `${url}?callback=${函数名}`;
    document.head.appendChild(script);
  });
}

// 使用
jsonp("http://api.example.com/菜品").then(数据 => console.log(数据));
// 服务端返回：callback_123({"菜品": ["红烧肉"]})

// 问题：只支持 GET，有安全风险（XSS）
~~~

### 安全：XSS 和 CSRF

**手写口诀：XSS 注入脚本，CSRF 伪造请求**

#### XSS（跨站脚本攻击）

~~~
XSS = Cross-Site Scripting
攻击者把恶意脚本注入到页面中

类型：
  1. 存储型 XSS：恶意脚本存到服务器数据库（评论区注入 <script>）
  2. 反射型 XSS：恶意脚本在 URL 参数中（搜索框注入）
  3. DOM 型 XSS：前端 JS 直接操作 DOM 插入恶意内容

防御：
  1. 转义用户输入（< → &lt; > → &gt;）
  2. CSP（Content Security Policy）限制脚本来源
  3. HttpOnly Cookie（JS 不能读取 Cookie）
  4. 输入校验
~~~

#### CSRF（跨站请求伪造）

~~~
CSRF = Cross-Site Request Forgery
攻击者诱导用户在已登录的网站上执行恶意请求

攻击过程：
  1. 用户登录了银行网站（Cookie 里有 session）
  2. 用户访问恶意网站
  3. 恶意网站自动发起请求到银行网站
  4. 浏览器自动带上 Cookie → 银行以为是用户操作

防御：
  1. CSRF Token（服务端生成随机 token，请求时验证）
  2. SameSite Cookie（限制 Cookie 的跨站发送）
  3. 验证 Referer / Origin 头
  4. 双重 Cookie 验证
~~~

### SameSite Cookie 属性详解

~~~
SameSite 的三个值：

  Strict（严格）：
    完全禁止第三方网站发送 Cookie
    从外部链接点进来也不会带 Cookie
    → 最安全，但用户体验差（从搜索引擎点进来要重新登录）

  Lax（宽松，默认值）：
    大部分第三方请求不带 Cookie
    但<a>链接、GET 表单、预加载请求会带
    → 安全和体验的平衡（推荐）

  None（不限制）：
    所有请求都带 Cookie
    必须同时设置 Secure（只在 HTTPS 下）
    → 最不安全，只有特殊场景需要
~~~

## 套路七：实时通信：轮询 / SSE / WebSocket

**手写口诀：轮询最简单，SSE 服务端单向推送，WebSocket 双向通信**

### 三种方案对比

| | 轮询（Polling） | SSE（Server-Sent Events） | WebSocket |
|---|---|---|---|
| 方向 | 客户端 → 服务端 | 服务端 → 客户端（单向） | 双向 |
| 协议 | HTTP | HTTP | 独立协议（ws://） |
| 实时性 | 差（取决于轮询间隔） | 好（服务端主动推送） | 最好（双向实时） |
| 实现复杂度 | 最简单 | 简单 | 较复杂 |
| 自动重连 | 需要自己实现 | ✅ 内置 | 需要自己实现 |
| 适用场景 | 低频更新（邮件通知） | AI 流式输出、实时数据推送 | 聊天、实时协作、游戏 |

### 方案1：轮询

~~~javascript
// ========== 短轮询 ==========
async function 轮询() {
  const 响应 = await fetch("/api/菜品状态");
  const 数据 = await 响应.json();
  更新界面(数据);
}

setInterval(轮询, 3000);  // 每 3 秒请求一次

// 问题：大量无效请求（数据没变也要请求），浪费带宽和服务器资源

// ========== 长轮询 ==========
async function 长轮询() {
  const 响应 = await fetch("/api/菜品状态");  // 服务端会挂住请求，直到有新数据
  const 数据 = await 响应.json();
  更新界面(数据);
  长轮询();  // 立即发起下一次长轮询
}

长轮询();

// 优点：比短轮询实时性更好，减少无效请求
// 缺点：每次都要建立新的 HTTP 连接，有延迟
~~~

### 方案2：SSE（Server-Sent Events）

~~~
SSE 的特点：
  基于 HTTP，服务端单向推送数据给客户端
  自动重连（连接断了会自动重试）
  文本格式（不能发二进制数据）
  浏览器原生支持 EventSource API
~~~

~~~javascript
// ========== 前端：EventSource 接收 ==========
const 事件源 = new EventSource("/api/菜品流");

// 监听默认消息
事件源.onmessage = (事件) => {
  console.log("收到数据：", 事件.data);
  更新界面(JSON.parse(事件.data));
};

// 监听自定义事件
事件源.addEventListener("新菜品", (事件) => {
  console.log("新菜品：", 事件.data);
});

// 监听连接打开
事件源.onopen = () => {
  console.log("SSE 连接已建立");
};

// 监听错误
事件源.onerror = (错误) => {
  console.log("SSE 连接错误，会自动重连");
};

// 关闭连接
事件源.close();

// ========== 服务端：Node.js (Express) ==========
app.get("/api/菜品流", (req, res) => {
  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");
  res.setHeader("Connection", "keep-alive");

  // 发送数据的格式：
  // data: 消息内容\n\n
  // event: 事件名\n
  // id: 消息ID\n
  // retry: 重连时间(ms)\n

  setInterval(() => {
    res.write(`data: ${JSON.stringify({ 菜品: "红烧肉", 价格: 38 })}\n\n`);
  }, 1000);

  // 发送自定义事件
  res.write(`event: 新菜品\ndata: ${JSON.stringify({ 名字: "宫保鸡丁" })}\n\n`);
});
~~~

### SSE 在 AI 应用中的应用（流式输出）

~~~
AI 流式输出的完整链路：

  用户输入 → 前端发请求 → 后端调 LLM API → LLM 逐 token 生成
  → 后端通过 SSE 逐 token 推送给前端 → 前端逐字渲染

为什么 AI 用 SSE 而不是 WebSocket？
  1. AI 回答是单向的（只有服务端→客户端），不需要双向通信
  2. SSE 基于 HTTP，更简单，自动重连
  3. WebSocket 是双向的，对于 AI 流式输出来说是"杀鸡用牛刀"
~~~

~~~javascript
// ========== 前端：fetch + ReadableStream 接收 SSE ==========
async function 流式请求(prompt) {
  const 响应 = await fetch("/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ prompt })
  });

  const 读取器 = 响应.body.getReader();
  const 解码器 = new TextDecoder();
  let 累积文本 = "";

  while (true) {
    const { done, value } = await 读取器.read();
    if (done) break;

    const 文本 = 解码器.decode(value, { stream: true });
    累积文本 += 文本;
    更新界面(累积文本);  // 逐字更新界面
  }
}

// ========== 前端：EventSource 接收 SSE ==========
const 事件源 = new EventSource("/api/chat-stream?prompt=红烧肉怎么做");
事件源.onmessage = (事件) => {
  if (事件.data === "[DONE]") {
    事件源.close();  // 流结束
    return;
  }
  const token = JSON.parse(事件.data).content;
  累积文本 += token;
  更新界面(累积文本);
};
~~~

## 套路八：性能优化

### 加载优化

**手写口诀：减少请求、压缩资源、懒加载、预加载**

~~~
1. 减少 HTTP 请求
   - 合并 CSS/JS 文件
   - CSS Sprites（雪碧图）
   - 内联小资源（Base64）

2. 压缩资源
   - Gzip / Brotli 压缩
   - 图片压缩（WebP 格式）
   - 代码压缩（Terser / cssnano）

3. 懒加载
   - 图片懒加载（loading="lazy" 或 IntersectionObserver）
   - 路由懒加载（() => import()）
   - 组件懒加载（defineAsyncComponent）

4. 预加载 / 预获取
   - <link rel="preload">（关键资源）
   - <link rel="prefetch">（可能用到的资源）
   - <link rel="preconnect">（提前建立连接）
   - DNS 预解析（dns-prefetch）

5. CDN 加速
   - 静态资源放 CDN
   - 就近访问，减少网络延迟
~~~

### 渲染优化

~~~
1. 减少重排重绘
   - 批量修改 DOM
   - 用 transform 代替 top/left
   - 读写分离

2. CSS 优化
   - CSS 放 <head>（尽早加载）
   - 避免深层选择器（#id > .class > tag）
   - 使用 will-change 提示浏览器

3. JS 优化
   - 避免长任务（拆分成小任务）
   - 使用 Web Worker（多线程）
   - requestAnimationFrame（动画优化）
   - 避免强制同步布局
~~~

### 网络优化

~~~
1. HTTP/2 多路复用（减少连接数）
2. Keep-Alive（复用 TCP 连接）
3. 减少 Cookie 大小（静态资源用无 Cookie 的域名）
4. 服务端渲染（SSR）或静态生成（SSG）
5. 预渲染（Prerender）
~~~

### 图片懒加载（手写）

**手写口诀：data-src 存真实地址，IntersectionObserver 监听可见性**

~~~javascript
// ========== 原生 loading 属性（最简单） ==========
// <img src="图片.jpg" loading="lazy" alt="菜品">

// ========== IntersectionObserver 实现 ==========
function 懒加载() {
  const 图片们 = document.querySelectorAll("img[data-src]");

  const 观察器 = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        const img = entry.target;
        img.src = img.dataset.src;     // 把 data-src 赋给 src
        img.removeAttribute("data-src");
        观察器.unobserve(img);          // 取消观察
      }
    });
  }, {
    rootMargin: "200px"  // 提前 200px 开始加载
  });

  图片们.forEach(img => 观察器.observe(img));
}
~~~

## 高频面试题

### 题目1：HTTP 状态码

| 状态码 | 含义 | 常见场景 |
|---|---|---|
| 200 | OK | 请求成功 |
| 201 | Created | 创建成功（POST） |
| 204 | No Content | 成功但没有返回内容（DELETE） |
| 301 | Moved Permanently | 永久重定向 |
| 302 | Found | 临时重定向 |
| 304 | Not Modified | 协商缓存命中 |
| 400 | Bad Request | 请求参数错误 |
| 401 | Unauthorized | 未登录/未认证 |
| 403 | Forbidden | 无权限（已登录但没权限） |
| 404 | Not Found | 资源不存在 |
| 405 | Method Not Allowed | 请求方法不允许 |
| 500 | Internal Server Error | 服务器内部错误 |
| 502 | Bad Gateway | 网关错误（上游服务挂了） |
| 503 | Service Unavailable | 服务器不可用（过载/维护） |

### 题目2：GET 和 POST 的区别

| | GET | POST |
|---|---|---|
| 参数位置 | URL 查询字符串 | 请求体 |
| 参数大小 | URL 长度限制（浏览器限制，通常 2KB-8KB） | 无限制（服务器可配置） |
| 缓存 | 可以被缓存 | 不会被缓存 |
| 幂等性 | 幂等（多次请求结果一样） | 不幂等 |
| 安全性 | 参数在 URL 中可见 | 参数在请求体中（相对安全） |
| 用途 | 获取数据 | 提交数据 |
| 浏览器历史 | 会留在历史记录 | 不会 |
| 书签 | 可以收藏 | 不可以 |

~~~
严格来说：
  GET 和 POST 在 TCP 层面没有区别
  都是基于 TCP 的 HTTP 请求
  区别在于 HTTP 规范的定义和浏览器的行为
~~~

### 题目3：从输入 URL 到页面渲染，简述流程

~~~
1. DNS 解析：域名 → IP 地址（浏览器缓存 → 系统缓存 → 路由器 → ISP → 根 DNS）
2. TCP 三次握手：建立连接
3. TLS 握手（HTTPS）：加密通道
4. 发送 HTTP 请求：拿到响应数据
5. 解析 HTML：构建 DOM 树
6. 解析 CSS：构建 CSSOM 树
7. 合成渲染树：DOM + CSSOM → 渲染树
8. 布局：计算每个节点的位置和大小
9. 绘制：把节点画到屏幕上
10. JS 执行：可能修改 DOM/CSSOM → 重新渲染
~~~

### 题目4：事件委托的原理

**手写口诀：把事件绑定到父元素，利用事件冒泡处理子元素的事件**

~~~javascript
// ========== 不用事件委托 ==========
const 菜品们 = document.querySelectorAll(".菜品");
菜品们.forEach(菜品 => {
  菜品.addEventListener("click", () => {
    console.log(菜品.textContent);
  });
});
// 问题：100个菜品 = 100个事件监听器 = 内存开销大

// ========== 用事件委托 ==========
const 菜单 = document.querySelector(".菜单");
菜单.addEventListener("click", (事件) => {
  const 目标 = 事件.target;  // 真正被点击的元素
  if (目标.classList.contains("菜品")) {
    console.log(目标.textContent);
  }
});
// 只有1个事件监听器 = 内存开销小
// 动态添加的菜品也能响应事件

// ========== 事件委托的好处 ==========
// 1. 减少事件监听器数量（内存优化）
// 2. 动态元素也能响应事件
// 3. 代码更简洁
~~~

### 题目5：安全相关 HTTP 头

| Header | 作用 | 示例 |
|---|---|---|
| Content-Security-Policy | 限制页面能加载的资源（防 XSS） | `default-src 'self'; script-src 'self' 'unsafe-inline'` |
| X-Content-Type-Options | 禁止浏览器猜测 MIME 类型 | `nosniff` |
| X-Frame-Options | 禁止页面被嵌入 iframe（防点击劫持） | `DENY` 或 `SAMEORIGIN` |
| Strict-Transport-Security | 强制使用 HTTPS | `max-age=31536000; includeSubDomains` |
| Set-Cookie（HttpOnly） | JS 不能读取 Cookie（防 XSS 窃取） | `session=abc; HttpOnly` |
| Set-Cookie（SameSite） | 限制 Cookie 跨站发送（防 CSRF） | `session=abc; SameSite=Lax` |
| Set-Cookie（Secure） | 只在 HTTPS 下发送 | `session=abc; Secure` |
| Access-Control-Allow-Origin | 允许跨域访问的来源 | `http://localhost:3000` |

### 题目6：TCP 三次握手和四次挥手

~~~
三次握手（建立连接）：
  客户端 → SYN=1, seq=x              → 服务端  （我要连接）
  客户端 ← SYN=1, ACK=1, seq=y, ack=x+1 ← 服务端  （收到，我也准备好了）
  客户端 → ACK=1, seq=x+1, ack=y+1   → 服务端  （好的，开始通信）

四次挥手（断开连接）：
  客户端 → FIN=1                      → 服务端  （我要断开）
  客户端 ← ACK=1                      ← 服务端  （收到，我还有数据没发完）
  客户端 ← FIN=1                      ← 服务端  （我也发完了，可以断开）
  客户端 → ACK=1                      → 服务端  （好的，断开）
  客户端等待 2MSL（确保服务端收到 ACK）

为什么握手三次、挥手四次？
  握手：服务端的 SYN 和 ACK 可以合并成一次发送
  挥手：服务端收到 FIN 后可能还有数据要发，不能把 ACK 和 FIN 合并
~~~

## 终极记忆卡片

~~~
套路1：从 URL 到页面
  DNS 解析（域名→IP）→ TCP 三次握手 → TLS 握手（HTTPS）
  → HTTP 请求 → 解析 HTML/CSS → 构建 DOM/CSSOM → 渲染

套路2：浏览器架构
  多进程：主进程（UI/网络）+ 渲染进程（DOM/JS/布局/绘制）+ GPU进程 + 网络进程
  安全沙箱：渲染进程被隔离，不能访问系统
  V8 引擎：源码 → AST → 字节码 → JIT 热点编译 → 机器码
  进程 vs 线程：进程独立内存，线程共享内存；JS 主线程和布局/绘制是同一个线程

套路3：渲染机制
  DOM + CSSOM → 渲染树 → 布局 → 绘制 → 合成
  重排（布局变了）→ 重排 + 重绘
  重绘（外观变了）→ 只重绘
  优化：批量修改、transform 代替 top/left、读写分离

套路4：浏览器缓存
  强缓存：Cache-Control / Expires → 不发请求，直接用缓存
  协商缓存：ETag + If-None-Match / Last-Modified + If-Modified-Since
  → 发请求问服务器 → 304 用缓存 / 200 新内容

套路5：浏览器存储与 Token
  Cookie（4KB，自动携带，可设 HttpOnly/SameSite）
  localStorage（5MB，永久，JS 可读，有 XSS 风险）
  sessionStorage（5MB，关闭标签页清除，同标签页隔离）
  JWT 结构：Header.Payload.Signature（Base64 编码 + 签名防篡改）
  JWT 存 Cookie（安全但有 CSRF）vs 存 localStorage（简单但有 XSS）

套路6：跨域与安全
  CORS → 正道（服务端设置响应头）
  代理 → 开发环境最常用
  JSONP → 老方案（只支持 GET）
  XSS → 注入脚本 → 转义输入 + CSP + HttpOnly
  CSRF → 伪造请求 → Token + SameSite Cookie

套路7：实时通信
  轮询 → 最简单，客户端定时请求（实时性差）
  SSE → 服务端单向推送，基于 HTTP，自动重连（AI 流式输出首选）
  WebSocket → 双向实时通信，独立协议（聊天/协作/游戏）

套路8：性能优化
  加载：压缩、懒加载、预加载、CDN
  渲染：减少重排重绘、Web Worker、requestAnimationFrame
  网络：HTTP/2、Keep-Alive、减少 Cookie

高频面试题
  状态码：200/301/302/304/400/401/403/404/500/502/503
  GET vs POST：参数位置、缓存、幂等性
  Cookie/localStorage/sessionStorage：大小、有效期、是否发到服务器
  JWT 三段结构：Header.Payload.Signature
  事件委托：父元素监听 + event.target
  安全 HTTP 头：CSP/X-Frame-Options/HSTS/HttpOnly/SameSite
  三次握手/四次挥手：建立连接/断开连接的过程
~~~
